# 叩君芯会员产品平台 · 功能清单与层级结构
## Feature Inventory & Hierarchy v1.1

> **本文档定位**：只列**功能、界面、配置项、上下级关系**，**不涉及定价**（定价另行讨论）。
>
> **与规格书的关系**：`04-完整功能规格说明书.md`（v2.0）定"是什么、为什么"；本文档定"有哪些、分几层、谁管谁、后台长什么样"；`06-日志与数据留存设计.md` 定日志。
>
> **核心概念**：**作品自定义工具（Custom Tool）** —— 每款文游可以定义自己的服务端工具接口，实现差异化功能。工具不在 HTML 里，走服务端执行，因此**抄得走界面，抄不走能力**。
>
> **v1.1 变更**：
> 1. **账号与会员体系重构**（§1 A 组、§2 A 组）—— 由「会员编码 + 抖音ID 登录」改为「**平台账号注册登录 + 个人主页填写抖音号与会员时长做绑定验证**」。
> 2. 前台界面由 13 个增至 **15 个**（新增注册、登录、个人主页、我的解锁、订单与支付）。
> 3. 后台界面由 12 个增至 **18 个**（新增日志中心、音乐库、订单与退款、绑定审核、用户账号管理、留存策略）。
> 4. 功能项由 216 条增至 **约 250 条**（新增 ACC / BND / QUO 三组）。
> 5. §9 本轮补充（日志、支付、音乐配置）。
>
> **唯一事实来源**：本文件 ｜ **版本**：v1.1

## 4. 作品工具体系 ★（新增核心）

### 4.1 为什么"工具在服务端"就抄不走

**这是本轮新增卖点的技术根据。**

> **先纠正一个容易误解的说法**：不是"前端更薄"。**前端是"逻辑薄、设计厚"** —— 它依然是经过精心设计的、美观的界面，依然带完整的**素材包**与**音乐包**。变薄的只是**业务编排**，不是**视觉与内容资产**。

```
传统做法（参考样例）：
  单文件 HTML（287KB）
  ├── 界面设计 + 素材     → 抄走
  ├── 音乐 + 播放器逻辑   → 抄走
  ├── 业务逻辑            → 抄走
  ├── 工具实现            → 抄走
  ├── Prompt              → 抄走
  └── 剧情内容            → 抄走
  结果：抄走 100%

本平台做法：
  前端（设计厚、逻辑薄）
  ├── 界面设计 + 布局 token   → 可抄（但只是一套"皮"）
  ├── 素材包（图片/音频/字体）→ 有防护：签名 URL + 隐形水印 + 按需下发
  ├── 音乐包 + 播放器 UI      → 可抄 UI，抄不到"选哪首曲、什么时候播"
  ├── 组件渲染（node.type）   → 平台组件库白名单，不可扩展
  └── 业务逻辑                → 不在前端
  服务端（编排厚）
  ├── 工具实现            → ✗ 抄不走
  ├── 工具前置条件        → ✗ 抄不走
  ├── 触发时机与概率      → ✗ 抄不走
  ├── 文案生成策略        → ✗ 抄不走
  ├── 音乐选配与播放策略  → ✗ 抄不走
  ├── 提示词方法论        → ✗ 抄不走
  └── 秘密内容            → ✗ 抄不走
  结果：能抄到一套好看的皮 + 一批素材，抄不到"什么时候发、发什么、给谁看、放哪首曲子、怎么判断"
```

**一句话**：`抄得走像素与素材，抄不走编排。`

**分层防护对应表**：

| 资产 | 防护手段 | 强度 |
|---|---|---|
| **UI 设计**（布局/视觉规范/动效） | 平台渲染器 + 组件库白名单 → 抄走的是"引用"，不是"实现" | 中高 |
| **素材包**（图片/音频/字体） | 短时效签名 URL + 用户隐形水印 + 未到达阶段不下发 + 可追溯 | 中（可追溯） |
| **音乐包** | 音频走服务端签名下发，曲库清单不下发；播放决策在服务端 | 中 |
| **业务编排**（工具/触发/策略） | 完全服务端执行 | **高（根本拿不到）** |
| **提示词方法论** | 母版永不下发 | **高** |
| **结局与隐藏真相** | 服务端 Tool | **高** |

#### 4.4.1 音乐与背景音乐体系（服务端）★

> 需求确认：**背景音乐与音乐播放器都走服务端**，并且**能选配功能、选择音乐**。
>
> 即：作品不打包音乐、不写播放逻辑；只声明"什么场景放什么"，实际选曲与下发由服务端完成。

**四层结构**：

```
① 平台音乐库（platform_music）
   曲目实体：track_id / 名称 / 艺术家 / 时长 / 格式 / 码率 / 版权 / 情绪标签 / 场景标签
        │
        ├──▶ ② 音乐包（music_pack）
        │      按主题打包：如"都市夜雨包""校园清新包""悬疑紧张包"
        │      作品可引用一个或多个音乐包
        │
        ├──▶ ③ 场景选配（work_music_binding）★
        │      作品级配置：场景 → 曲目/选曲规则
        │      例：开场 → 曲A；紧张 → 从"紧张"标签随机；结局 → 按结局ID指定
        │
        └──▶ ④ 运行时播放器（server-side player）
               服务端持播放状态，前端只渲染播放器 UI 并播放服务端给的签名 URL
```

**曲目元数据字段**：

| 字段 | 说明 |
|---|---|
| `track_id` / `title` / `artist` / `album` | 基本信息 |
| `duration_sec` / `format` / `bitrate` | 音频参数 |
| `mood_tags` | 情绪标签（温情/紧张/失落/治愈/燃/悬疑…） |
| `scene_tags` | 场景标签（开场/日常/冲突/告白/离别/结局…） |
| `loop_points` | 循环点（可选） |
| `license` | 版权来源与授权范围（必须） |
| `volume_default` | 默认音量（不同曲目响度不同，需要归一化） |
| `fade_in_ms` / `fade_out_ms` | 默认淡入淡出 |
| `watermark_id` | 隐形水印 ID |

**场景选配配置（作品级）**：

| 场景 key | 取值方式 | 示例 |
|---|---|---|
| `intro` | 固定曲目 | `{"fixed": "track_001"}` |
| `daily` | 随机（同标签） | `{"tag": "治愈", "avoidRepeat": 3}` |
| `conflict` | 权重随机 | `{"pool": [{"id":"t1","w":3},{"id":"t2","w":1}]}` |
| `ending.*` | 按结局 ID 映射 | `{"byEnding": {"end_good":"t9","end_bad":"t10"}}` |
| `silence` | 静音 | `{"silent": true}` |

**服务端播放器能力**：

| 能力 | 说明 |
|---|---|
| 播放/暂停/停止 | 服务端持状态，前端同步 |
| 淡入淡出 | 切歌不突兀（默认 800ms） |
| 单曲/列表/随机循环 | 与「一起听歌」联动 |
| 响度归一化 | 按 `volume_default` 自动校正 |
| 断点续播 | 跨设备恢复播放位置 |
| 场景自动切换 | 剧情推进到某阶段自动换曲（服务端触发） |
| 与剧情联动 | 曲目位置可绑定剧情事件（如"播到 1:23 时角色发一条消息"） |
| 沉默规则 | 对白密集段落自动降低 BGM 音量（ducking） |

**前端职责**：只有播放器 UI 组件（`music-player` / `music-list` / `listen-together`）+ 播放服务端给的签名 URL。**曲库清单、选曲规则、场景映射一律不下发。**

**配置项（见 §5.3 / §5.5）**：作品级选配"音乐包引用 + 场景→曲目映射 + 全局音量 + 是否允许用户关闭 BGM"；界面级配置播放器外观 Token。

### 4.5 作品自定义工具（Custom Tools）★

**这是"差异化"的实现方式。** 已确认：**只使用两种定义方式，不开放脚本。**

| 方式 | 表达能力 | 谁来做 | 状态 |
|---|---|---|---|
| **方式 1：启用内置** | 低（平台既有能力） | 管理员勾选 + 配参数，零代码 | ✅ 采纳 |
| **方式 2：声明式组合** | 高（原子能力任意组合） | 管理员拖拽拼装，零代码 | ✅ 采纳（主力） |
| ~~方式 3：受限脚本~~ | 最高 | 需开发能力 | ❌ **已确认不开放** |

> **为什么砍掉脚本**：一旦开放，就要承担沙箱逃逸、资源耗尽、绕过前置校验三类风险，审核成本与安全面都上一个台阶。声明式组合的表达力**已覆盖平台需要的全部场景**（条件分支、循环、子调用见 §4.5.2），因此不值得为边际表达力引入这些风险。

#### 方式 1：启用内置（零代码）

```json
{ "use": "moments.post", "config": { "maxPerDay": 2, "stageMin": 3 } }
```

#### 方式 2：声明式组合（推荐，管理员无需写代码）

```json
{
  "name": "rewrite.message",
  "displayName": "改写消息并重演",
  "description": "玩家改写历史中某条消息后，重演后续剧情。",
  "parameters": {
    "type": "object",
    "properties": {
      "nodeId": { "type": "string" },
      "msgId":  { "type": "string" },
      "newText":{ "type": "string" }
    },
    "required": ["nodeId", "msgId", "newText"]
  },
  "preconditions": [
    "member.logged_in",
    "work.unlocked",
    "session.worldline == 'rewritten'",
    "session.node(nodeId).reached == true"
  ],
  "steps": [
    { "op": "rule.eval", "expr": "boundary(nodeId, msgId)", "as": "bound" },
    { "op": "state.set", "path": "rewritten.node(msgId).text", "value": "$.newText" },
    { "op": "llm.generate", "promptRef": "replay", "vars": { "bound": "$.bound" }, "as": "result" },
    { "op": "rule.eval", "expr": "validatePack($.result, $.bound)", "as": "valid" },
    { "op": "if", "cond": "$.valid == false", "then": [{ "op": "return", "value": { "ok": false, "reason": "重演结果不完整，已回滚" } }] },
    { "op": "state.patch", "value": "$.result.state" },
    { "op": "ui.render", "target": "chat.messages", "op": "replace-range", "node": { "type": "chat.bubble", "props": "$.result.lines" } },
    { "op": "schedule.once", "delay": 0, "payload": { "event": "lock_nodes_after", "next": "$.bound.next" } }
  ],
  "permissions": ["state.write", "llm.generate", "ui.render", "schedule.once"],
  "rateLimit": { "perSession": 30, "cooldownSec": 0 },
  "sideEffects": ["state", "ui"],
  "audit": true
}
```

#### 方式 2 的完整表达能力（替代脚本所需）

| 能力 | 语法 | 说明 |
|---|---|---|
| 顺序执行 | `steps[]` | 按序执行 |
| 变量绑定 | `"as": "name"` + `"$.name"` 引用 | 步骤间传值 |
| 条件分支 | `{"op":"if","cond":"...","then":[...],"else":[...]}` | 表达式为真走 then |
| 多路分支 | `{"op":"switch","on":"...","cases":{...}}` | 按值分派 |
| 循环 | `{"op":"foreach","in":"$.list","as":"item","do":[...]}` | 遍历 |
| 提前返回 | `{"op":"return","value":{...}}` | 中断并返回 |
| 断言 | `{"op":"assert","cond":"...","message":"..."}` | 不满足即拒绝 |
| 子工具调用 | `{"op":"tool.call","name":"moments.post","args":{...}}` | 复用其他工具 |
| 并行 | `{"op":"parallel","branches":[...]}` | 并行执行分支 |
| 事务 | `{"op":"transaction","steps":[...]}` | 全部成功或全部回滚 |
| 重试 | `{"op":"retry","times":2,"steps":[...]}` | 失败重试 |
| 超时 | `{"op":"timeout","ms":3000,"steps":[...]}` | 超时中断 |

> 这套组合能力等价于一门**受限的声明式工作流语言**：有分支、循环、子调用、事务、重试、超时，但不含文件、网络、反射、任意代码执行。安全面可控，表达力足够。

### 4.6 工具定义 Schema

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | ✅ | 唯一标识（`^[a-z][a-z0-9_.]{2,48}$`），不得与平台保留名冲突 |
| `type` | ✅ | `builtin` / `custom` |
| `displayName` | ✅ | 后台展示名 |
| `description` | ✅ | **给模型看的描述**（决定模型何时调用） |
| `parameters` | ✅ | JSON Schema |
| `preconditions` | ✅ | 前置条件表达式数组 |
| `implementation` | ✅ | `{kind: builtin\|compose, ...}`（**不支持 `script`**） |
| `permissions` | ✅ | 需要的原子能力白名单 |
| `rateLimit` | 🔶 | `{perSession, perDay, cooldownSec}` |
| `returns` | 🔶 | 返回值 Schema |
| `ui` | 🔶 | 返回的 UI 指令声明 |
| `sideEffects` | ✅ | `state` / `ui` / `notify` / `asset` |
| `audit` | ✅ | 是否记录调用日志 |
| `version` | 🔶 | 工具版本 |
| `fallback` | 🔶 | 失败时的降级行为 |

### 4.7 工具执行链路

```
模型输出 tool_call
      │
      ▼
① 解析与校验参数（JSON Schema）
      │ 失败 → 返回参数错误，让模型重试（≤2 次）
      ▼
② 前置条件校验链
   ├─ 登录态
   ├─ 该会员是否持有该 work 的 entitlement
   ├─ 会话状态是否满足（stage / worldline / reached）
   ├─ 频次与冷却（rateLimit）
   └─ 单回合工具调用次数上限
      │ 任一失败 → 返回结构化拒绝原因（给模型一句可用的解释）
      ▼
③ 执行实现
   ├─ builtin → 平台实现
   └─ compose → 按 steps 顺序执行原子能力
      │ 超时 → 返回"信息不可用"，让模型降级
      ▼
④ 内容安全审核（若产生文本）
      │ 命中 → 按策略拦截/改写
      ▼
⑤ 写状态 + 产出 UI 指令
      ▼
⑥ 审计日志
      ▼
⑦ 结果回填给模型 → 模型生成最终回复
      ▼
⑧ 返回前端：{ finalText, ui[], state }
```

### 4.8 工具返回的声明式 UI 协议

**前端只认识 `node.type`，不认识业务语义。这是防抄的核心。**

```json
{
  "ok": true,
  "ui": [
    {
      "target": "chat.messages",
      "op": "append",
      "node": {
        "type": "redpacket-card",
        "props": { "amount": 52.0, "note": "买个小蛋糕", "opened": false }
      }
    },
    {
      "target": "wallet.balance",
      "op": "patch",
      "value": 468.0
    }
  ],
  "state": { "wallet": 468.0, "redpacketCount": 3 },
  "hint": "红包已发出，可以自然提及但不要重复强调金额"
}
```

| 字段 | 说明 |
|---|---|
| `ui[].target` | 目标容器（`chat.messages` / `moments.feed` / `wallet.balance` / `memo.list` …） |
| `ui[].op` | `append` / `prepend` / `replace` / `patch` / `remove` / `replace-range` |
| `ui[].node` | 声明式节点：`{type, props}`，type 来自组件库白名单 |
| `state` | 状态增量（前端可乐观更新，服务端为权威） |
| `hint` | 给模型的下一轮提示（不给用户看） |

**安全约束**：
- `node.type` 必须在组件库白名单内，否则拒绝
- `props` 必须通过该组件的 props Schema 校验
- **禁止 `html` / `script` / `style` 原始字符串字段**
- UI 指令**不做前端持久缓存**（防止一次性把所有内容拉下来）

### 4.9 工具的测试与调试

| 功能 | 说明 |
|---|---|
| 测试台 | 手填参数 → 执行 → 看返回、UI 指令、状态变化、耗时 |
| 干跑模式 | 不写状态，只返回将要产生的效果 |
| 调用日志 | 入参/结果/耗时/前置条件判定过程 |
| 回放 | 复现某次真实调用 |
| 参数建议 | 从真实调用日志生成参数示例，反哺 Prompt |
| 误调用分析 | 统计模型在什么场景错误调用了该工具 |

### 4.10 工具与提示词的关系

| 提示词负责 | 工具负责 |
|---|---|
| 何时需要信息 | 提供信息 |
| 用什么语气对用户说话 | 执行副作用（发消息、改状态） |
| 如何把工具结果编织进回复 | 保证前置条件与安全 |

**服务端负责**：是否允许提供。

→ 三者的配合设计就是 §10.8 的「提示词 × Tool 联动」，是本平台的核心竞争力。

## 7. 功能依赖与上下级关系

### 7.1 关键依赖链

```
会员体系 ──┬─→ 登录 ─→ 会话 ─→ 解锁 ─→ 权益 ─→ 进入作品
           └─→ 额度 ─→ 计费账本

作品体系 ──┬─→ 作品 ─→ 版本 ─→ 作品包 ─→ 校验 ─→ 审核 ─→ 发布
           ├─→ 内容库 ─→ 内容版本 ─→ 披露阶段
           └─→ 素材库 ─→ 签名URL ─→ 水印

工具与AI ──┬─→ 母版 ─→ 作品Prompt ─→ 运行时Prompt ─→ 模型调用
           ├─→ 人设生成 ─→ 人物 ─→ 触发映射 ─→ 事件触发
           └─→ 原子能力 ─→ 内置工具 ─┐
                                     ├─→ 工具注册表 ─→ 工具执行 ─→ UI指令 ─→ 前端渲染
                       自定义工具 ───┘

通道体系 ──┬─→ 平台通道 ─→ 渠道池 ─→ 路由 ─→ 计量 ─→ 账本
           └─→ BYOK ─→ 本地凭据 ─→ 转发 ─→ （可选计量）

运行时 ────┬─→ 布局渲染器 ─→ 会话界面
           └─→ 外壳/容器/导航栈 ─→ 游戏游玩界面
```

### 7.2 上下级关系（谁管谁）

| 上层 | 管什么 | 下层 |
|---|---|---|
| 作品 | 声明启用哪些工具、提示词模式、App 容器、布局 | 版本、内容、素材、工具 |
| 版本 | 冻结一次交付快照 | 作品包、内容版本 |
| 工具定义 | 声明参数、前置条件、权限、限流 | 工具实例、调用日志 |
| **原子能力** | 是工具的地基，**不可被作品修改** | 内置工具、自定义工具 |
| 提示词母版 | 产出作品 Prompt | 作品 Prompt |
| 作品 Prompt | 组装出运行时 Prompt | 运行时 Prompt |
| 系统配置 | 默认值 | 作品配置（可覆盖） |
| 作品配置 | 默认值 | 会话配置（可覆盖） |
| 平台通道 | 上游渠道与路由 | 单次调用 |
| 权益 | 决定能否执行工具的前置校验 | 工具执行 |

**覆盖优先级（从高到低）**：会话配置 > 作品配置 > 系统配置
**通道解析优先级**：界面临时 > 作品允许 > 用户默认 > 平台默认

| B-05 工具管理 | 查 `TOOL_CALL` + 误调用分析 |
| B-09 通道与策略 | 查 `SEC`（限流/SSRF/异常） |
| **B-16 留存策略配置**（新增） | 12 类日志的热存/总留存/到期动作配置 + 归档与销毁记录 |

#### 9.1.3 日志的存储与容量要点

| 要点 | 结论 |
|---|---|
| 主数据库 | MySQL 8.4 存业务事实/审计/计费；ClickHouse 只存访问/AI/工具分析投影；对象存储存内容与归档 |
| 最大头 | `ACCESS`（DAU 1 万时约 1.2 GB/天）→ **必须采样 + 180 天 TTL** |
| 内容日志 | 默认关闭 → 默认零成本零风险 |
| 合规底线 | `ACCESS`/`SEC`/`BIZ` ≥180 天，满足《网络安全法》≥6 个月 |
| 不可篡改 | `AUDIT` 链式哈希 + 权限层禁 UPDATE/DELETE |
| 待确认 | 备案时主管部门是否要求 `AI_CONTENT` 全量开启 |

### 9.2 支付渠道（已确认）

**只考虑支付宝与微信支付两条通道。**

| 项 | 规格 |
|---|---|
| 渠道 | 支付宝（电脑网站支付 / 手机网站支付 / APP 支付）、微信支付（JSAPI / Native / H5 / APP） |
| 不接入 | Stripe / PayPal / Adyen / GoCardless 等海外渠道（**平台面向国内市场**） |
| 订单类型 | ① 会员订阅（月/季/年）② 额度充值（平台通道 token 余额） |
| 关键机制 | 回调**验签 + 幂等**；**主动查单兜底**（定时补偿，防掉单）；退款原路返回 |
| 对账 | 按日与支付宝/微信账单比对，差异告警 |
| 资质前置 | 支付宝商户号、微信支付商户号、营业执照、ICP 备案 |

**对应功能项（更新 BIL 组）**：

| ID | 功能 | 说明 |
|---|---|---|
| BIL-12 | 订单创建 | 会员订阅 / 额度充值 |
| BIL-13 | 支付宝支付 | 下单 + 回调验签 + 幂等 |
| BIL-13b | **微信支付** | 下单 + 回调验签 + 幂等 |
| BIL-14 | 主动查单兜底 | 定时轮询未决订单 |
| BIL-15 | 退款 | 原路退回，财务审批 |
| BIL-16 | 支付对账 | 与支付宝/微信账单日比对 |

**对架构的简化收益**：
- 不需要多币种、多支付服务商编排 → **不引入 Lago 这类用量计费引擎的理由更充分**
- 支付与账本解耦：支付只管"钱进来"，账本管"钱怎么花"
- 支付服务商仅 2 家 → 抽象层可以很薄，直接在业务层封装两个 adapter

### 9.4 组件库不可扩展（已确认）

见 §3.3 的说明。要点：**组件库为固定白名单，作品不能注册新组件**；特殊视觉只能通过 ① 组合现有组件 + Token 深度定制，或 ② `custom.slot:{name}` 自定义槽位（仅 CSS + 素材，不含逻辑）实现。

### 9.5 前端定位（修正）

**前端是"逻辑薄、设计厚"，不是"更轻薄"。**

| 维度 | 状态 |
|---|---|
| 视觉设计 | **厚** —— 依然是精心设计、美观的界面 |
| 素材包 | **厚** —— 图片/音频/字体完整打包（受签名 URL + 水印保护） |
| 音乐包 | **厚** —— 但音频实体在服务端，前端只播服务端给的签名 URL |
| 播放器 UI | **厚** —— 完整播放器界面 |
| 组件渲染 | **平台提供** —— 作品只引用 `node.type` |
| 业务逻辑 | **不在前端** —— 全部服务端 |
| 工具编排 | **不在前端** —— 全部服务端 |
| Prompt | 视模式而定（`SERVER` 不下发 / `PACKAGE` 下发） |
