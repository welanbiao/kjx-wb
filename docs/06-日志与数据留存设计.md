# 叩君芯会员产品平台 · 日志与数据留存设计
## Logging & Data Retention Design v1.1

> **文档定位**：定义平台要**生成哪些日志、记录哪些字段、存在哪里、留多久、怎么脱敏、怎么查**。
>
> **约束来源**：
> - 合规：《网络安全法》日志留存 ≥ 6 个月；《生成式人工智能服务管理暂行办法》要求留存输入输出
> - 业务：解锁审计、计费对账、问题排查、风控取证
> - 隐私：BYOK 内容不记录；个人信息脱敏；用户可查可删
> - 成本：高频日志不得压垮主打库，必须冷热分层
>
> **配套文档**：`04-完整功能规格说明书.md`（v2.0，§16 引用本文）、`05-功能清单与层级结构.md`
>
> **存储基线**：MySQL 8.4 是业务事实、审计与计费的权威存储；ClickHouse
> 只承载 `ACCESS` / `AI_CALL` / `TOOL_CALL` 等分析投影。禁止从 ClickHouse 回读权限、权益或余额。

## 1. 设计目标与原则

### 1.1 五个目标

| # | 目标 | 验收标准 |
|---|---|---|
| 1 | **可审计** | 任何一次解锁、扣费、权益变更、后台操作，都能还原"谁、何时、做了什么、结果如何" |
| 2 | **可对账** | 账本流水 ↔ 用量事件 ↔ 上游账单，三方差异可定位到单次调用 |
| 3 | **可排查** | 用户报障时，凭 `trace_id` 能串起前端 → 网关 → 模型 → 工具 → 存档的完整链路 |
| 4 | **可合规** | 满足 ≥180 天留存、输入输出留存、不可篡改、可导出配合监管 |
| 5 | **可控制** | 日志成本可控；不记录不该记的内容；用户可查可删 |

### 1.2 六条设计原则

| 原则 | 说明 |
|---|---|
| **P1 结构化** | 全部 JSON 结构化，禁止裸文本拼接；字段名全平台统一 |
| **P2 全链路 ID** | `trace_id` / `request_id` / `session_id` / `turn_id` / `idempotency_key` 贯穿始终，任意一条日志可横向串联 |
| **P3 写不阻塞主流程** | 日志异步落盘（本地缓冲 + 批量投递），日志故障不影响业务 |
| **P4 冷热分层** | 热数据（可查）→ 温数据（归档可查）→ 冷数据（合规留存，离线取） |
| **P5 默认最小化** | 默认不记录对话内容；默认脱敏；记录范围可配 |
| **P6 审计不可篡改** | 审计日志只追加（WORM），带链式哈希，任何改动可被发现 |

## 2. 日志分类总览

共 **12 类**，按用途分四组。

| 组 | 类别 | 代号 | 记录什么 | 主存储 | 热存 | 总留存 |
|---|---|---|---|---|---|---|
| **业务** | 业务操作日志 | `BIZ` | 解锁、权益变更、订单、存档 | MySQL | 永久 | 永久 |
| **业务** | 计费日志 | `BILLING` | 计量事件、账本流水、结算 | MySQL（append-only） | 永久 | 永久 |
| **审计** | 审计日志 | `AUDIT` | 后台敏感操作（WORM + 链式哈希） | MySQL | ≥3 年 | ≥3 年 |
| **审计** | 安全日志 | `SEC` | 登录、限流、拦截、SSRF 尝试、异常 | MySQL | ≥1 年 | ≥1 年 |
| **审计** | 内容审核日志 | `MOD` | 内容安全命中记录 | MySQL | ≥1 年 | ≥1 年 |
| **技术** | 访问日志 | `ACCESS` | 每次 HTTP 请求 | ClickHouse | 30 天 | 180 天 |
| **技术** | AI 调用日志 | `AI_CALL` | 每次模型调用的元数据 | ClickHouse | 90 天 | 180 天 |
| **技术** | AI 内容日志 | `AI_CONTENT` | Prompt / 输入 / 输出**内容** | 对象存储（加密） | 7 天 | 30 天（可关） |
| **技术** | 工具调用日志 | `TOOL_CALL` | 每次工具调用的入参与结果 | ClickHouse | 90 天 | 180 天 |
| **运维** | 应用日志 | `APP` | 服务运行日志、异常 | Loki | 7 天 | 30 天 |
| **运维** | 链路追踪 | `TRACE` | 端到端 span | Tempo | 7 天 | 14 天 |
| **运维** | 错误日志 | `ERROR` | 前后端异常聚合 | Sentry | 30 天 | 90 天 |

> **说明**：`AI_CONTENT` 是唯一记录"对话内容"的类别，**默认降级为关闭**（见 §7.3）。

## 3. 通用日志信封（字段规范）

所有类别共用同一层外壳，`payload` 字段按类别扩展。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `log_id` | string(uuid) | ✅ | 日志唯一 ID |
| `ts` | datetime(ms, +08:00) | ✅ | 事件时间（服务端时钟） |
| `category` | enum | ✅ | 12 类之一 |
| `level` | enum | ✅ | `DEBUG` / `INFO` / `WARN` / `ERROR` / `FATAL` |
| `trace_id` | string | ✅ | 端到端链路 ID（前端生成，全链路透传） |
| `span_id` | string | 🔶 | 当前 span |
| `parent_span_id` | string | 🔶 | 父 span |
| `request_id` | string | ✅ | 单次 HTTP 请求 ID |
| `idempotency_key` | string | 🔶 | 幂等键（有副作用的操作必填） |
| **`actor`** | object | ✅ | 见下表 |
| **`context`** | object | 🔶 | 见下表 |
| **`source`** | object | ✅ | 见下表 |
| **`outcome`** | object | ✅ | 见下表 |
| **`metrics`** | object | 🔶 | 见下表 |
| `payload` | object | 🔶 | 类别特有字段 |
| `schema_version` | string | ✅ | 信封版本，如 `1.0` |

### 3.1 `actor`（行为主体）

| 字段 | 说明 |
|---|---|
| `type` | `MEMBER` / `ADMIN` / `SYSTEM` / `ANONYMOUS` |
| `member_id` | 会员内部 ID |
| `member_code` | 会员编码（**脱敏保留前3后2**，如 `DY0**01`） |
| `douyin_id` | 抖音ID（**脱敏保留首字符**，如 `@张*`） |
| `admin_id` | 后台账号 ID |
| `admin_name` | 后台账号名 |
| `roles` | 角色数组 |

### 3.2 `context`（业务上下文）

| 字段 | 说明 |
|---|---|
| `work_id` / `work_version` / `content_version` | 作品与版本 |
| `session_id` / `turn_id` | 会话与回合 |
| `save_slot` | 存档槽位 |
| `tool_name` / `tool_version` | 工具 |
| `channel` | `PLATFORM` / `BYOK` |
| `credential_id` | BYOK 凭据 ID（**不记 Key 本身**） |
| `provider` / `model` | 上游与模型 |
| `prompt_version_id` | 使用的 Prompt 版本 |
| `stage` | 内容披露阶段 |

### 3.3 `source`（来源）

| 字段 | 说明 |
|---|---|
| `ip` | 客户端 IP（合规必需，保留） |
| `ip_region` | IP 归属地（省市，用于风控与告警） |
| `ua` | User-Agent（截断 256 字符） |
| `device_id` | 设备指纹（哈希后） |
| `app_version` / `platform` | 前端版本与平台 |
| `api_version` | 接口版本 |

### 3.4 `outcome`（结果）

| 字段 | 说明 |
|---|---|
| `status` | `SUCCESS` / `FAILED` / `REJECTED` / `PARTIAL` |
| `code` | 错误码（见规格书 §12.5） |
| `reason` | 人类可读原因（≤256 字符） |
| `retry_count` | 重试次数 |

### 3.5 `metrics`（度量）

| 字段 | 说明 |
|---|---|
| `latency_ms` | 总耗时 |
| `first_token_ms` | 首 token 耗时（流式） |
| `input_tokens` / `output_tokens` / `cached_tokens` / `reasoning_tokens` | Token 分列 |
| `cost_amount` | 平台成本 |
| `charge_amount` | 向用户计费额（BYOK 为 0） |
| `tool_calls` | 本回合工具调用次数 |

## 4. 各类日志明细

### 4.1 `ACCESS` 访问日志

| 项 | 内容 |
|---|---|
| 生成时机 | 每个 HTTP 请求（含静态资源可选采样） |
| 记录内容 | 方法、路径、查询参数（**白名单，不含密钥**）、状态码、响应字节数、耗时、`source`、限流判定结果 |
| 不记录 | 请求体、响应体、Cookie、Authorization 头 |
| 存储 | ClickHouse `log_access`，按天分区 |
| 热/总留存 | 30 天 / 180 天 |

**payload 字段**：`method` / `path` / `query_keys`（只记 key 名）/ `status` / `resp_bytes` / `rate_limited`(bool) / `upstream_ms`

### 4.2 `BIZ` 业务操作日志

| 动作 | 记录内容 |
|---|---|
| 会员登录 | 会员编码（脱敏）、设备、结果、失败原因 |
| 作品解锁 | 会员、作品、版本、解锁前/后已解锁数、解锁前/后剩余数、结果、失败原因、`source` |
| 权益手动变更 | 操作人、会员、作品、增/删、变更前后 |
| 存档保存 | 会员、作品、槽位、存档大小、schema 版本、校验结果 |
| 存档冲突 | 冲突的版本号、两端更新时间 |
| 会话创建/删除 | 会话、作品、通道 |
| 订单创建/支付/退款 | 订单号、金额、渠道、状态流转 |
| 作品上架/下架 | 操作人、作品、版本、灰度参数 |
| 内容版本发布 | 操作人、作品、内容版本、节点数变化 |
| 通道配置变更 | 会员、默认通道、凭据增删（**不记 Key**） |

| 存储 | MySQL `log_biz`，不分区，按归档策略迁移 |
|---|---|
| 留存 | 永久（业务事实） |

### 4.3 `AUDIT` 审计日志（WORM）

| 项 | 内容 |
|---|---|
| 覆盖范围 | 后台登录/登出、权限变更、账号增删、作品发布/回滚、内容与 Prompt 修改、工具定义修改、会员权益变更、系统配置变更、退款、数据导出、凭据清除 |
| 必需字段 | `actor`（完整，不脱敏）、`source`（完整 IP）、`target`（对象类型+ID）、`action`、`before`、`after`、`result`、`reason` |
| 不可篡改 | 每条记录 `prev_hash` + `hash`（链式哈希），任何修改可被检测 |
| 不可删除 | 无删除接口；归档时保持链完整 |
| 存储 | MySQL `log_audit`（独立账号仅授 INSERT，禁止 UPDATE/DELETE） |
| 留存 | ≥3 年 |

**链式哈希算法**：
```
hash_n = SHA256( prev_hash + canonical_json(payload) )
```
每日生成一张"日终结存证"，可对外证明日志未被篡改。

### 4.4 `SEC` 安全日志

| 事件 | 记录内容 |
|---|---|
| 登录成功/失败 | 会员编码（脱敏）、IP、地区、设备指纹、失败次数、是否触发二次验证 |
| 异常登录 | 跨省切换、新设备、短时间多 IP |
| 限流触发 | 限流维度、当前值、阈值、被拦截的请求 |
| 解锁失败 | 失败原因分类、频次（用于刷量检测） |
| BYOK 地址被拒 | `base_url` 主机（脱敏）、命中规则（内网/保留地址） |
| 内容安全拦截 | 命中类型、动作、来源（入站/出站/工具产出） |
| 凭据操作 | 新增/删除/测试凭据（**不记 Key**） |
| 风控熔断 | 触发原因、熔断范围、恢复时间 |

| 存储 | MySQL `log_sec`，不分区，按归档策略迁移 |
|---|---|
| 留存 | ≥1 年 |

### 4.5 `AI_CALL` AI 调用日志

**每次模型调用一条**，是成本归因与问题排查的主力。

| 字段 | 说明 |
|---|---|
| `channel` | `PLATFORM` / `BYOK` |
| `credential_id` | BYOK 凭据 ID（不记 Key） |
| `provider` / `model` / `model_tier` | 上游与档位 |
| `prompt_version_id` | Prompt 版本 |
| `prompt_mode` | `SERVER` / `PACKAGE` / `BOTH` |
| `messages_count` | 消息条数（**不记内容**） |
| `messages_tokens_est` | 输入估算 token |
| `tool_defs_count` | 声明的工具数 |
| `tools_enabled` | 启用的工具名列表 |
| `structured_output` | 是否使用 JSON Schema |
| `stream` | 是否流式 |
| `temperature` / `max_tokens` / `top_p` | 采样参数 |
| `outcome` | 成功/失败/降级层级 |
| `degrade_level` | 三级降级中的哪一级（`TOOL` / `JSON_SCHEMA` / `PROMPT_RETRY`） |
| `metrics` | latency / first_token / token 分列 / cost |
| `retry_count` / `fallback_from` | 重试与故障转移轨迹 |

| 存储 | ClickHouse `log_ai_call`，按天分区 |
|---|---|
| 留存 | 热 90 天 / 总 180 天 |

### 4.6 `AI_CONTENT` AI 内容日志（默认关闭）

> **这是唯一记录对话内容的类别。** 默认**关闭**；开启时有严格约束。

| 项 | 内容 |
|---|---|
| 记录什么 | System Prompt 全文（**秘密字段以占位符替代**）、用户输入、模型输出、工具入参与结果 |
| 何时开启 | ① 平台通道 + 全局配置开启 ② 内容安全调查 ③ 用户报障并授权 ④ 审核抽查（脱敏后） |
| **BYOK 通道** | **永不记录内容**（无论配置如何） |
| 秘密字段处理 | `truth` / 人物内在 / 结局文本 → 替换为 `[[REDACTED:secret_id]]`，只留引用 |
| 存储 | 对象存储，AES-256 加密，独立桶，访问需二次授权 + 全量审计 |
| 留存 | 默认 30 天，可配置为 7 天或 0（关闭） |
| 用户可见 | 用户可在"我的数据"中查看与自己相关的记录并申请删除 |
| 访问审计 | 每次读取都写 `AUDIT` |

### 4.7 `TOOL_CALL` 工具调用日志

**每次工具调用一条**。

| 字段 | 说明 |
|---|---|
| `tool_name` / `tool_version` / `tool_type` | `builtin` / `custom` |
| `params` | 入参（**脱敏后**；涉及敏感内容的字段以哈希或占位替代） |
| `precondition_results` | 前置条件逐条判定结果（登录/权益/会话状态/频次） |
| `impl_kind` | `builtin` / `compose` |
| `steps_executed` | 组合步骤执行轨迹（步骤名 + 耗时 + 结果） |
| `primitives_used` | 实际调用的原子能力列表 |
| `result_summary` | 结果摘要（不记渲染全文） |
| `ui_ops_count` | 产出的 UI 指令条数 |
| `state_changed` | 状态变更的路径列表（不记值） |
| `duration_ms` | 执行耗时 |
| `outcome` | 成功/前置拒绝/执行失败/超时/限流 |
| `reject_reason` | 被拒绝时的具体原因 |

| 存储 | ClickHouse `log_tool_call`，按天分区 |
|---|---|
| 留存 | 热 90 天 / 总 180 天 |

### 4.8 `BILLING` 计费日志

| 子类 | 记录内容 | 存储 |
|---|---|---|
| 计量事件 | `usage_event`：每次调用的 token 与成本，含三级归因 | MySQL 权威记录 + Outbox 投影 ClickHouse |
| 账本流水 | `ledger_entry`：append-only，含 `biz_type` / `direction` / `amount` / `balance_after` / `idempotency_key` | MySQL（**永久，禁止 UPDATE/DELETE**） |
| 冻结/释放 | 预授权、冻结、结算、释放四态记录 | MySQL |
| 幂等冲突 | 相同 `scene + ref_id + idempotency_key` 的重复请求记录 | MySQL |
| 对账记录 | 内部对账与上游对账的差异明细 | MySQL `reconcile_record` |
| 余额变动 | 每次变动前后余额快照 | MySQL |

**留存**：永久（财务事实，不可删）

### 4.9 `MOD` 内容审核日志

| 字段 | 说明 |
|---|---|
| `direction` | `INBOUND`（用户输入）/ `OUTBOUND`（模型输出）/ `TOOL`（工具产出） |
| `text_hash` | 文本哈希（**不存原文**，除非人工复审） |
| `text_preview` | 脱敏预览（≤50 字，可配） |
| `hit_type` | 涉政/涉黄/涉暴/违禁/自定义词表 |
| `hit_words` | 命中词（脱敏） |
| `action` | `BLOCK` / `REWRITE` / `NOTIFY` / `PASS` |
| `reviewer` | 人工复审人（若有） |
| `review_result` | 人工复审结论 |

| 存储 | MySQL `log_moderation` |
|---|---|
| 留存 | ≥1 年 |

### 4.10 `APP` 应用日志 / `TRACE` 链路 / `ERROR` 错误

| 类别 | 内容 | 存储 | 留存 |
|---|---|---|---|
| `APP` | 服务启动、配置加载、任务调度、连接池、GC、慢查询 | Loki | 7 热 / 30 总 |
| `TRACE` | 端到端 span：前端 → 网关 → 业务 → 模型 → 工具 → 存档 | Tempo | 7 热 / 14 总 |
| `ERROR` | 前后端异常堆栈、用户影响面、版本 | Sentry | 30 热 / 90 总 |

**采样策略**：`ACCESS` 与 `TRACE` 正常流量按 10% 采样；**错误与慢请求 100% 记录**。

## 5. 存储策略

### 5.1 冷热分层

```
         写入                         查询
          │                            │
          ▼                            ▼
┌──────────────────┐          ┌──────────────────┐
│  本地缓冲         │          │  热：ClickHouse   │  0–90 天，任意查询
│  (磁盘队列+批量)  │ ──────▶  │  / MySQL          │
└──────────────────┘          └────────┬─────────┘
                                       │ 归档任务（每日）
                                       ▼
                              ┌──────────────────┐
                              │  温：对象存储      │  90–180 天，按需拉起
                              │  Parquet + 分区    │
                              └────────┬─────────┘
                                       │ 归档任务（每月）
                                       ▼
                              ┌──────────────────┐
                              │  冷：归档存储      │  180 天–3 年，合规留存
                              │  低频访问 + 加密   │
                              └──────────────────┘
```

### 5.2 各存储选型与用途

| 存储 | 承载类别 | 理由 |
|---|---|---|
| **MySQL 8.4** | `BIZ` / `BILLING` / `AUDIT` / `SEC` / `MOD` | 业务事实源；强一致、事务、可用独立账号限制写权限 |
| **ClickHouse** | `ACCESS` / `AI_CALL` / `TOOL_CALL` | 高写入吞吐、列式聚合快（用量大盘） |
| **对象存储** | `AI_CONTENT` / 归档 Parquet | 便宜、可加密、可生命周期管理 |
| **Loki** | `APP` | 与 Prometheus/Grafana 同栈 |
| **Tempo / Jaeger** | `TRACE` | OpenTelemetry 标准 |
| **Sentry** | `ERROR` | 前后端统一异常聚合 |

### 5.3 分区与索引策略

> ⚠️ **MySQL 适配提示（详见归档选型 §30.2）**
> MySQL 要求「**每个唯一键（含主键）都必须包含分区表达式的列**」，因此
> `ledger_entry(id PK, idempotency_key UNIQUE)` + `PARTITION BY RANGE(created_at)` **建不出来**（ERROR 1503）。
> 落地调整：
> | 表 | MySQL 方案 |
> |---|---|
> | `ledger_entry` / `usage_event` | **不分区**；幂等键抽到独立的 `idempotency_guard(idempotency_key PK)` 表（不分区） |
> | `log_biz` / `log_audit` / `log_sec` | **不分区**，改用归档表 + 定时清理（见 §8.2） |
> | ClickHouse 三张表 | **不受影响**（用 ClickHouse 自己的分区语法） |

| 表 | 分区 | 关键索引 |
|---|---|---|
| `log_biz` | 不分区 | `(member_id, ts)`、`(work_id, ts)`、`(action, ts)` |
| `log_audit` | 不分区 | `(admin_id, ts)`、`(target_type, target_id)` |
| `log_sec` | 不分区 | `(member_id, ts)`、`(event_type, ts)`、`(ip, ts)` |
| `log_moderation` | 不分区 | `(hit_type, ts)`、`(direction, ts)` |
| `ledger_entry` | 不分区 | `(member_id, ts)`、`UNIQUE(idempotency_key)` |
| `usage_event` | 不分区 | `(work_id, ts)`、`(session_id)`、`(turn_id)` |
| `log_access` (CH) | 按天 | `(ts)`、`(path, ts)`、`(status, ts)` |
| `log_ai_call` (CH) | 按天 | `(member_id, ts)`、`(work_id, ts)`、`(model, ts)`、`(channel, ts)` |
| `log_tool_call` (CH) | 按天 | `(tool_name, ts)`、`(session_id, ts)`、`(outcome, ts)` |

**通用 TTL**：ClickHouse 表设 `TTL ts + INTERVAL 180 DAY`，自动淘汰，避免手工清理。

### 5.4 容量估算（参考）

| 类别 | 单条大小 | 日均条数（假设 DAU 1 万） | 日增 | 180 天累计 |
|---|---|---|---|---|
| `ACCESS` | ~0.6 KB | ~200 万 | ~1.2 GB | ~216 GB |
| `AI_CALL` | ~1.2 KB | ~20 万 | ~240 MB | ~43 GB |
| `TOOL_CALL` | ~1.5 KB | ~10 万 | ~150 MB | ~27 GB |
| `BIZ` | ~1 KB | ~2 万 | ~20 MB | ~3.6 GB |
| `AUDIT` | ~2 KB | ~100 | ~0.2 MB | ~36 MB |
| `SEC` | ~1 KB | ~5 万 | ~50 MB | ~9 GB |
| `AI_CONTENT` | ~8 KB | 默认关闭 | 0 | 0（开启时另计） |

> 结论：**只有 `ACCESS` 是大头** → 必须采样 + 短 TTL。其余类别体量可控。

## 6. 生成与采集链路

```
应用代码
  │
  ├─ ① 结构化埋点（@LogEvent 注解 / LogContext 上下文）
  │     - 从 ThreadLocal/MDC 取 trace_id / actor / context
  │     - 自动补 source（IP/UA/device）
  │
  ├─ ② 脱敏过滤器（在序列化之前）
  │     - 敏感字段正则替换
  │     - 秘密字段占位符替换
  │     - BYOK 内容直接丢弃
  │
  ├─ ③ 本地磁盘队列（有界，满则丢弃低优先级 + 告警）
  │
  ├─ ④ 批量投递器（每 200ms 或 500 条）
  │     ├─ MySQL（AUDIT/BILLING 与业务同事务；通知/分析投影写 Outbox）
  │     ├─ ClickHouse
  │     ├─ 对象存储（内容日志）
  │     └─ OTLP → Loki / Tempo
  │
  └─ ⑤ 采集端
        - Fluent Bit / Vector（可选，用于文件日志）
        - OpenTelemetry Collector（trace/metrics/logs 统一）
```

**关键约定**：

| 约定 | 说明 |
|---|---|
| 日志失败不回滚业务 | 除 `AUDIT` 与 `BILLING` 外，日志写入失败不阻断主流程 |
| `AUDIT` 强一致 | 审计日志必须与业务操作**同事务**写入，失败即回滚业务 |
| `BILLING` 强一致 | 账本流水与扣费同事务，失败即回滚 |
| 就地异步 | `ACCESS` / `AI_CALL` / `TOOL_CALL` 异步投递，不阻塞响应 |
| 上下文透传 | `trace_id` 由前端生成，通过请求头透传全链路（含转发到上游时的自定义头） |
| 有界队列 | 队列满时丢弃 `DEBUG`/`INFO`，保留 `WARN`/`ERROR`，并告警 |

## 7. 脱敏与隐私

### 7.1 强制脱敏字段

| 字段 | 脱敏方式 | 适用范围 |
|---|---|---|
| API Key（BYOK） | **完全不记录** | 全部日志 |
| API Key（平台上游） | 完全不记录 | 全部日志 |
| 会员编码 | 保留前 3 后 2（`DY0**01`） | `ACCESS` / `AI_CALL` / `TOOL_CALL` / `SEC` |
| 会员编码 | **明文**（审计必需） | `AUDIT` / `BIZ` / `BILLING` |
| 抖音ID | 保留首字符（`@张*`） | 非审计类 |
| 手机号 | 中间四位掩码 | 全部 |
| 后台密码 | 完全不记录 | 全部 |
| 对话内容 | 默认不记录 | 全部（`AI_CONTENT` 除外） |
| Prompt 秘密字段 | 占位符 `[[REDACTED:secret_id]]` | `AI_CONTENT` |
| 存档内容 | 不记录全文，只记大小与哈希 | 全部 |
| 凭据 Header | 键名保留、值掩码 | 全部 |

### 7.2 统一脱敏组件

- **入库前**在序列化阶段统一过滤（不是各业务自己写）
- 规则集中配置：`sensitive_fields.yaml`，含字段名匹配 + 正则兜底
- 正则兜底：`sk-[A-Za-z0-9]{8,}` / `Bearer\s+\S+` / `1[3-9]\d{9}` / 身份证号
- 单元测试强制覆盖：新增日志字段必须通过脱敏测试，否则 CI 失败

### 7.3 内容记录的三道闸

```
第一道：全局配置        AI_CONTENT_ENABLED = false（默认）
第二道：通道判定        channel == BYOK → 永远丢弃内容（不受配置影响）
第三道：字段判定        命中 secretRef 的字段 → 占位符替换
```

### 7.4 用户权利

| 权利 | 实现 |
|---|---|
| 知情 | 「我的数据」页列出平台记录了哪些类别的日志 |
| 查阅 | 可查看与自己相关的 `BIZ` / `BILLING` / `AI_CALL` 元数据 |
| 删除 | 可申请删除 `AI_CONTENT` 中与自己相关的内容；`BIZ`/`BILLING`/`AUDIT` 依法留存不可删（明确告知） |
| 更正 | 会员信息更正走运营流程 |
| 导出 | 可导出自己的消费与解锁记录 |

## 8. 留存、归档与销毁

### 8.1 留存矩阵

| 类别 | 热存 | 总留存 | 到期动作 |
|---|---|---|---|
| `BIZ` | 永久 | 永久 | 不销毁 |
| `BILLING` | 永久 | 永久 | 不销毁（财务） |
| `AUDIT` | ≥3 年 | ≥3 年 | 归档后按制度审批销毁 |
| `SEC` | ≥1 年 | ≥1 年 | 归档后销毁 |
| `MOD` | ≥1 年 | ≥1 年 | 归档后销毁 |
| `ACCESS` | 30 天 | 180 天 | 自动 TTL 删除 |
| `AI_CALL` | 90 天 | 180 天 | 自动 TTL 删除 |
| `TOOL_CALL` | 90 天 | 180 天 | 自动 TTL 删除 |
| `AI_CONTENT` | 7 天 | 30 天（可配 7/0） | 自动删除，不可恢复 |
| `APP` | 7 天 | 30 天 | 自动删除 |
| `TRACE` | 7 天 | 14 天 | 自动删除 |
| `ERROR` | 30 天 | 90 天 | 自动删除 |

> **合规底线**：`ACCESS` / `SEC` / `BIZ` 的留存策略需满足《网络安全法》≥6 个月（180 天）要求，本设计已满足。

### 8.2 归档流程

| 频率 | 动作 |
|---|---|
| 每日 03:00 | 把超过热存期的 ClickHouse 数据导出为 Parquet → 对象存储（按 `category/dt=` 分区） |
| 每月 01 日 | 把超过温存期的 Parquet 转归档存储（低频访问层） |
| 每季度 | 生成归档清单报告（类别、时间范围、条数、校验哈希） |
| 到期 | 按留存矩阵自动删除；`AUDIT` 需人工审批 |

### 8.3 销毁要求

| 项 | 要求 |
|---|---|
| 删除方式 | 存储层真删（非逻辑删），对象存储需清理多版本 |
| 销毁记录 | 写 `AUDIT`：类别、时间范围、条数、执行人/任务、销毁证明哈希 |
| 不可恢复 | `AI_CONTENT` 与 `ACCESS` 到期后不可恢复 |
| 备份一致性 | 备份中的过期数据同步清理（备份保留策略不得超过数据留存策略） |

### 9.1 后台查询能力

| 页面 | 支持查询 | 说明 |

| B-05 工具管理 | `TOOL_CALL` | 工具调用日志与误调用分析 |
| B-09 通道与策略 | `SEC` | 限流、SSRF、异常记录 |

### 9.2 检索能力要求

| 能力 | 说明 |
|---|---|
| 按 `trace_id` 聚合 | 一次请求跨 6 类日志的所有记录，按时间排序展示 |
| 按 `session_id` 聚合 | 一次游戏会话的全部 AI 与工具调用 |
| 按 `member_id` 聚合 | 某会员的全部行为轨迹 |
| 组合筛选 | 时间 + 类别 + 状态 + 作品 + 模型 + 工具 |

| 数据权限 | 按后台角色限制可见范围（FINANCE 不见内容日志，OPERATOR 不见计费明细） |

### 9.3 排查场景速查

| 用户报障 | 查什么 |
|---|---|
| "解锁没成功" | `BIZ`（解锁动作）+ `SEC`（是否限流/异常） |
| "扣费不对" | `BILLING`（流水）+ `AI_CALL`（token 明细）+ `usage_event` |
| "AI 回复很慢" | `AI_CALL`（latency/first_token）+ `TRACE`（哪一段慢） |
| "工具没触发" | `TOOL_CALL`（是否有调用、前置条件是否拒绝） |
| "内容被拦截" | `MOD`（命中类型与动作） |
| "存档丢了/被改" | `BIZ`（存档保存记录）+ 存档校验结果 |
| "余额莫名减少" | `ledger_entry`（全流水）+ 幂等冲突记录 |
| "别人用了我的会员" | `SEC`（登录记录、设备、IP 地区）+ `BIZ`（异地解锁） |
