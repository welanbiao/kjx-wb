## 2. 必答项（未答复部分）

### ✅ B-1 已闭环：`已订阅月数` 的数据来源

| 项 | 内容 |
|---|---|
| **问题** | 后台的 `subscribed_months`（用于绑定比对）是**运营直接从抖音后台抄录入库**，还是由 `subscribed_days` 换算？ |
| **为什么关键** | 435 天 ÷ 30 = **14.5**：`floor` 得 14、`round`/`ceil` 得 15。用户大概率填 **15**。若后台存 14，则**该用户永远比对失败** —— 这是**大面积误判** |
| **结论** | ✅ **运营直接从抖音后台抄录"已订阅 X 个月"**。`subscribed_months` 与 `subscribed_days` 各自独立录入，互不换算；比对逻辑为精确相等 |
| **阻塞** | M1 ｜ **状态**：✅ 已确认 |

### ✅ B-2 已闭环：会员编码怎么发放到用户手上

| 项 | 内容 |
|---|---|
| **问题** | 三要素依赖「会员编码」，但**用户怎么知道自己的编码**？由谁发放？ |
| **为什么关键** | 用户拿不到编码就无法绑定；转化率会明显下降 |
| **结论** | ✅ **给每个主播一个后台账号**，主播在自己的页面里用**会员编码生成器**生成与主播账号绑定的编码，自行发给会员。详见 `09-M1数据库设计与项目骨架.md` §6 |
| **阻塞** | M1 ｜ **状态**：✅ 已确认 |

### ✅ B-3 已闭环：平台通道定价

每千 token 收多少？按模型档位分别定价？不定则计费模块无法封版。
**结论**：✅ **成本 × 4 倍加价**（默认值，上线后调）。标准档 0.08/4/16 元每百万 token；高级档 0.60/18/54 元。详见 `10-成本与定价测算.md` |

### ✅ B-4 已闭环：单用户日预算 / 单会话预算上限

文游单局约 72 万 token（规格 §13.2.4）。需设上限保护毛利，超限时提示改用 BYOK。
**结论**：✅ 日预算 **300 万 token**（≈ 2 局）；单会话 **150 万 token**。超限时提示改用 BYOK |

### ✅ B-5 已闭环：买断制还是租用制

会员到期后已解锁作品是否仍可用？规格已按**买断制**设计（符合 docx 规则 5 原文）。
**结论**：✅ **买断制**。已解锁作品永久可用，不再校验会员状态。**阻塞 M1** ｜ ✅

### ✅ B-6 已闭环：平台是单主播还是多主播

决定 `member` 表唯一键：单主播 → `UNIQUE(douyin_id)`；多主播 → `UNIQUE(dept_id, douyin_id)`。
**结论**：✅ **多主播**。`kjx_host` 作为 `sys_dept` 的 1:1 扩展表；`UNIQUE(dept_id, douyin_id)`；**绑定表单不新增字段** —— 主播通过「专属链接参数」或「会员编码前缀」带入，无参数时才显示下拉兜底 |

### ✅ B-7 已闭环：绑定是否默认需要人工审核

你已确认不加设备风控信号，那么人工审核是唯一的兜底。
**结论**：✅ **默认全人工审核**（前期量小，可这么做）。配置 `auto-approve: false`；后续量上来再切自动 |

### ✅ B-8 已闭环：绑定失败锁定阈值

**结论**：✅ 失败 **3 次锁 30 分钟** |

### ✅ B-9 已闭环：邮箱注册是否开放

**结论**：✅ **不开放邮箱注册，仅手机号** |

### ✅ B-10 已闭环：是否保留"演示模式"

未绑定/未付费用户能否试玩（服务端预置剧本，不消耗额度、不调真实模型）？

### ✅ B-11 已闭环：「已订阅天数」是连续还是累计

用户充 3 个月 → 停 2 个月 → 再充 12 个月，已订阅天数是 **15 个月**（累计）还是只算这次？

峰值需要 **50~80 个并发长连接**同时挂在生成中。若提供商限制"并发 20"，直接撞墙。

## 2.5 接口契约评审项（已闭环）

### ✅ R8 已闭环：手机号加密方案

| 方案 | 合规 | 复杂度 | 说明 |
|---|---|---|---|
| **A. AES 加密 + HMAC 索引**（推荐） | ✅ 好 | 中（需密钥管理） | 手机号是最敏感的个人信息之一；**将来改造要迁移全量数据 + 重建索引**，成本远高于一开始做对。工作量约半天 |
| B. 明文存储 | 🔶 欠佳 | 低 | 国内不少平台如此，但隐私政策需说明，未来改造麻烦 |

**关联风险**：若用普通 SHA256 做索引，11 位手机号可被彩虹表秒破 → **必须用 HMAC（带密钥）**。
**结论**：✅ **方案 A —— AES-256-GCM 加密 + HMAC-SHA256 索引**（密钥版本化、不进 Git）。详见 `11` §4 R8 ｜ ✅

> 其余 11 条对接风险（R1~R12）已在 `11-M1接口契约与业务联动.md` §4 列明并给出对策，其中 R1/R2 为 P0，已在文档中给出技术方案，无需你决策。

## 5. 风险提示

### ⚠️ R-1 三要素之下仍有残余风险

三要素里只有**会员编码**有保护作用。一旦泄露（截图转发、群聊），就退化成两要素。
**建议**：明确"编码泄露"应急流程（客服核对手机号后换发新编码）；后台提供批量重置能力。

### ⚠️ R-2 `已订阅月数` 比对的大面积误判风险（见 B-1）

若月数由天数换算，435 天 = 14.5，用户填 15、系统存 14 → **成片绑定失败**，且因提示语统一，用户不知道为什么。

### ⚠️ R-3 文游 token 成本可能超预期

按规格 §13.2.4 推算，日 token 约 **1.6 亿**；**廉价模型档月成本约 6 千元，旗舰档 3~6 万元（差 10 倍）**。
**建议**：落实 D-22 的模型分级；界面实时显示消耗；上线第一周就盯成本分布。

### ⚠️ R-4 运营对会员数据的手工依赖度高

会员数据靠人工抄录（docx 原始设定）。人工抄录必有错漏，而绑定后用户端**自动同步**，抄错会立刻被用户发现。
**建议**：关键字段修改二次确认 + 填理由（已定 D-8）；提供批量导入；定期与抖音后台数据对账。

### ⚠️ R-5 上游 API 提供商的单点依赖

按 D-30，平台不对接多个上游、自行找一家 API 提供商。**若该提供商限流、涨价、或服务中断，整个平台不可用。**
**建议**：至少预留**两家**可切换的提供商（Higress 的多渠道路由本就是为此设计），切换只改配置。

### ⚠️ R-6【本轮新增】合规范围收窄带来的风险（知晓即可）

按 D-29~D-32，本平台**不做生成式 AI 备案、不做实名与防沉迷、以"AI 互动小说"表述上架**。如实记录：
- **建议至少保留内容安全审核**（入站/出站）—— 云厂商 API 成本极低，却能拦住明显违规内容，避免被投诉下架。**这是性价比最高的一道保险。**
- 其余合规事项按你的决定延后，不做进一步展开。
