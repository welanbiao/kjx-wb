## 0. 设计约定

### 0.1 命名与规范

| 项 | 约定 |
|---|---|
| **表前缀** | 自研表统一 `kjx_`；RuoYi-Vue-Plus 自带表保持 `sys_` / `infra_` 前缀 |
| **字段命名** | `snake_case`，不使用保留字 |
| **主键** | `id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT` |
| **字符集** | **`utf8mb4`** + **`utf8mb4_0900_ai_ci`**（⚠️ **绝不能用 utf8mb3**，emoji 存不了） |
| **存储引擎** | **InnoDB**（事务 + 行锁），禁用 MyISAM |
| **时间字段** | `DATETIME(3)`，统一 `Asia/Shanghai`，默认值 `CURRENT_TIMESTAMP(3)` |
| **布尔字段** | `BIT(1)`，默认 `b'0'` |
| **IP 字段** | `VARBINARY(16)`（同时支持 IPv4/IPv6），应用层用 `INET6_ATON/INET6_NTOA` |
| **金额字段** | `DECIMAL(18,6)`（token 计费精度需要） |
| **枚举字段** | `VARCHAR(16~32)` + 应用层枚举（**不用 MySQL ENUM**，改值要 DDL） |
| **JSON 字段** | `JSON` 类型；**需要按值查询的字段一律抽成独立列**（见归档选型 §30.2 第 5 条） |
| **审计字段** | `creator` / `create_time` / `updater` / `update_time` / `deleted`（RuoYi-Vue-Plus 风格） |
| **逻辑删除** | `deleted BIT(1) DEFAULT b'0'`；**账本/审计/解锁记录不逻辑删除** |
| **租户字段** | `tenant_id BIGINT DEFAULT 0`（RuoYi-Vue-Plus 兼容，本项目固定 0，不做多租户） |

### 0.2 三条铁律

1. **分区限制**：MySQL 要求「每个唯一键（含主键）都必须包含分区表达式的列」→ **M1/M2 的表全部不分区**；幂等键独立成 `kjx_idempotency_guard` 表（不分区）
2. **禁止"先查后改"**：并发敏感操作（解锁、扣费）必须用**单条 CAS 语句**
3. **DDL 非事务性**：一个 Flyway 迁移文件只做一件事

### 2.2.1 V2.1 — 主播表（多主播模式，已确认）

> **已确认：平台服务多个主播**，且**主播直接复用 RuoYi 的「部门」机制承载**（`sys_dept`）。
>
> **设计决策**：不自己造主播隔离机制，**用框架原生的部门 + 数据权限**——
> 每个主播 = 一个部门，主播账号 = `sys_user`（`dept_id` 指向该部门），
> 数据隔离由 RuoYi 的 `@DataPermission` 自动拼 SQL 完成，**无需自研 MyBatis 拦截器**。

```sql
-- 主播扩展表：主键即 sys_dept.id（1:1 扩展，不新建独立 ID 体系）
-- 部门管理页面负责增删改；本表只存业务扩展字段
CREATE TABLE `kjx_host` (
  `dept_id`     BIGINT UNSIGNED NOT NULL COMMENT '★主播ID（= sys_dept.id，与部门 1:1）',
  `host_code`   VARCHAR(32)     NOT NULL COMMENT '主播短码（用于绑定链接与会员编码前缀）',
  `dy_account`  VARCHAR(128)    DEFAULT NULL COMMENT '主播抖音号',
  `logo_url`    VARCHAR(512)    DEFAULT NULL COMMENT '头像/Logo',
  `contact`     VARCHAR(255)    DEFAULT NULL COMMENT '客服联系方式',
  `remark`      VARCHAR(255)    DEFAULT NULL COMMENT '备注',
  `creator`     VARCHAR(64)     DEFAULT '' COMMENT '创建者',
  `create_time` DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  `updater`     VARCHAR(64)     DEFAULT '' COMMENT '更新者',
  `update_time` DATETIME(3)     NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  `deleted`     BIT(1)          NOT NULL DEFAULT b'0' COMMENT '是否删除',
  PRIMARY KEY (`dept_id`),
  UNIQUE KEY `uk_kjx_host_code` (`host_code`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='主播扩展（对应 sys_dept 的一个部门）';
```

**部门侧的初始化约定**：

| 项 | 约定 |
|---|---|
| 部门树 | `叩君芯（顶级）` → `运营部` + 各主播部门（如 `主播-叩君芯`、`主播-XX`） |
| 数据权限 | 主播角色 → **「仅本部门数据」**；运营 → 「全部数据」或自定义 |
| 账户归属 | 主播账号 `sys_user.dept_id` = 其主播部门；同部门可挂多个账号（未来加人不用改结构） |
| 顶级部门 | `叩君芯` 本身不挂主播扩展记录，仅作树根 |

**主播维度的取值方式（三选一，优先级从高到低）**：

| 优先级 | 方式 | 说明 | 用户负担 |
|---|---|---|---|
| **1** | **专属绑定链接带入** | 主播在抖音群里发 `https://xxx.com/bind?h=kjx`，登录后自动带入主播，**表单不显示主播字段** | **零** ← 推荐主用 |
| 2 | 会员编码前缀推断 | 会员编码格式约定为 `{主播短码}-{8位随机}`（如 `KJX-A3F9K2B7`），系统校验一致性 | 零 |
| 3 | 表单下拉选择 | 前两者都没有时，表单显示"选择主播"下拉兜底 | 需选一次 |

> **设计要点**：三要素（抖音号 + 已订阅月数 + 会员编码）**保持不变**，主播是**隐含的第四维度**，通常由链接或编码带入，不额外增加用户输入。

> **⚠️ 关键设计说明（B-1）**：`subscribed_months` 与 `subscribed_days` **各自独立录入，互不换算**。
> 435 天 ÷ 30 = 14.5，若由天数换算月数会得 14 或 15，与用户填写值不一致 → **大面积绑定失败**。

### 3.2 解锁作品（CAS 原子更新）★

```sql
-- 第 ① 步：CAS 更新额度（★必须单条语句，禁止"先 SELECT 判断再 UPDATE"）
-- MySQL REPEATABLE READ 下，UPDATE 是当前读并加行锁，此写法并发安全
UPDATE kjx_member
   SET unlocked_count = unlocked_count + 1,
       remain_count   = remain_count - 1,
       version        = version + 1,
       update_time    = CURRENT_TIMESTAMP(3)
 WHERE id = #{memberId}
   AND deleted = b'0'
   AND status = 'VALID'
   AND unlocked_count < available_count;
-- 影响行数 = 0 → 额度用完或会员无效，直接失败返回

-- 第 ② 步：插入权益（唯一索引兜底并发；重复插入会抛 DuplicateKey → 回滚整个事务）
INSERT INTO kjx_member_entitlement
  (dept_id, member_id, account_id, work_id, work_version, source, unlock_record_id, unlocked_at)
VALUES
  (#{deptId}, #{memberId}, #{accountId}, #{workId}, #{workVersion}, 'user', #{recordId}, CURRENT_TIMESTAMP(3));

-- 第 ③ 步：写解锁记录（快照）
INSERT INTO kjx_unlock_record
  (dept_id, member_id, member_code, douyin_id, account_id, work_id, work_name, work_version,
   before_unlocked_count, after_unlocked_count, before_remain_count, after_remain_count,
   result, source, request_fingerprint, idempotency_key)
VALUES
  (#{deptId}, #{memberId}, #{memberCode}, #{douyinId}, #{accountId}, #{workId}, #{workName}, #{workVersion},
   #{beforeUnlocked}, #{afterUnlocked}, #{beforeRemain}, #{afterRemain},
   'SUCCESS', 'user', #{fingerprint}, #{idempotencyKey});
```

### 3.4 会员派生字段重算（单一 recalc，M-6）

```sql
-- 由 recalc 服务统一调用，禁止在别处重复实现公式
UPDATE kjx_member
   SET start_at        = DATE_SUB(expire_at, INTERVAL subscribed_days DAY),
       available_count = FLOOR(subscribed_days / 30),   -- ★M-1：floor，非 ceil
       unlocked_count  = (SELECT COUNT(*) FROM kjx_member_entitlement WHERE member_id = kjx_member.id),
       remain_count    = GREATEST(FLOOR(subscribed_days / 30) -
                          (SELECT COUNT(*) FROM kjx_member_entitlement WHERE member_id = kjx_member.id), 0),
       status          = CASE
                           WHEN NOW(3) < DATE_SUB(expire_at, INTERVAL subscribed_days DAY) THEN 'NOT_STARTED'
                           WHEN NOW(3) > expire_at THEN 'EXPIRED'
                           ELSE 'VALID'
                         END,
       version         = version + 1,
       update_time     = CURRENT_TIMESTAMP(3)
 WHERE id = #{memberId};
```

### 3.5 解锁失败记录的窗口合并（M-5，防刷爆）

```sql
-- 同 member + work + 原因，60 秒内只落一条（计数累加）
INSERT INTO kjx_unlock_record

  (#{memberId}, #{memberCode}, #{workId}, 'FAILED', #{reason}, 'user', CURRENT_TIMESTAMP(3))
```

## 6. 会员编码生成规则（D-48 / D-51）

### 6.1 发放链路（已确认）

```
① 后台给每个主播开一个账号，并关联到 kjx_host.admin_user_id
        │
        ▼
② 主播登录后台 → 进入「会员编码生成器」页面
   录入该会员信息：抖音号 + 已订阅月数 + 到期时间
        │
        ▼
③ 系统自动生成会员编码（格式见 §6.2），写入 kjx_member
        │
        ▼
④ 主播把编码发给会员（抖音群 / 私信）
        │
        ▼
⑤ 会员在平台注册 → 个人主页填三要素（抖音号 + 月数 + 编码）
        │
        ▼
⑥ 系统按三要素精确匹配 → 绑定成功
```

> **为什么"录入即生成"而不是"预生成编码池"**：预生成会产生"码已发但无会员信息"的中间态，
> 会员绑定时无法确定其额度，逻辑会复杂化。录入即生成让**编码与会员记录一一对应**，最简单。
> 若主播确实需要批量印码，作为钩子 **H-14** 后续扩展（加 `kjx_member_code` 编码池表）。

### 6.2 编码格式

| 项 | 规格 |
|---|---|
| 格式 | `{主播短码}-{8位随机}` |
| 示例 | `KJX-A3F9K2B7` |
| 唯一性 | `UNIQUE KEY uk_kjx_member_code`，**全局唯一** |
| 大小写 | **统一大写**；用户输入时自动转大写、去空格、去连字符后比对 |
| 前缀作用 | ① 隐含主播归属（三级取值第 2 级）② 便于人工识别与客服核对 |
| 生成者 | **系统生成**，不接受人工输入（避免重复与格式不一） |
| 随机策略 | 8 位大写字母数字，排除 O/0、I/1、L；唯一键冲突最多重试 5 次 |

> **安全取舍已定稿（D-52）**：使用随机码防枚举；人工核对依赖主播前缀与完整三要素。

### 6.3 主播账号的权限边界（D-51）

| 能做什么 | 不能做什么 |
|---|---|
| 生成编码 + 录入自己名下的会员 | 看其他主播的会员与编码 |
| 查看自己名下会员的绑定状态 | 修改作品、改价格、改系统配置 |
| 查看自己名下会员的解锁情况 | 退款、改账本 |
| 导出自己名下的会员列表 | 删除会员（只能运营/超管） |

**实现方式**：主播账号 = RuoYi `sys_user` 的一条记录（角色 `HOST`），
主播 = **部门**，数据隔离由 RuoYi `@DataPermission`（「仅本部门数据」）自动完成，**不自研拦截器**。

## 7. 额度模型（D-49 / D-50，已确认）

### 7.1 模型定义

```
天数额度池 = FLOOR(累计已订阅天数 / 30)（历史天数累计，不随时间减少、不会过期）
已解锁数   = 已解锁作品数
剩余额度   = 天数额度池 − 已解锁数

解锁一个作品 = 占用 1 个额度槽；不直接修改 subscribed_days
```

**对应到字段**：
```sql
available_count = FLOOR(subscribed_days / 30)   -- 累计天数换算出的额度池总量
unlocked_count  = 已解锁作品数
remain_count    = available_count - unlocked_count
```

### 7.2 解锁条件（全部满足）

| # | 条件 | 说明 |
|---|---|---|
| ① | 已登录 + 已绑定会员 | 登录态 + `kjx_member_binding.status = MATCHED` |
| ② | **会员状态 = VALID** | 当前时间在开通时间与到期时间之间（**原 docx 规则 7：过期不能再解锁**） |
| ③ | 剩余额度 > 0 | `unlocked_count < available_count` |
| ④ | 作品已上架 | `kjx_work.status IN ('PUBLISHED','GRAY')` |

> **注意条件 ② 的含义**：额度池虽然不会过期，但**会员过期后不能动用剩余额度**。
> 用户想继续解锁，必须**再去抖音续费** → 运营/主播分别更新累计天数、展示比对月数与到期时间
> → 会员恢复 VALID → 才能解锁。`subscribed_months` 只用于绑定比对，不参与额度计算。
> 这与用户描述的"想重新积累月数就只能再去抖音充一个会员"完全一致。

### 7.3 累计制的三个推论（需团队知晓）

| 推论 | 说明 | 影响 |
|---|---|---|
| **额度只增不减**（除解锁消耗） | 用户充 15 个月、解锁 3 个、过期、再充 12 个月 → 额度池 27 个月，剩余 24 | 长期用户会攒下大量额度 |
| **额度不随时间衰减** | 停会员期间额度池不变（不清零也不增长） | 与"租用制"完全不同 |
| **作品数 < 额度时额度闲置** | 平台只有 3 个作品但用户有 24 个月额度 | 对应 07 清单 **B-9**（你已决定暂不处理）与钩子 **H-9** |

### 7.4 与"买断制"的关系

- **买断制（D-50）** 管的是：**已解锁的作品**永久可用，不再校验会员状态
- **额度池（D-49）** 管的是：**还能解锁几个新作品**
- 两者互不影响：过期后**已解锁的能继续玩**，但**不能解锁新的**

| 2 | **B-6：单主播还是多主播** | ✅ **多主播** | ① `kjx_host` 作为 `sys_dept` 的 1:1 扩展表；② `UNIQUE(dept_id, douyin_id)`；③ **绑定表单不新增字段**——主播通过「专属链接参数」或「会员编码前缀」带入，无参数时才显示下拉兜底（见 §2.2.1） |
| 3 | **B-7：绑定是否默认人工审核** | ✅ **默认全人工审核**（前期量小，可这么做） | 配置 `auto-approve: false` 保持；绑定提交后状态为 `PENDING_REVIEW`，运营在后台逐条审核。后续量上来再切自动 |
