## 1. 接口通用约定

### 1.1 路径与分组

| 分组 | 前缀 | 使用者 | 鉴权 |
|---|---|---|---|
| **前台-账号** | `/app/auth/**` | 注册/登录（免登录） | 否 |
| **前台-业务** | `/app/**` | 会员（C 端） | Sa-Token（`loginType = app`） |
| **后台-主播** | `/admin-api/kjx/self/**` | 主播（HOST 角色） | Sa-Token（`loginType = admin`）+ 角色校验 |
| **后台-运营** | `/admin-api/kjx/**` | 运营/上架/财务/超管 | Sa-Token（`loginType = admin`）+ 权限点 |
| **AI 代理** | `/v1/**` | 运行时（OpenAI 兼容） | 虚拟 Key / 会话令牌（M3） |

### 1.2 统一响应体

```json
{ "code": 0, "data": {}, "msg": "" }
```

| code | 含义 |
|---|---|
| `0` | 成功 |
| `401` | 未登录 / 令牌失效 |
| `403` | 无权限 |
| `400` | 参数错误 |
| `409` | 冲突（唯一键、状态冲突） |
| `429` | 限流 |
| `500` | 服务端错误 |

**业务错误码放在 `code` 的 4 位以上区间**（如 `1001` 会员不存在），与 HTTP 状态码分离，便于前端精细处理。

### 1.3 通用请求头

| 头 | 说明 |
|---|---|
| `Authorization: Bearer {token}` | Sa-Token 令牌 |
| `X-Idempotency-Key` | **幂等键**（所有有副作用的写接口必填，如解锁） |
| `X-Device-Id` | 设备指纹（登录、绑定、解锁时上报） |
| `X-Client-Version` | 前端版本 |

### 1.4 错误码表（M1）

| code | HTTP | 文案（前端直接用） |
|---|---|---|
| `1001` | 400 | 信息不匹配，请核对后重试 |
| `1002` | 409 | 该会员信息已被使用，如有疑问请联系客服 |
| `1003` | 409 | 每个账号只能绑定一个会员 |
| `1004` | 429 | 尝试次数过多，请 30 分钟后再试 |
| `1005` | 403 | 会员尚未生效，生效时间 {time} |
| `1006` | 403 | 会员已过期，请续费 |
| `1007` | 403 | 可解锁数量已用完 |
| `1008` | 403 | 作品已下架 |
| `1009` | 403 | 请先完成会员绑定 |
| `1010` | 200 | 已解锁，正在进入（幂等成功） |
| `1011` | 400 | 验证码错误或已过期 |
| `1012` | 429 | 发送过于频繁，请稍后再试 |
| `1013` | 403 | 账号已锁定，请联系客服 |
| `1014` | 403 | 账号注销中，暂时无法操作 |

## 2. 接口契约

### 2.1 账号组

#### 2.1.1 发送验证码

```
POST /app/auth/send-code
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `phone` | string | ✅ | 手机号 |
| `scene` | enum | ✅ | `register` / `login` / `reset_pwd` / `cancel` |
| `captchaId` | string | ✅ | tianai-captcha 的挑战 ID |
| `captchaData` | object | ✅ | 滑块/点选结果 |

**响应**：`{ "code": 0, "data": { "expireIn": 300 } }`

**服务端动作**：
1. 校验 tianai-captcha 挑战（防机器刷）
2. 频控：同号 60 秒 1 条、每日上限 10 条；同 IP 每小时上限
3. 生成 6 位码 → **Redis 存哈希**（key: `kjx:sms:code:{scene}:{phoneHash}`，TTL 5 分钟）
4. 经 SMS4J 发送
5. 写 `kjx_verify_code` 审计记录

---

#### 2.1.2 注册

```
POST /app/auth/register
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `phone` | string | ✅ | 手机号（**唯一注册方式，不开放邮箱**，见 D-57） |
| `password` | string | ✅ | 8~32 位，含字母 + 数字 |
| `code` | string | ✅ | 短信验证码 |
| `agreeTerms` | bool | ✅ | 必须为 true |

**响应**：`{ "code": 0, "data": { "token": "...", "accountId": 1 } }`

**服务端动作**：
1. 校验验证码（比对 Redis 哈希，成功后立即删除）
2. 密码强度校验 + bcrypt/Argon2 哈希
3. 手机号 AES 加密存 `phone`，HMAC-SHA256 存 `phone_hash`（用于唯一索引）
4. 插入 `kjx_account`（`status=1`，`bind_status=0`）
5. 签发 Sa-Token（`loginType = app`）
6. 写 `BIZ` 日志（注册事件）

> ⚠️ **手机号加密的连带影响**：`phone_hash` 是对手机号做 **HMAC（带固定密钥）**，不是普通 SHA256——
> 否则 11 位手机号的 SHA256 可被彩虹表反查。密钥走环境变量，**轮换需重建索引**。

---

#### 2.1.3 登录

```
POST /app/auth/login          # 密码登录
POST /app/auth/login-by-code  # 验证码登录（免密）
```

**响应**：
```json
{
  "code": 0,
  "data": {
    "token": "...",
    "expireIn": 2592000,
    "account": { "id": 1, "nickname": "xxx", "avatar": null },
    "bindStatus": 0,
    "member": null
  }
}
```

**服务端动作**：
1. 查 `account`（按 `phone_hash`）
2. 校验密码 / 验证码
3. 失败计数（Redis `kjx:login:fail:{accountId}`），连续 5 次锁 15 分钟
4. 签发 Sa-Token，记录 `last_login_at` / `last_login_ip`
5. **写 `kjx_account_device`（upsert，按 account_id + device_id）**
6. 写 `SEC` 日志（含 IP、地区、设备）

### 2.2 会员绑定组 ★（核心）

#### 2.2.1 查询绑定状态

```
GET /app/member/binding
```

**响应**：
```json
{
  "code": 0,
  "data": {
    "status": "NONE",
    "submitAt": null,
    "rejectReason": null,
    "member": null
  }
}
```

`status` 取值：`NONE` / `PENDING_REVIEW` / `MATCHED` / `REJECTED` / `UNBINDING`

- `NONE` / `REJECTED` → 前端展示填写表单
- `PENDING_REVIEW` → 展示"资料审核中，预计 1 个工作日"
- `MATCHED` → 展示完整会员信息
- `UNBINDING` → 展示"解绑审核中"

---

#### 2.2.2 获取主播列表（三级取值第 3 级兜底）

```
GET /app/member/hosts
```

**响应**：
```json
{ "code": 0, "data": [ { "hostCode": "kjx", "hostName": "叩君芯" } ] }
```

> **前端取值逻辑（三级）**：
> 1. URL 带 `?h=kjx` → 直接用，**不显示主播字段**
> 2. 无 URL 参数 → 用户先填**会员编码**，前端从编码前缀（`KJX-`）**自动推断主播**，仍不显示字段
> 3. 若编码无前缀或前缀无法识别 → 才展示主播下拉，调本接口取列表

---

#### 2.2.3 提交绑定 ★

```
POST /app/member/binding
X-Idempotency-Key: {uuid}
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `hostCode` | string | 🔶 | 主播短码（三级取值带入；带入不到时前端展示下拉） |
| `douyinId` | string | ✅ | 抖音号（前端可预规范化：trim、去 @、小写） |
| `memberCode` | string | ✅ | 会员编码（前端可预规范化：trim、大写、去 -） |
| `claimMonths` | int | ✅ | 已订阅月数 |

**响应（成功 · 直接通过）**：
```json
{
  "code": 0,
  "data": {
    "status": "MATCHED",
    "member": {
      "memberCode": "KJX-A3F9K2B7",
      "douyinId": "@zhangsan",
      "expireAt": "2027-08-09",
      "availableCount": 14,
      "unlockedCount": 2,
      "remainCount": 12,
      "status": "VALID"
    }
  }
}
```

**响应（成功 · 转人工审核）**：`{ "status": "PENDING_REVIEW", "member": null }`

**响应（失败）**：`{ "code": 1001, "msg": "信息不匹配，请核对后重试" }`

**服务端处理链**（★ 全流程要严格按序）：

```
① 幂等检查（scene=binding, ref_id=account_id；同键异参返回 409）
        │
② 登录态校验（Sa-Token）
        │
③ 绑定功能是否被锁定（bind_locked_until > now → 1004）
        │
④ 该账号是否已绑定（bind_status == MATCHED → 1003）
        │
⑤ 规范化三要素
   · hostCode   → 查 kjx_host 得到 dept_id
   · douyinId   → trim / 去 @ / 小写
   · memberCode → trim / 大写 / 去 -
        │
⑥ 三要素精确匹配 kjx_member
   WHERE dept_id = ? AND member_code = ? AND douyin_id = ? AND subscribed_months = ?
        │
   ├─ 未命中 → 失败计数 +1（Redisson RRateLimiter）
   │           超 3 次 → 设 bind_locked_until = now + 30min
   │           返回统一提示 1001（不区分是哪一项错，防探测）
   ├─ 命中但 bind_state = 1（已被绑）→ 1002 + 展示申诉入口
   ▼
⑦ 是否自动通过？（配置 auto-approve，当前 = false）
   ├─ false → 写 binding(status=PENDING_REVIEW) → 后台待审
   └─ true  → 写 binding(status=MATCHED) + 更新 member.bind_state=1, bound_account_id, bound_at
        │
⑧ 写 BIZ + SEC 日志
        │
⑨ 事务提交
```

**后台审核通过时的动作**（`POST /admin-api/kjx/binding/{id}/approve`）：

```
① 校验 binding.status == PENDING_REVIEW
② 更新 binding → MATCHED, matched_at, reviewer_id
③ 更新 member → bind_state=1, bound_account_id, bound_at
④ 更新 account → bind_status=2
⑤ 同事务写 `kjx_outbox_event`（站内信 + 短信通知事件）
⑥ 同事务写 BIZ + AUDIT；事务提交后 Outbox Worker 调用 SMS4J
```

> ⚠️ **第 ③ 步的并发安全**：`kjx_member_binding` 上有 `UNIQUE(member_id)` 与 `UNIQUE(account_id)` 双唯一键。
> 若两个账号同时被审核通过指向同一会员，**第二次插入/更新会因唯一键失败并回滚**。这是设计意图，不是 bug。

### 2.3 作品与解锁组

#### 2.3.1 作品列表

```
GET /app/works?workType=game&unlocked=true&pageNo=1&pageSize=20
```

**服务端关键逻辑**：
- 只返回 `status IN ('PUBLISHED','GRAY')` 且 `deleted=0` 的作品
- **灰度过滤**：`GRAY` 状态的作品，按 `gray_ratio` 与账号 ID 取模决定是否可见
- **下架作品不展示**，但**已解锁用户仍可访问**（M-9：下架 ≠ 停服）→ 因此在**已解锁列表**里仍要返回
- 附带 `unlocked` 标记（LEFT JOIN `kjx_member_entitlement`）

#### 2.3.2 解锁 ★

```
POST /app/works/{workCode}/unlock
X-Idempotency-Key: {uuid}
```

**响应（成功）**：
```json
{
  "code": 0,
  "data": {
    "workCode": "breakup-editor",
    "unlockedCount": 3,
    "remainCount": 12,
    "entryUrl": "/runtime/breakup-editor",
    "alreadyUnlocked": false
  }
}
```

**服务端处理链**（★ 单事务）：

```
① 幂等检查（scene=unlock, ref_id=workId）→ 命中且请求哈希一致则直接返回首次结果（1010）；
   同键异参返回 409
        │
② 登录态 + 绑定态校验（bind_status=MATCHED → 否则 1009）
        │
③ 会员状态校验：status == VALID（否则 1005/1006）
        │
④ 作品校验：存在 + status IN ('PUBLISHED','GRAY')（否则 1008）
        │
⑤ 【CAS 原子更新】★ 一条 SQL 完成额度扣减
   UPDATE kjx_member
      SET unlocked_count = unlocked_count + 1,
          remain_count   = remain_count - 1,
          version        = version + 1
    WHERE id = ?
      AND deleted = b'0'
      AND status = 'VALID'
      AND unlocked_count < available_count;
   → 影响行数 = 0 → 1007（额度用完）或 1006（状态变了）
        │
⑥ INSERT kjx_member_entitlement（UNIQUE(member_id, work_id) 兜底并发）
   → DuplicateKey → 说明并发重复解锁 → 回滚 → 改为返回 1010
        │
⑦ INSERT kjx_unlock_record（含前后快照 + source='user'）
        │
⑧ 写 BIZ 日志
        │
⑨ 事务提交
```

> ⚠️ **第 ⑤ 步必须是一条 SQL**。禁止写成"先 SELECT 查 `unlocked_count` 判断，再 UPDATE"——
> MySQL 在 REPEATABLE READ 下，快照读会读到旧值，并发下必然超解锁。

#### 2.4.1 录入会员（生成编码）★

```
POST /admin-api/kjx/self/member
```

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `douyinId` | string | ✅ | 抖音号 |
| `subscribedMonths` | int | ✅ | **已订阅月数**（抖音后台抄录，直接录入，**不做换算**） |
| `subscribedDays` | int | ✅ | **累计已订阅天数**（额度计算来源，与月数独立录入） |
| `expireAt` | datetime | ✅ | 到期时间 |
| `remark` | string | 🔶 | 备注 |

> **铁律**：`subscribedMonths` 与 `subscribedDays` 均为必填且互不换算。
> `subscribedMonths` 只用于三要素绑定；`subscribedDays` 只用于
> `availableCount = floor(subscribedDays / 30)`。禁止任何 `months × 30` 或 `days ÷ 30` 分支。

**响应**：
```json
{
  "code": 0,
  "data": {
    "memberId": 100,
    "memberCode": "KJX-A3F9K2B7",
    "availableCount": 14,
    "status": "NOT_STARTED"
  }
}
```

**编码生成规则**（D-52 已确认改用随机码）：

```
格式：{主播短码}-{8位随机大写字母数字}
示例：KJX-A3F9K2B7
· 去掉易混淆字符（O/0、I/1、L）
· 全局唯一（UNIQUE KEY，冲突则重试，最多 5 次）
· 生成后立即返回给主播，由主播自行发给会员
```

## 3. 跨模块功能联动（全局串联）

### 3.1 主链路：从主播录会员到用户玩到作品

```
【主播侧】
主播登录后台（loginType=admin，角色 HOST）
    │
    ▼
录入会员 ──► kjx_member（含订阅月数/到期时间）
    │        └─► 系统生成 member_code ──► 返回给主播
    │
    ▼
主播把编码发给会员（抖音群/私信）
    │
════════════════ 平台边界 ════════════════
    │
【会员侧】
会员注册 ──► kjx_account（bind_status = NONE）
    │            └─► tianai-captcha + SMS4J 验证码
    │            └─► 写 kjx_account_device
    ▼
个人主页填三要素 ──► BindingService
    │                 ├─ 三要素匹配 kjx_member
    │                 ├─ 失败计数（Redisson RRateLimiter）
    │                 └─ 写 kjx_member_binding(PENDING_REVIEW)
    ▼
【运营侧】
后台审核 ──► binding → MATCHED
    │        ├─► member.bind_state = 1
    │        ├─► account.bind_status = 2
    │        ├─► 发通知（站内信 kjx_notification + 短信 SMS4J）
    │        └─► 写 BIZ + AUDIT
    ▼
【会员侧】
进入作品选择 ──► work 列表（灰度过滤 + 解锁标记）
    │
    ▼
点击解锁 ──► UnlockService
    │         ├─ 幂等守护 kjx_idempotency_guard
    │         ├─ CAS 扣减 kjx_member.remain_count
    │         ├─ 写 kjx_member_entitlement
    │         └─ 写 kjx_unlock_record
    ▼
进入运行时界面（M5）
```

### 3.2 联动矩阵（谁触发谁）

| 触发源 | 触发动作 | 被影响对象 | 是否同步 |
|---|---|---|---|
| 注册成功 | 写账号 + 建设备 + 写欢迎通知 Outbox；提交后签发令牌/异步投递 | `kjx_account` / `kjx_account_device` / `kjx_outbox_event` | 业务同事务 + 投递异步 |
| 登录成功 | 更新设备 + 记录登录 | `kjx_account_device` / `kjx_account` | 同步 |
| 主播录入会员 | 生成编码 + 派生字段计算 | `kjx_member` | 同步 |
| 提交绑定 | 失败计数 / 写待审 | `kjx_account.bind_fail_count` / `kjx_member_binding` | 同步 |
| **审核通过** | **更新三张表 + AUDIT + 通知 Outbox** | `kjx_member_binding` + `kjx_member` + `kjx_account` + `kjx_outbox_event` | **同步（同事务）** |
| 审核通过后 | 消费 Outbox，落站内信并发短信 | `kjx_notification` + SMS4J | **异步、至少一次、幂等** |
| 解锁成功 | 幂等守护 + CAS 扣额度 + 写权益 + 写记录 + AUDIT/Outbox | `kjx_idempotency_guard` + `kjx_member` + `kjx_member_entitlement` + `kjx_unlock_record` + `kjx_outbox_event` | **同步（同事务）** |
| 运营改会员数据 | 重算派生字段 + 写 AUDIT + **通知用户** | `kjx_member` / `kjx_notification` | 同步 + 异步通知 |
| 运营改权益 | 重算 `unlocked_count` + 写 `unlock_record(source=official_*)` | `kjx_member_entitlement` / `kjx_unlock_record` | 同步 |
| 账号注销 | 冷静期后解绑 + 删个人信息 | `kjx_member_binding` / `kjx_account` | 异步（定时任务） |

### 3.3 三个必须同步的"多表写"

| 操作 | 涉及表 | 事务要求 |
|---|---|---|
| **审核通过绑定** | `member_binding` + `member` + `account` + `AUDIT` + `outbox` | **必须同事务** |
| **解锁** | `idempotency_guard` + `member`(CAS) + `entitlement` + `unlock_record` + `AUDIT/outbox` | **必须同事务** |
| **运营改权益** | `entitlement` + `member`(重算) + `unlock_record` + `AUDIT/outbox` | **必须同事务** |

> **其余副作用通过 Transactional Outbox 异步**（通知、统计、ClickHouse 投影）。
> Outbox 与业务事实同事务，投递采用至少一次并要求消费者幂等；`AUDIT` 与 `BILLING` 仍必须同事务。

### 3.4 派生字段的单一写入口（M-6）

```
                  ┌──────────────────────────┐
   所有写操作 ───►│  MemberRecalcService       │
   （录会员/改会员/│  唯一的 recalc 实现        │
     改权益/解绑） └──────────┬───────────────┘
                             │
                             ▼
                    kjx_member 派生字段
        start_at / available_count / unlocked_count /
        remain_count / status
```

**禁止在任何其他地方重复实现这 5 个公式。** 这是 M-6 的强制要求——原 docx 把同一公式描述了 6 遍，多处实现必然写歪。

## 4. 对接风险清单（重点）

> 你问"对接方面会有什么问题"——以下 12 条是我预判会在 M1 集成阶段真实撞上的问题，按严重度排序。

### 🔴 R1. 前后台两套账号体系并存 —— 最容易搞混

| 体系 | 表 | 谁用 | 登录方式 |
|---|---|---|---|
| **后台账号** | RuoYi `sys_user` | 运营/主播/财务/超管 | 用户名 + 密码（RuoYi 原生） |
| **前台账号** | `kjx_account` | 会员（C 端） | 手机号 + 密码/验证码 |

**风险**：Sa-Token 若不区分 `loginType`，**前台会员的 token 可能被后台接口接受**（越权）。

**必须做**：
```java
// 前台登录
StpUtil.login(accountId, new SaLoginModel().setDevice("app"));
// 后台登录（RuoYi 原生，loginType=admin）
StpUtil.login(userId, new SaLoginModel().setDevice("admin"));

// 接口鉴权时校验 loginType
@SaCheckLogin(type = "app")     // 前台接口
@SaCheckLogin(type = "admin")   // 后台接口
```
**并在前端做一次越权测试**：拿前台 token 调后台接口，必须 401。

---

### ✅ R2 已解决：主播直接用「部门」承载（不再自研隔离机制）

> **原方案的问题**：我原打算在 `kjx_host.admin_user_id` 上做关联、Service 层手拼条件。
> 致命缺陷是「**靠每个开发者记得写**」—— 漏一个 self 接口就是横向越权。
>
> **已确认改为**：**主播 = RuoYi 的部门（`sys_dept`）**，直接复用框架原生数据权限。

**设计**：

| 项 | 约定 |
|---|---|
| 主播 | = 一个**部门**（`sys_dept`） |
| 主播账号 | = `sys_user`，`dept_id` 指向其主播部门，角色 `HOST` |
| 业务扩展 | `kjx_host` 主键 = `sys_dept.id`（1:1 扩展，只存 `host_code` / `dy_account` / `logo` 等业务字段） |
| **数据隔离** | **RuoYi `@DataPermission` 自动拼 SQL**，主播角色设为「**仅本部门数据**」 |
| 业务表关联 | `kjx_member.dept_id` = `sys_dept.id`；`kjx_member_binding` / `kjx_member_entitlement` / `kjx_unlock_record` **冗余 `dept_id`** 让数据权限直接生效 |

**收益**：
1. **零自研代码** —— 不写 MyBatis 拦截器、不维护 `HostContext`
2. **后台「部门管理」页面直接就是主播管理**，省一个页面
3. 部门树天然支持「叩君芯 → 运营部 / 各主播」的层级
4. 未来一个主播挂多个员工账号，同部门加 `sys_user` 即可，结构不变

**仍要注意两点**：

| # | 注意 |
|---|---|
| 1 | 业务表**必须有 `dept_id` 字段**，数据权限才能自动生效；若靠 JOIN 关联会失效 → 所以 `binding` / `entitlement` / `unlock_record` 要**冗余 `dept_id`** |
| 2 | **验收必须做横向越权测试**：用主播 A 的账号尝试访问主播 B 的 `memberId`，**必须查不到**（不是 403，是查不到） |

### 🟠 R3. Flyway 与 RuoYi 自带 SQL 脚本冲突

RuoYi-Vue-Plus 仓库自带 `sql/*.sql` 初始化脚本（建 `sys_*` 表 + 初始数据）。

**风险**：若既手工导入 RuoYi 的 SQL，又让 Flyway 跑 `V1__baseline_ruoyi.sql`，会**表已存在**报错。

**建议二选一**：
- **方案 A（推荐）**：把 RuoYi 的 SQL 整理成 `V1__baseline_ruoyi_vue_plus.sql`，**配置 `baseline-on-migrate: true`**，从此全部走 Flyway，不再手工导入
- 方案 B：`sys_*` 表手工导入，Flyway 只管 `kjx_*` 表（配置 `baseline-version` 指定起始版本）

**必须选一个并写进 README**，否则新人搭环境必然撞。

---

### 🟠 R4. SMS4J 与 RuoYi 内置短信模块冲突

RuoYi-Vue-Plus 自带短信模块（有自己的配置表和发送接口）。我们选了 SMS4J。

**风险**：两套短信配置、两条发送路径，运维混乱；且可能重复发送。

**建议**：
- **禁用/移除** RuoYi 内置短信模块的发送实现
- 保留其**配置管理 UI**（运营配密钥用），底层替换为 SMS4J 调用
- 或者干脆全部用 SMS4J，运营侧配置走自定义页面

---

### 🟠 R5. X-File-Storage 与 RuoYi 文件模块冲突

同上。RuoYi 有自己的 `infra_file` 表与上传接口。

**建议**：
- 保留 RuoYi 的 `infra_file` 作为**文件元数据表**（记录文件名/大小/URL/上传者）
- **底层存储改用 X-File-Storage**（一行代码切换云厂商）
- 好处：未来从阿里云 OSS 换腾讯云 COS，**业务代码零改动**

---

### 🟠 R6. tianai-captcha 与 Sa-Token 的验证码流程集成

tianai-captcha 是**独立的验证码服务**，有自己的校验 API（`ImageCaptchaApplication.matching()`），与 Sa-Token 无关。

**风险**：若把它当"Sa-Token 的验证码"用，会找不到对应 API。

**正确做法**：
```
① 前端调 tianai-captcha 的 GET /captcha/gen 拿挑战
② 用户完成滑块/点选
③ 前端把 {captchaId, captchaData} 随业务请求提交
④ 服务端在业务逻辑里调 tianai 的 matching() 校验
⑤ 校验通过才发短信/继续业务
```
**即：验证码校验是业务逻辑的一步，不是框架拦截器。**

### 🟠 R7. Redis key 命名冲突

Sa-Token、Redisson、业务缓存、验证码、限流**共用一个 Redis 实例**，key 可能撞。

**必须规划前缀**：

| 用途 | 前缀 |
|---|---|
| Sa-Token 会话 | `satoken:*`（Sa-Token 默认，可配） |
| 验证码 | `kjx:sms:code:{scene}:{phoneHash}` |
| 登录失败计数 | `kjx:login:fail:{accountId}` |
| 绑定失败计数 | `kjx:binding:fail:{accountId}` |
| 解锁限流 | `kjx:unlock:rate:{memberId}` |
| Redisson 锁 | `kjx:lock:{biz}:{id}` |
| Redisson 延迟队列 | `kjx:delay:{type}` |
| 业务缓存 | `kjx:cache:{module}:{id}` |

**约定**：所有自定义 key **必须以 `kjx:` 开头**。写进开发规范。

### 🟠 R8. 手机号加密后的检索与唯一性问题

`phone` 用 AES 加密存储不可检索，因此需要 `phone_hash`（**HMAC-SHA256，带密钥**）做唯一索引与查询。

**风险**：
- 用普通 SHA256 会被彩虹表反查（11 位手机号空间只有 1.5 亿，秒破）
- 密钥轮换会导致**所有历史 `phone_hash` 失效**

**对策**：
- 必须用 **HMAC + 固定密钥**（密钥入环境变量，**不进 Git**）
- 密钥版本化管理：`phone_hash_v1` / `phone_hash_v2` 并存，轮换时双写、后台逐步迁移
- 若嫌复杂，**初期可直接存明文手机号**（很多国内平台如此），但要在隐私政策中说明，且加密是合规方向

> **这条建议你拍板**：加密（合规好、复杂度高）vs 明文（简单、合规欠佳）。

### 🟡 R9. 时区与"会员到期"判定

会员状态（VALID/EXPIRED）依赖**服务端当前时间**与 `expire_at` 比较。

**风险**：若 MySQL 时区、JVM 时区、应用配置不一致，会出现"到期日当天被判定为已过期"或反之。

**必须统一**：
- MySQL：`--default-time-zone=+08:00` + 连接串 `serverTimezone=Asia/Shanghai`
- JVM：容器 `TZ=Asia/Shanghai`
- `expire_at` 语义：**到期日 23:59:59** 之前都算有效（需在 Recalc 里用 `< DATE_ADD(expire_at, INTERVAL 1 DAY)` 或明确 `expire_at` 存"最后有效时刻"）

**这条容易被忽略，但会引发大量客服纠纷。**

### 🟡 R10. 灰度作品的可见性一致性

灰度按 `账号ID % 100 < gray_ratio` 判断。**同一账号在列表页和详情页必须得到一致结果**，否则用户会看到"列表里有但点进去 404"。

**对策**：把灰度判定抽成 `WorkVisibilityService`，**列表、详情、解锁三处调同一个方法**。

### 🟡 R11. 前端 token 存储方式

Next.js 前台存 token 的两种方式：

| 方式 | 优点 | 缺点 |
|---|---|---|
| `httpOnly` Cookie | 防 XSS 窃取 | 跨域配置复杂；SSR 需处理 |
| `localStorage` | 简单 | **XSS 可窃取** |

**建议**：`httpOnly` Cookie + CSRF Token。因为前台会渲染第三方作品（Form B 沙箱 iframe），**XSS 面比普通站点大**。

---

### 🟡 R12. 沙箱作品的跨域与 token 传递

Form B 作品跑在**独立子域 iframe**里，需要调平台 SDK。

**风险**：
- iframe 拿不到主站 Cookie（不同源）→ 无法直接鉴权
- 若把 token 通过 `postMessage` 传给 iframe，**作品可以拿到 token 直接调平台 API**（越权）

**对策**：
- **不传 token**。改由宿主代理：iframe 通过 `postMessage` 请求宿主，**宿主用自己的 token 调后端**，再把结果回传
- 所有 SDK 调用都经宿主中转，iframe 永远拿不到凭证

（这条是 M5 的问题，但**现在的接口设计要为它预留**：SDK 类接口要支持"宿主代理调用"模式。）

## 5. 原待拍板项 R8 —— ✅ 已确认



| 方案 | 合规 | 复杂度 | 说明 |
|---|---|---|---|
| **A. 加密（AES）+ HMAC 索引** | ✅ 好 | 中（需密钥管理、密钥轮换方案） | 推荐方向 |
| **B. 明文存储** | 🔶 欠佳 | 低 | 国内不少平台如此，但隐私政策要说明，且未来改造麻烦 |

**结论：✅ 已确认方案 A（AES 加密 + HMAC 索引）**

| 项 | 规格 |
|---|---|
| 加密算法 | **AES-256-GCM**（Spring `StringEncryptor` 或自研加解密工具类） |
| 索引算法 | **HMAC-SHA256**（带密钥）—— **绝不能用普通 SHA256**，11 位手机号空间仅 1.5 亿，彩虹表秒破 |
| 密钥管理 | 主密钥入环境变量、**不进 Git**；版本化（`phone_hash_v1` / `v2`），轮换时双写 + 后台逐步迁移 |
| 涉及字段 | `kjx_account.phone`（密文）、`kjx_account.phone_hash`（HMAC） |
| 展示规则 | 后台列表**掩码显示**（`138****8888`）；仅超管可解密查看，且**写 `AUDIT`** |
