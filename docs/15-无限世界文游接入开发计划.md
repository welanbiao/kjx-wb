# 叩君芯 · 无限世界文游接入开发计划
## 实施稿 v0.13

> **状态**：可派发。玩法、组件和存档规则以本文为准。排版和视觉以两款原网页为准，开发时直接打开原文件复用，不要凭本文重新画一版。  
> **开工范围**：共用工具、分手结局修改器、小手机、单买桩、管理台配置、接入指南。  
> **不做**：修改会员月数/天数公式、打开对外 API 售卖、接真实短信或支付宝/微信、把管理台并进会员站、让旧网页继续自己请求模型或自己存档。

## 0. 使用方法

1. 每个工作包一个开发代理。审查代理只看本文的验收条和测试结果，不替开发代理重写需求。
2. 开发代理开工前读本文里该工作包的章节。做页面时直接打开原网页工程，复用排版、样式和结构；数据改走本文的后端组件。不要先把界面扔掉再按文字重做。
3. 只改该工作包「文件所有权」里的路径。公共契约、错误码、根 POM、`kjx-server` 装配若必须改，停下来交给审查代理，不要自行改冻结语义。
4. 每个工作包独立编译、独立测试，交回：改了哪些文件、测试命令和通过/失败/跳过数量、未完成项。
5. 前一个工作包的验收未过，不开始依赖它的下一个。
6. 每个接入开发任务或浏览器测试任务结束时，主代理把其中通用的问题补进 `docs/接入游戏/常见问题.md`。不记录某一款的剧情细节，不记录密钥。后续文游接入先读这份记录，再读本文对应工作包。WP-G 的正式指南从这里整理，不另起一套互相矛盾的说法。

```text
4. 完成后运行该工作包写明的测试命令；
5. 返回变更文件、测试结果、未完成项。
```

## 2. 已拍板

1. 第一批共用工具只有四件：人设组装、一对一发送、群聊发送、发红包。朋友圈留到小手机。
2. 第一款接入的文游是「分手结局修改器」。进入只消耗现有会员额度。
3. 单买支付桩确认之前，两款文游的完整版都只能用会员额度进入。额度解锁在桩完成前后都有效。试玩不消耗额度，也不等于解锁完整版。
4. 每一款文游都有一块试玩，展示方式与分手结局案卷墙上的「试玩」相同：放在最前、标明试玩、不填密钥也能走进去，超出剧本的操作被拒绝。
5. 后端工具与具体剧情解耦。前端只按后端给出的组件类型渲染，不在页面里写发红包、改余额、拼人设提示词。
6. 《接入新文游指南》单独成 WP-G，放在全部功能实现之后，不和管理台配置写在同一个工作包里。指南只记录已经跑通的接法。
7. WP-B 验收通过后，先做 WP-B1，不进入小手机。WP-B1 由测试子代理按真实用户顺序走完：登录、自己填写接口地址和密钥、购买、再用该密钥游玩。主代理只验收。密钥不得写进后端代码。
8. 文游上架不经过审查队列。接入该作品的开发按规则把作品写成已上架，会员站列表随即能看到。管理员之后可以在作品管理里改上架或下架。会员绑定审核仍保留，与作品上架无关。
9. 前端排版和视觉按原网页部署，能复用的样式、结构和静态资源直接搬。重新规划的是组件交互和数据：页面不再自己请求模型、不再把局面写进浏览器。原主站里已有的工具、会话、存档和素材签名继续用，不另写一套。
10. 两款文游的完成验收都是三条，缺一不可：界面与原版一致；功能与原版一致；交互已经组件化。
11. 会员站主页和账号外壳按「有辨识度的网页设计」重做，贴合无限文游世界。文游手机内界面不参与这次重做。幻灯片技能已从仓库删除，不再作为前端参考。

## 3. 网页主题

主站对外是一个端口。会员站外壳保持现在的天空蓝地面、奶油色内容板和少量橙色。色值：地面与顶栏 `#1387C0`，内容板 `#FAEDD1`，强调 `#F4520D`。蓝色约占六成，奶油色约占三成，橙色约占一成。路径是「登录、绑定、作品、我的解锁」。管理员在本浏览器登录后才多一个「管理」入口。

文游进手机之后的屏幕，按原网页的排版部署，不按会员站这套色重画手机内部。原文件允许开发时直接打开：

- 分手结局修改器：`D:\分手结局修改器-v2-给产品`。页面结构在 `index.html`，样式在 `css`，交互脚本在 `js`，图片和音乐在 `assets`。
- 小手机：`D:\小手机v3.0\叩君芯AI对话小手机3.0 (7)(1).html`。排版、样式和画面结构以这一份为准。v3 里直接请求模型、写入 `localStorage` 的脚本不进入会员站。开发计划里的微信核心先接：消息、一对一、朋友圈、备忘录、相册、钱包、红包、转账。五子棋、象棋、扫雷、猜词、猜拳、猜数字、饱了么、京西、酷猫、电话和手机内的密钥表单留在画面里，不接成第二套模型通道。

复用方式：把原页面的结构和样式迁进会员站的游玩页，静态图和音乐按第 3.5 节进对象存储，地址改成签名地址。原脚本里凡是改局面、发模型、读写浏览器存档的函数删掉，改成调用后端工具后的组件声明。密钥输入框可以留在原设置屏的位置，提交目标改成后端。

不要整页用 iframe 套旧站，让旧脚本继续自己玩。那样排版虽然一样，数据仍在浏览器里。

登录页只有会员站这一页，不再单独做一块管理台登录。密码登录里，手机号和会员密码进入会员站。若填写的是管理员账号和密码，就进入若依后台。管理员登录之后，会员站路径上才出现「管理」。点「管理」也进入同一个若依后台，不是再开一个登录页。

后台用若依的侧栏和顶栏。主播只看到自己的资料、自己的会员、绑定状态和自己的解锁记录。运营和管理员看到工作台，以及下面这份管理清单。点「作品管理」能看当前作品是否上架、版本、谁解锁了、权益从额度还是购买来。密钥只显示已配置或未配置。

| 菜单 | 管什么 |
|---|---|
| 工作台 | 待审绑定、在架作品数、今日解锁 |
| 主播管理 | 主播部门与主播资料 |
| 跨部门会员 | 会员月数、天数、状态；月数和天数分开改 |
| 绑定审核 | 通过或驳回，驳回要填原因 |
| 申诉处理 | 申诉列表和处理结果 |
| 作品管理 | 接入时已上架。管理员可改为下架或重新上架，并查看试玩是否可用、版本、解锁记录。没有上架审查队列 |
| 作品内容 | 节点、人物、结局、披露阶段；母版提示词不下发 |
| 素材与音乐 | 图片和音乐是否入库、版权是否齐；不提供永久直链 |
| 权益调整 | 给指定会员加减某部作品的解锁 |
| 解锁记录 | 按作品、会员、时间查看，含额度解锁和购买解锁 |
| 订单 | 桩订单的未支付和已确认；空验签不能当成成功 |
| 用户账号 | 正常、锁定、注销；可强制下线 |
| 日志 | 按链路编号、会话、会员查看业务日志和安全日志，不含密钥和聊天正文 |
| 健康检查 | 服务是否可用 |

主播账号不能打开运营清单。直接访问别人的作品或会员，后端拒绝。前端把菜单藏起来不算权限。

产品对外的说法：这里是「无限世界」的主世界。用户买下或解锁一个文游副本，是在扩充自己的版图。个人主页汇总已解锁副本、进度和成就。成就只能由后端已经提交的事件产生。平台自己的模型接口本阶段不对外卖；游玩默认用用户自己的密钥，由后端转发。

### 3.1 分手结局修改器（第一款）

主题是叩君芯模拟器的七夕特别版。标题两句：「如果那句话没说出口，他们还会分手吗？」「今天，帮 TA 改写曾经的选择。」

玩家先在案卷墙选一对已经分手的人，再选代入她或他，然后进入那个人的手机。玩法是：探索感情里已经发生的事，在可改写的节点改掉一句话，看对方回复、旁白、动态、便签、账单、相册和结局如何跟着变。历史原对话不能直接改，必须切到改写版才能发送。可以打开对方手机；对方可能毫无察觉，也可能发现，之后不回消息、写下失望、甚至反过来怀疑玩家。玩家可以在结局册里选择放手，感情按当前结局走。

可玩示例是「江雪 × 张旸奕」，回避型依恋对焦虑型依恋。墙上的句子：他曾为她删掉最好的朋友，最后为朋友的一句话删掉了她。其余副本本阶段只保留身份，不要求全部可玩：江迟 × 温宁、方硕 × 苏念、秦渡 × 夏栀、谢衍 × 唐梨。第一款验收只要求江雪 × 张旸奕这一对能走通。

手机里玩家能看到的表面：

- 状态栏和动态岛，时间从 9:41 这一类系统时间来，不由模型随便改。
- 案卷墙、选边、解锁手机、主屏幕。
- 与对方的一对一聊天，以及手机里其他联系人的一对一线程（不是一个大群房间）。
- 动态、便签、账单、相册、结局册。
- 顶上的世界切换：「原世界回溯」和「结局改写后」。
- 指标：分手概率、对方对自己的爱意。爱意分男女两侧，内部记录，页面可以显示百分比，但模型不能把精确数值当成可以对玩家朗读的台词重点。

一次改写在后端必须落成这些事实，页面不能自己发明：

- 被改的是哪个节点、下一处可介入节点是哪个。
- 从被改句的下一条起到下一节点末尾的重演消息。被改句本身和它之前的历史由系统拼接，不由模型重写。
- 每条消息有节点、消息号、说话方（她或他）、时间、正文，以及是否改写、已读、撤回、沉默、分支。
- 可选：对方即时回复零到三条、一条十五到五十字的涟漪旁白、一条埋下来以后才会翻出的话。
- 动态、便签、账单、相册只替换两个节点日期之间的条目，区间外保留。
- 状态：分手概率 0 到 100，男对女爱意 0 到 100，女对男爱意 0 到 100，推进天数，以及一个标记（对方确认、对方醒悟，或空）。
- 标题和过场旁白本轮冻结，模型不许改。

世界联动用规则，不另叫一次模型。改写句里若出现道歉、想你、别走一类软话，或滚、无所谓、别联系一类硬话，才改其他线程的预览和未读，并可能往便签草稿里加一条系统说明。没有这两类话，世界不动。

旧网页把密钥和整局进度放在浏览器里，并直接请求用户填写的模型地址。迁入后这两件事删除。密钥只在当次由后端转发。局面以服务端会话为准。

案卷墙的第一张卡就是试玩，不是完整版里的某一对。卡片眉题写「玩法示例」，角标写「试玩」。这一张不锁。上面有关系类型、一句金句、两个人的名字，以及「进入某一方手机」的入口。左右滑动才是其余副本；未做好的标「敬请期待」，不能点进空内容。江雪 × 张旸奕同时承担这张试玩卡和第一版完整版，但两条会话分开：试玩不扣会员额度，完整版才扣。

试玩入口在标题页就能选，文案是「请填密钥，或用演示模式」。选演示后进入案卷墙，手机角上显示「演示」。演示里的改写不请求模型，只回放后端写好的那几句。玩家改了一句剧本没准备的话，页面提示「演示模式暂未覆盖这句改写」，局面不改。完整版关掉演示标记，才走密钥和模型。

### 3.2 小手机（第二款，朋友圈在这里做）

主题是「梦女小手机」。外壳像一部微信：消息列表、一对一聊天、朋友圈、备忘录、相册、钱包、底部加号里的红包和转账。默认玩家名是「梦女」。默认对方是一个温柔、会开玩笑、关心日常但不黏人的男生。人设要求永远不承认自己是 AI，不打破第四面墙。

开局生成两步，都在后端做：先得到一份完整结构化人设，再生成三到五条初始朋友圈。钱包初始显示额是 520，这是游戏内货币，不是平台会员额度，也不是人民币订单。

朋友圈、红包、转账、备忘、相册的画面按 `小手机01.html` 里已有的区块摆，不重新设计。这些区块里的点击改成后端组件：朋友圈、红包、转账、备忘不再在页面里改数据。

小手机同样要有试玩，放在作品入口最前，角标「试玩」。不要求案卷墙，但信息结构相同：一句能看懂的金句、角色名、一个不锁的入口。试玩内容是一段写死的短聊天和一条朋友圈，不调用模型，不扣游戏钱包，也不扣会员额度。超出这段剧本的发送、红包或朋友圈，提示试玩未覆盖，状态不变。完整版才从 520 的钱包和后端生成的人设开始。

### 3.3 从旧机器人经验里留下的做法

这些是规则，不是把旧机器人搬进来。

- 注入的是世界状态：现在是谁、说到哪一天、哪些标志已经成立、人设里的说话方式和铁律。台词由模型写。代码里不写死角色的示例对白。
- 能用规则决定的事不调用模型。分手结局里软话/硬话引起的线程预览，就是规则。
- 人设拆开存：外显、内在、成因、说话方式、触发、铁律。不要把整份提示词在两款文游之间复制粘贴。
- 群聊免打扰、表情包当主回复、QQ 机器人的部署方式，不进入这两款文游。

### 3.4 每款文游的试玩

以后每接一款文游，都要有一块和分手结局试玩卡同类的入口，不能只有解锁后的完整版。

- 位置在该作品入口的最前面。角标写「试玩」。旁边有一句金句和角色名。未完成的其他章节标「敬请期待」。
- 不登录会员额度、不支付、不填写模型密钥，也能进入试玩。
- 试玩剧本放在后端，按固定步骤回放。不调用模型，所以没有密钥也能走完准备好的那几步。
- 玩家操作超出剧本时，后端拒绝写入，页面说明这一句试玩没有覆盖。
- 试玩会话单独标记。它不发放完整版权益，不增加主世界成就，不改完整版会话里的消息和钱包。
- 完整版仍按已拍板的规则：桩确认前只用会员额度进入。从试玩里不能直接变成完整版，必须再走解锁。

### 3.5 图片和音乐放哪里

分手结局已经备好的画面和声音不放进会员站的页面目录，也不放进浏览器能直接穷举的公开静态文件夹。数量是：46 张 webp（壁纸、手机框、主屏）、22 个 svg、2 张 png 遮罩、1 个字体、2 首 mp3。开场音乐约 14MB，主屏音乐约 6MB。两首都低于单文件 50MB 的上传上限。

存放分成两层。

玩家看得到的图、字体和音频，进对象存储的公开范围。开发时写到本机目录，由环境变量 `KJX_WORK_OSS_ROOT` 指定；不设这个目录时只留在进程内存里，重启就没了，所以开发机必须设目录。库里记一条素材或曲目：属于哪部作品、哪个版本、对象键、类型、版权是否齐。页面拿到的是短时签名地址，过期再向后端要，不把永久直链写进前端包。

玩家不该下载走的内容进服务端范围：试玩剧本、改写规则、人设母版、选曲规则。对象键落在 `server/` 下。这个范围禁止签发到公开地址。选哪首曲子、什么时候播，留在后端；公开范围里只放音频文件本身。

试玩和完整版可以共用同一张壁纸、同一首曲子。差别是会话和权益，不是复制两套文件。小手机以后若有自己的图和音乐，同样按作品分目录放进同一套存储，不和分手结局的对象键混用。

现在还没有接阿里云或腾讯云。换云时只换存储适配，对象键和库里的记录不改。签名用的本地密钥不是云密钥，不能写进日志。会员站顶栏那个小标志可以继续留在页面工程里，它不是文游素材。

### 3.6 对局数据、存档和日志各放哪里

玩家里的进度不放在浏览器里，也不写进日志表。后端只用两张已有的业务表，日志只是旁路。

**进行中的局面**放在会话表。一行就是一个账号在一部作品里的一局。固定列有：会话编号、账号、作品编码、当前阶段、内容版本、状态版本号。会变的事实放在一列 JSON 里，例如分手结局的节点、重演消息、分手概率、两侧爱意、原世界或改写世界、侧线预览；小手机的一对一消息、朋友圈条数、游戏钱包。试玩在这份 JSON 里标成试玩，不另开一张表。每次写入都重算校验和，并用版本号做乐观锁。两个请求同时写，后一个冲突，必须重读再写，不能覆盖。

**存档**是局面的快照，不是第二份真相。玩家继续游戏时，以会话表为准；存档只在自动槽或手动槽上留一份可恢复的副本。槽位按「会话 + 槽名」唯一。快照带同一套校验和，再加一段 HMAC 签名，防止页面改完再交上来。签名密钥不进日志。读档时签名或校验和对不上就拒绝，不把坏数据写回会话。试玩可以有自己的自动槽，但不能读进完整版会话。

**日志不负责恢复进度。** 系统已经有十二类日志。这一阶段和文游对齐的方式如下。

| 发生的事 | 写入 | 不写入 |
|---|---|---|
| 额度解锁、桩订单确认、创建或覆盖存档 | 业务日志。永久留在 MySQL。记下谁、何时、哪部作品、哪个会话、哪个槽、成功或拒绝 | 聊天正文、密钥 |
| 登录失败、密钥地址指向内网、无权益硬闯 | 安全日志。MySQL，至少留一年 | 密钥本身 |
| 模型调用 | 调用元数据：通道是用户密钥、模型名、耗时、用量、成功或失败、同一条 trace。分析库未开时不阻塞游玩 | 密钥、完整提示词。对话内容默认不落库 |
| 人设组装、发消息、发红包、试玩拒绝 | 工具名、是否通过、拒绝原因、同一条 trace | 人设全文、红包附言以外的长对白 |
| 后台改上架或看订单 | 审计日志，只追加 | 密钥 |

同一次点击从页面到存档共用一个 `trace_id`，会话编号和回合编号放在日志的上下文里，这样排障能串起来，但恢复进度只读会话表和存档表。业务日志故障不能让已经校验通过的落库回滚；日志写入失败只记错误，不向玩家假装这一步没发生。分析用的访问日志和工具明细库本阶段可以关着，不能因此改掉上面这张对齐表。

会员额度、权益、游戏钱包、人民币订单仍然分属各自的表。游戏钱包在会话 JSON 里，不进会员额度，也不进账本。

## 4. 必须守住的事实（开发中已经碰过）

会员额度在服务端计算：可解锁数等于已订阅天数除以 30 的整数商。月数和天数是两个独立字段，页面禁止把天数换算成月数，也禁止反过来。绑定核对用的是已订阅月数，不是可解锁数。新解锁要求会员有效；已经解锁的作品是买断，会员过期仍可进入。工具调用只检查有没有这份权益，不因为过期再拦一次。

一对一发送和发红包的后端实现已经存在，但是不完整：

- 一对一发送只往界面指令里追加一条气泡，角色固定为 NPC，正文来自参数。气泡类型 `chat.bubble`，属性只允许正文，以及角色枚举：npc、user、system。多出来的字段会被拒绝。它还没有把消息写进会话状态。
- 发红包会用钱包减去金额，红包计数加一，并给出红包卡片和余额。钱包缺省当 0。现在金额大于余额时仍会减成负数。已有测试是钱包 100、先调整减 10、再发 20，结果应为 70。这个成功例子必须保持。
- 朋友圈发送已经能追加动态卡片并增加计数。本阶段不要改它的行为，小手机工作包再启用。
- 人设组装和群聊发送还没有。

界面白名单里和本阶段有关的类型：聊天气泡、红包卡片、钱包余额、动态卡片。禁止在属性里放 html、script、style。作品不能注册新的组件类型。

工具实现只允许内置函数和明确步骤的组合。脚本类实现直接拒绝。同一次幂等键，参数相同则返回原结果，参数不同则冲突，不得执行第二次。无权益、会话不属于当前账号、会话和作品对不上，都要拒绝且不改状态。

数据库迁移：工具模块已占用 V620 到 V628，下一号只能是 V629。V630 起已被会话和存档占用，不能拿来做工具。迁移目录是 `classpath:db/migration`，不能写成会扫到测试脚本的 `classpath*:`。

本地运行时已经证实的坑，写代码和启动时直接避开：

- JDBC 字符集参数写 `UTF-8`。写成 `utf8mb4` 会在连接时失败。
- 本机 Redis 是 `127.0.0.1:6380` 且有密码。不要连到 6379。
- 从 WP-B 起，数据库验收用本机已经有的容器：`kjx-mysql` 在 `127.0.0.1:3306`，库名 `koujunxin`；`kjx-redis` 在 `127.0.0.1:6380`。密码只从本机 `.env` 读取，不写进仓库、不打进日志。不要再为验收启动临时 MySQL。`kjx-dev-gateway` 只是 80 端口的 Nginx，不是数据库。容器若是退出状态，先把 `kjx-mysql` 和 `kjx-redis` 拉起来再验。单元测试可以不连库；标明为数据库集成或验收的检查必须打在这套库上。
- 带请求体的浏览器调用如果没写 Content-Type，会变成纯文本，后端拒绝。会员站转发层必须把这种请求改成 JSON。
- 在组件扫描阶段用条件注解注册控制器，条件当时不成立，控制器会丢。控制器要在自动配置里用 Bean 注册。
- 管理端登录附加信息不能从默认的登录工具读取，那只能看到会员端。部门隔离要读管理端登录对象。
- 会员站和管理台是两个应用。对外一个端口时：会员页面和会员接口进会员站，`/admin/` 进管理台且基础路径就是 `/admin/`，`/admin-api` 进后端。不要用会员站的重写去代理管理台的热更新。
- 模型密钥、手机号、验证码不进日志，也不进浏览器长期存储。
- 平台通道失败或用户密钥失败时，不得改扣平台余额。
- 支付验签密钥为空时，回调保持失败，不能当成支付成功。
- 冻结中的平台扣费会话若只放在内存里，进程重启后对不上。本阶段文游不走平台扣费，不要依赖那段内存状态。

## 5. 一次游玩在后端里的顺序

1. 页面提交玩家操作和会话编号。
2. 后端确认登录、权益、会话属于该账号且属于该作品。
3. 需要模型时，后端用人设组装的结果、当前局面和允许的工具名拼请求，再转发到用户密钥对应的地址。地址每次都要检查，内网、环回和元数据地址拒绝。
4. 模型如果调用工具，先后检查参数、权益、会话、阶段和余额。不合法则拒绝，局面不变。
5. 合法则写入局面，返回给玩家看的台词，以及组件声明。声明形如：放到聊天记录末尾，类型是红包卡片，属性是金额、祝福和未拆开。
6. 页面只按类型渲染。刷新后以服务端局面为准。

人设六个字段：外显、内在、成因、说话方式、触发、铁律。前四项缺一则组装失败，不生成空提示词。组装结果放在会话状态里给模型用，不作为玩家可见组件。

## WP-A 四个共用工具

### 目标

人设组装、一对一发送、群聊发送、发红包成为与任何一部剧情无关的后端工具。状态写在服务端，界面声明只用白名单类型。

### 依赖

无。不依赖文游内容。

### 文件所有权

- `backend/kjx-modules/kjx-tool/**`
- 新迁移只能是该模块下的 V629

### 开发功能

1. 人设组装：从会话状态读取人设。缺人或前四项为空则失败且不写提示词。成功时把拼好的片段放进状态，供后续模型调用，不产生玩家可见组件。

3. 群聊发送：正文和发言人都不能空。成功时同样用聊天气泡，并带上发言人。为此允许气泡多一个可选发言人字段，最长 64。消息写入单独的群消息列表，不要和一对一列表混在一起。
4. 发红包：金额缺失、小于等于 0、或大于当前钱包（没有钱包视为 0）时失败，钱包、红包计数和界面指令都保持原样。成功时的扣款、计数、红包卡片和余额声明保持现有成功路径。
5. 三个需要注册的工具名：`persona.assemble`、`chat.send`、`chat.group.send`、`redpacket.send`。后两个里已有的发送和红包要补全，不是另起一套同名实现。
6. 用一份与江雪、梦女都无关的夹具调用这四件。不调用真实模型。

### 验收

- 群聊消息不进一对一列表；发言人出现在气泡属性里，且能通过白名单校验。
- 钱包 100、调整减 10、再发 20，余额仍是 70。
- 余额不足时发红包，余额和红包计数不变。
- 命令：`mvn -f backend/pom.xml -pl kjx-modules/kjx-tool -am test`
- 无 Docker 时容器测试可以跳过，但上述单元测试必须通过。交回通过数、失败数、跳过数。

### 注意事项

- 不要改朋友圈工具。
- 不要把提示词片段放到玩家可见组件里。
- 不要在日志里打印人设全文以外的密钥；人设片段可以出现在测试断言里，不要出现在运行日志。
- 不要改 V620 到 V628 已执行过的脚本；变更用 V629。
- 不要改会员模块、计费模块、契约和会员站页面。

- 一段变更说明：每个工具写了哪些状态字段、发出哪种组件。

## WP-B1 真实用户游玩验收

## WP-C 小手机与朋友圈

### 目标

梦女小手机按同一套工具接入。开局在后端生成人设和三到五条朋友圈。一对一、红包、转账使用已有工具，不写第二份。

### 依赖

WP-A 验收通过，并且 WP-B1 已由主代理通过。WP-B 的解锁和游玩入口已经存在，本工作包复用入口，不改额度规则。

### 文件所有权

- `backend/kjx-modules/kjx-tool/**` 里朋友圈发送的启用和测试；若要改朋友圈行为，只加测试能锁住的增量
- `apps/web` 里小手机游玩页
- 该作品自己的内容数据

### 开发功能

1. 独立作品，类型是文游。解锁仍只用会员额度。
2. 界面按 v3 单文件的微信式布局复用：消息列表、一对一、朋友圈、备忘录、相册、钱包、红包、转账。默认称呼梦女，默认联系人顾西。游戏内钱包从 520 起算，和会员额度分开。不要重新画一版微信。手机里的模型地址和密钥不使用，沿用会员站设置里已经保存的通道。
3. 开局：后端生成结构化人设并保存，再生成三到五条初始朋友圈。人设必须走 WP-A 的组装，不能把旧网页里的长提示词原文当成唯一真相源。旧提示词里的约束要收成字段：说话自然、偶尔反问、关心日常、不黏人、不承认自己是 AI、不打破第四面墙。
4. 发消息走一对一发送。发红包走发红包，余额不足时页面保持原余额。转账走已有的钱包调整加转账卡片，金额不能把游戏钱包扣成负数。
5. 朋友圈发送保持「追加动态卡片并增加计数」。小手机只启用它，不把实现复制进作品。
6. 入口最前放试玩卡：角标「试玩」，一句金句，梦女和默认男生的名字。试玩是一段固定短聊天加一条朋友圈，不调用模型，不把钱包从 520 扣下去，也不扣会员额度。试玩里再发红包或再发朋友圈时，提示未覆盖且钱包不变。完整版才生成人设并使用 520 的钱包。

### 验收

完成必须同时满足下面三条。

1. 界面一致。消息列表、聊天、朋友圈、备忘录、相册、钱包、红包和转账的排版与 v3 单文件一致，不重画。
2. 功能一致。原版能做的一对一、朋友圈、红包、转账、备忘和试玩，这里都能做，并且结果相同：余额不足不扣款，开局有三到五条朋友圈，钱包从 520 起。
3. 已经组件化。这些操作走后端工具和会话表，不走页面里的旧脚本。

- 额度解锁后进入，刷新后人设字段、朋友圈条数和钱包仍在。
- 初始朋友圈条数在 3 到 5 之间。
- 发一条一对一、发一笔不大于余额的红包、再发一笔大于余额的红包：前两笔留下记录，第三笔余额不变。
- 与分手结局修改器互不覆盖会话。在小手机里的操作不会改江雪那一局的消息。
- 未解锁时试玩卡可进入。试玩完成后额度不变，完整版钱包仍是进入完整版时的 520，不含试玩操作。

### 注意事项

- 原页面的样式和结构要复用。禁止整页 iframe 套旧站，也禁止只凭本文描述重画一版。
- 游戏钱包 520 不是订单金额。
- 不在本工作包打开单买。

- 说明朋友圈、一对一、红包分别调用的工具名。

## WP-D 单买桩

### 目标

同一份解锁权益增加来源「单次购买」。开发环境用桩确认后才发放。确认前不能靠购买进入两款文游。

### 依赖

### 文件所有权

- 会员权益写入处，仅增加来源，不改额度公式
- 不接真实支付宝、微信 SDK

### 开发功能

1. 创建一笔未支付订单，作品和账号写在订单上。未确认时查询权益，该作品仍是未解锁。
2. 桩确认只在显式调用时把订单标成已支付，并写入一条权益。来源与额度解锁区分开。

### 验收

- 有效会员仍可以用额度解锁，不创建订单。

### 注意事项

- 不调用外网支付。
- 不在日志里写支付密钥。

## 6. 审查时怎么验收

审查代理不重做开发。两款文游先按第 2 节第 10 条的三条验收，再用浏览器点原版和迁入版对照。三条里任何一条不成立，工作包不通过。

- 界面：关键屏幕并排看，排版不一致则不通过。
- 功能：原版的主路径在迁入版走一遍，行为不一致则不通过。
- 组件化：抽查请求是否进后端工具；页面仍直接请求模型或只写浏览器存档，则不通过。
- 测试命令是否就是本文写的那条。
- 通过、失败、跳过的数量是否交回。失败则不通过。数据库验收若打在临时库上，不通过，改到 `kjx-mysql` 和 `kjx-redis` 再验。
- 抽查：红包余额不足是否未改状态；人设缺字段是否未写提示词；两款文游的会话是否隔离；密钥是否出现在日志或页面存储里。
- 存档是否只作为会话的快照；日志是否没有被当成进度来源；业务日志是否记下解锁和存档且不含密钥与聊天正文。
- 文件是否越出该工作包的所有权。越出则退回，不把公共契约改动算进通过。
