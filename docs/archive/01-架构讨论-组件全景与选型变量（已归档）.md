# 叩君芯会员产品网站 · 第 1 轮架构讨论
## 组件全景与选型变量（先想清楚"要造哪些东西"，再谈"用哪个开源项目"）

> 讨论对象：上传/售卖 **AI 驱动文游** 与 **多轮对话式 UI Layout（Multi-turn Conversational UI Layout）美化皮肤** 的会员制网站
> 输入材料：《叩君芯会员产品网站功能设计文档.docx》（8 页 / 约 3500 字，荣耀文档导出，最后修改 2026-09-19）

## 0. 先说文档读取结论（重要：文档和你现在描述的产品对不齐）

文档实际写的是一份 **「会员产品解锁系统」**，覆盖三张表 + 六个页面 + 解锁校验 + 防篡改清单：

- 三张表：会员授权表、产品表、解锁记录表
- 六个页面：主界面、会员登录、产品选择、产品管理（后台）、会员授权管理（后台）、解锁记录查询（后台）
- 核心规则：可解锁产品数 = 已订阅天数 ÷ 30 向上取整；已解锁产品永久可用、不再校验会员状态
- 防篡改：后端查表、后端校验数量、产品按 ID 隔离、请求签名验签

**文档里没有出现的**：
「产品」到底是什么形态、皮肤怎么上传/审核/版本化、AI 能力从哪来、谁付模型的钱、钱怎么收（有"解锁"没有"支付"）、会话与存档、创作者体系、合规与备案。

**结论**：这份文档 = 这个网站的 **M1「会员与解锁」模块**；
你现在要做的 = 把它扩成 **「AI 文游 & 对话式 UI 皮肤」的数字商品平台 + LLM 能力网关与计量计费**。
两者不是替换关系，是包含关系。第 2 轮选型时必须把这两层分开选。

## 1. 定性：这实际上是三个系统叠在一个域名下

| # | 子系统 | 本质 | 并发特征 | 技术难度 | 文档覆盖 |
|---|---|---|---|---|---|
| A | 会员与解锁（Entitlement） | 低频写 + 强一致性的授权账 | 低 QPS，但**不能错、不能超卖** | 中 | ✅ 已覆盖 |
| B | 数字商品商城 + 皮肤交付 | 内容分发 + 交易 | 读多写极少，海量静态资源，靠 CDN | 中 | ❌ 未覆盖 |
| C | LLM 路由网关 + 计量计费 | 高并发代理 + 用量账本 | 高 QPS、长连接、流式、成本敏感 | **高** | ❌ 未覆盖 |

三者技术选型几乎没有交集，**必须分开选型、分开部署、分开扩容**。
失败模式通常是：想用一个"后台管理框架"或"商城模板"全包，最后 C 拖垮 A/B。

## 2. 组件全景（9 层）——请按这个清单自查有没有漏

每层给出：要解决什么 / 必须先定什么 / 最容易踩的坑。

### L1 客户端与呈现层
- 商城首页、皮肤详情页、我的会员、订单/购买、设置
- **皮肤预览器（Preview Sandbox）**：多轮对话 UI 布局的实时预览
- **宿主运行时（Host Runtime）**：真正跑文游 + 对话式 UI 的地方
- 必须先定：**皮肤是"数据"还是"代码"？**（见 §5 Q1）——这一条决定整个站的安全模型与选型
- 坑：皮肤来自创作者 = 第三方产物 → XSS / CSS 逃逸 / 越权读取宿主上下文

### L2 皮肤资产与规范层（这个站真正的护城河，也是最常被漏掉的一层）
- **Skin Spec**：版本化 JSON Schema —— design tokens（颜色/间距/字号/圆角/动效曲线）+ layout slots（消息气泡/头像/工具条/输入区/流式光标）+ 组件替换 + 资源清单 + 依赖声明 + 宿主兼容版本
- 包管理：skin 包 = 版本化 bundle，对象存储 + CDN，语义化版本 + 兼容性声明 + 升级迁移器
- 授权与防拷贝：license token（绑定会员/设备/域名）、运行时校验、水印、混淆
- 必须先定：皮肤是否允许任意 JS？允许 = 安全与审核成本 ×10
- 坑：**纯前端皮肤一定可以被复制**，技术上防不住；只能靠「账号绑定 + 服务端下发 + 持续更新 + 法务」

### L3 会话与对话运行时
- 多轮对话状态机：session / turn / 上下文窗口 / 记忆 / 摘要压缩
- 流式传输：SSE 或 WebSocket、断线续传、长连接规模与心跳
- 文游引擎：分支剧情 DSL、状态机、变量系统、存档/回档/多结局
- 必须先定：上下文超出窗口时怎么办（截断 / 摘要 / RAG 检索）
- 坑：LLM 是秒级慢依赖，必须先返回布局骨架再流式填充，否则 UI 假死

### L4 AI 能力网关（AI Gateway）
- 多供应商适配：OpenAI / Anthropic / Gemini / DeepSeek / Qwen / 豆包 / 自建 vLLM
- 路由策略：按成本、延迟、质量、可用性；降级与故障转移；灰度发布
- 治理：虚拟 Key、租户隔离、QPS + Token 双限流、并发上限、超时、重试风暴防护
- 成本与观测：token 计数（含缓存命中、推理 token）、单价表、成本归因到「用户/皮肤/会话」、审计日志、Prompt 与响应留痕及合规脱敏
- 缓存：精确缓存 + 语义缓存（可省 20%~50% 成本）
- 坑：**token 计数口径必须与供应商账单一致**，否则计费永远对不上账

### L5 计量与计费（Metering & Billing）
- 三种口径并存：订阅（月费）/ 买断（单个皮肤）/ 用量（token、点数、对话轮次）
- 预授权 → 冻结 → 结算 → 释放（防止欠费跑单）
- 幂等键、双录记账（double-entry，append-only 流水 + 余额派生）、对账、退款、发票
- 分账（若开放创作者上传）
- 坑：钱的部分**不要**随手写 `UPDATE balance = balance - x`；必须 append-only 流水，余额由流水派生，否则查不出差异

### L6 交易与支付
- 订单 / 支付单 / 退款单、回调验签、主动查单兜底
- 渠道：微信支付、支付宝（国内）；Stripe / Paddle（海外）
- 坑：支付回调必须幂等 + 定时查单补偿，否则掉单

### L7 身份、权限与风控
- 用户身份：文档里是「会员编码 + 抖音ID」= 弱凭证（见 §4 P0-4）
- 后台：RBAC + 操作日志（文档已提）
- 防刷：注册 / 登录 / 解锁 / LLM 调用 四道限流；设备指纹；Geo / UA 风控
- 坑：会员码即凭证 → 一人泄露，全网可用

### L8 内容、审核与合规
- 上传审核（机审 + 人审）、版权/侵权、AIGC 生成内容标识
- **国内落地关键路径**：生成式 AI 服务备案、ICP 备案/ICP 许可证、等保、未成年人保护、内容安全
- 坑：文游 = UGC 皮肤 + AI 生成文本，是**双重**内容风险；备案是工期关键路径，不能上线后再补

### L9 平台工程（让"高并发 / 快速部署 / 稳定安全"成立的那一层）
- 部署：容器化 + IaC + 一键环境；CI/CD；灰度与回滚
- 可观测：Metrics / Logs / Traces + 告警 + 业务大盘（解锁成功率、网关 P99、每用户成本、毛利）
- 数据面：OLTP（Postgres）+ 缓存（Redis）+ 分析（ClickHouse）+ 对象存储（S3/MinIO）+ 搜索
- 安全：密钥管理、WAF、签名验签（文档已提）、审计
- 容量：CDN 扛皮肤下载，网关扛 LLM 调用，DB 只扛交易与授权

## 4. 文档里必须提的问题（按严重度排序）

### P0-1【套利漏洞】向上取整 → 订阅 1 天 = 白得 1 个永久产品
`可解锁产品数 = 已订阅天数 ÷ 30 向上取整`，配合规则 5「已解锁产品永久可用、不再校验会员状态」：
**只要订阅 1 天，就能解锁 1 个产品并永久使用。**
- 建议：改为 `floor(已订阅天数 / 30)`；或设最小解锁门槛（≥30 天才解锁第 1 个）；或以「到期时间 − 开通时间」精确计算并做门槛校验。
- 文档示例 435 天 → 15 个（14.5 进位）就是这个问题。

### P0-2【商业模型自相矛盾】"月费订阅"的预期 + "一次买断"的体验
背景说"按月购买、充几个月解锁几个"（持续付费），规则 5 说"已解锁永久可用、不再校验会员状态"（一次买断）。
用户充 3 个月拿 3 个永久产品后即可停订 → LTV 断崖 + 退款/客诉。
- 建议二选一：(a) 解锁 = 永久买断，那定价按买断定；(b) 解锁 = 租用，会员过期后已解锁产品转"只读/暂停"，续费恢复。
- 折中方案：历史版本永久可用，**新版本**需续费或重新解锁才可升级。

### P0-3【并发一致性】解锁的原子性没写
高并发下双击/脚本会超解锁，必须：
- `UNIQUE(member_id, product_id)` 唯一索引，天然防重复解锁；
- 条件更新（CAS）：`UPDATE member SET unlocked_count = unlocked_count + 1 WHERE id = ? AND unlocked_count < available_count AND status = 'valid'`，按影响行数判断成功；
- 或 `SELECT ... FOR UPDATE` 行锁 + 事务；再配 Redis 分布式锁（幂等键 = 请求 ID）。
- 解锁记录表写入必须在同一事务内。

### P0-4【身份凭证太弱】防篡改清单漏了这一条
「会员编码 + 抖音ID」是两个可猜测、可截图转发的字符串；加上"登录态长期保留 + 支持多设备"，等于一次泄露全网可用。
- 建议：绑定手机号验证码 / 首次登录绑定设备指纹 / 限制同时在线设备数 / 异常登录告警 / 敏感操作二次验证。

### P0-5【失败记录被刷】失败也要写记录 = 被恶意刷爆
"超额解锁 / 已下架 / 已过期"都写失败记录，攻击者循环调用即可产生海量脏数据。
- 建议：失败记录加限流 + 按（会员, 产品, 原因）做窗口合并/采样，或失败记录单独冷表。

### P1-1 派生字段满天飞
开通时间、可解锁产品数、已解锁数量、剩余可解锁数、会员状态 5 个都是"计算字段"，同一公式在文档里描述了 6 遍。
- 建议：**单一写入口 + 落库物化**（任何写操作走同一个 recalc 函数），避免多处实现公式写歪；并只读视图对外。

### P1-2 "未生效"状态没有 UX 定义
状态三态（有效/已过期/未生效）判断依赖服务端时间，但"未生效"用户看到什么？能不能登录？需要明确。

### P1-3 运营手改已解锁产品会让两张表对不上
解锁记录表存的是快照，运营手删/手增后，"已解锁数量"与记录表推演值不一致。
- 建议：解锁记录表加 `source` 字段（user / official_add / official_remove），运营改动也落一条记录，否则日后对不了账。

### P1-4 产品下架后已解锁用户还能不能用？
文档只说"前端不展示入口"。用户有书签/存了 URL 怎么办？后端拦不拦？
- 建议：明确写进接口契约——"下架 ≠ 停服"：已解锁仍可访问，仅列表不展示（或明确停服并通知）。

### P1-5 "请求加签名"防不住逆向
若签名密钥打包进前端，签名等于没有。
- 建议：真正的校验全部在后端 + 服务端会话；前端签名只作为"提高脚本小号成本"的辅助手段（动态 nonce + 时间窗 + 设备指纹），不要当作核心防线。

## 6. 硬约束清单（会直接淘汰候选项目）

- [ ] 支持流式（SSE / WebSocket），且反向代理与网关**不能缓冲**响应
- [ ] 支持 Token 级限流与用量事件产出（不只是 QPS）
- [ ] 支持多供应商 + 故障转移 + 配额/预算
- [ ] 计费可幂等、可对账、可退款（append-only 账本）
- [ ] 静态资源可签名鉴权后交给 CDN（防盗链）
- [ ] 有 RBAC + 审计日志（合规必备）
- [ ] 早期能单机 Docker Compose 一键起，后期能平滑上 K8s（不能一步到位上重架构）
- [ ] 可观测性齐（Metrics/Logs/Traces）且能定位"某次调用花了多少钱"

## 7. 第 2 轮候选池预览（**只是候选，不是结论**）

按 §5 的变量定下来之后，我会逐个按「多租户计费能力 / 性能 / 开源协议 / 可观测 / 国内适配 / 维护活跃度」打分：

- **LLM 网关**：LiteLLM、New-API / One-API、Higress AI Gateway、Apache APISIX（ai-proxy）、Kong AI Gateway、Portkey Gateway、Envoy AI Gateway、Bifrost
- **用量计费账本**：Lago、OpenMeter、Kill Bill，或自研 append-only ledger（Postgres）
- **商城内核**：Medusa、Vendure、Saleor，或自研 headless（数字商品其实不需要重型电商）
- **对话 UI 运行时**：assistant-ui、Vercel AI SDK、CopilotKit、Lobe Chat、Open WebUI + 自研 Skin Spec 渲染器
- **叙事引擎**：ink、Yarn Spinner，或自研状态机（中文文游通常要自研）
- **基础设施**：Postgres + Redis + ClickHouse + MinIO/S3、Coolify / Dokploy / K3s、Keycloak / Zitadel / Casbin、OpenTelemetry + Grafana/Sentry
- **支付**：微信支付 / 支付宝（国内）、Stripe（海外）
