## 0. 先说一个必须提前拍板的法律问题：AGPL 浓度过高

这个领域最流行的几个项目（New-API、Lago）都是 **AGPL-3.0**，New-API 还额外附加了 Section 7 条款。这意味着：

- 你若**修改**它们并对外提供网络服务，你的修改**必须开源**；
- New-API 的附加条款还要求：修改版必须保留 `Frontend design and development by New API contributors.` 署名，并在界面上保留指向原项目的可见链接；
- New-API README 自己就写明：**作为公开生成式 AI 服务 / API 转卖服务运营前，需先完成备案、许可、内容安全、实名、日志留存、税务与上游授权**（这与你"国内为主"的落地路径直接冲突风险）。

**结论**：AGPL 项目可以用，但只用在"**独立进程 + 只通过 API 调用 + 不做二次修改**"的位置，或直接采购商业授权。**所有需要长期深度定制、且承载你商业模型的核心模块，一律选 Apache-2.0 / MIT。**

## 2. 皮肤形态：我的结论 —— 分两档，v1 只做「声明式」

这是整个项目最重要的一个技术决策，比选哪个网关重要得多。

### 2.1 Tier-1（v1 必须）：声明式皮肤

皮肤 = **一份带版本号的 JSON（Skin Spec）+ 可选的作用域 CSS + 静态资源清单**，不允许任意 JS。

Skin Spec 建议包含：

| 分组 | 内容 |
|---|---|
| `meta` | skinId、版本号、作者、名称、预览图、宿主兼容版本区间 |
| `tokens` | 颜色 / 字号阶梯 / 行高 / 间距 / 圆角 / 阴影 / 动效曲线（时长、缓动） |
| `layout` | 多轮对话的版式槽位：消息列表方向、气泡形状与对齐、头像位、时间轴、分组折叠、流式光标、输入区布局、工具调用卡片、引用块、系统提示条 |
| `components` | 允许替换的组件映射表（白名单枚举，不是任意组件） |
| `assets` | 字体、贴图、背景，带哈希与体积上限 |
| `compat` | 支持的能力开关（如是否支持多模态、是否支持工具调用渲染） |

**为什么够用**：「多轮对话式 UI Layout 的美化」本质上是 **token + 槽位 + 组件映射** 问题，而不是「任意代码」问题。气泡形态、布局方向、流式呈现、引用卡片、输入区结构，全都能用声明式描述。

**为什么必须是这个**：
1. **XSS / CSS 逃逸面归零**，可用 Shadow DOM 做主文档内隔离；
2. **审核自动化**：JSON Schema 校验 + 资源扫描即可机审 90%，人工只审美术与合规；
3. **上架速度**：创作者改一行 JSON 就能出皮肤，不需要你 review 代码；
4. **换肤不炸宿主**：宿主升级不会因为皮肤里的 JS 而白屏；
5. **性能可预测**：皮肤包体积、渲染成本可静态估算，直接对应 CDN 与带宽预算。

### 2.2 Tier-2（v2 再开）：受限 JS 沙箱

只有当创作者明确要求"自定义交互动效/自定义组件"时才开，且必须：
- 独立 **domain** 的 iframe + `sandbox="allow-scripts"`（不给 `allow-same-origin`）；
- 宿主 ↔ 皮肤只通过 **postMessage RPC**，能力白名单（能不能读会话内容、能不能发请求、能不能存本地）；
- 主站 CSP `frame-ancestors` / `connect-src` 严格收敛；
- 人工审核 + 代码扫描 + 运行时超时熔断。

**明确不建议 Tier-3（微前端应用包 / qiankun / Wujie / micro-app）**：皮肤是"外观资产"不是"业务应用"，上微前端等于把审核、性能、稳定性成本翻倍，而收益只是"极少数创作者的极端表现欲"。

### 2.3 防拷贝的实话

无论哪一档，**前端能拿到的资产一定能被复制**。所以皮肤的防盗版只能靠：
账号绑定（license 绑定会员 + 设备指纹）+ 服务端签名下发 URL + 关键资源运行时校验 + 水印（含隐形水印便于追责）+ 持续更新（旧版本不再维护）。

**不要把预算花在"技术防盗"上，要把预算花在"账号绑定 + 更新节奏"上。**

## 3. AI 网关选型：三层拆分，而不是选一个"大而全"

你们要同时支持"平台统一采购"和"用户自带 Key"，且团队 Java 强、要国内落地。我的建议是**把 AI 流量拆成三层职责**，各层选最合适的：

### 3.1 推荐组合

| 层 | 职责 | 推荐 | 许可证 | 理由 |
|---|---|---|---|---|
| **入口网关**（南北向） | TLS、鉴权、限流、WAF、路由、灰度 | **Apache APISIX** 或 **Higress** | Apache-2.0 | 两者都成熟；见下方取舍 |
| **AI 专用网关** | 多供应商适配、Token 限流与配额、故障转移、语义缓存、内容安全 | **Higress AI 网关** | Apache-2.0 | 一键 Docker 部署、控制台可视化配置消费者/配额/限流、内置 DeepSeek/通义/豆包/Azure/OpenAI、自带 AI 监控面板（输入输出 Token / 消费者用量） |
| **业务侧模型编排** | 提示词模板、会话上下文组装、BYOK 解密透传、成本归因、计量事件产出 | **自研 Java 服务（Spring Boot）** | — | 这部分和会员/皮肤/额度强耦合，任何网关都给不了你，必须自研 |

### 3.2 Higress vs APISIX vs ShenYu：怎么选

| 维度 | Higress | APISIX | ShenYu |
|---|---|---|---|
| 语言 | Go / Envoy | Lua / OpenResty | **Java** |
| AI 场景成熟度 | ★★★★★（官方级场景文档：多模型代理、语义缓存、应用安全、Token 管理） | ★★★★（ai-proxy-multi / ai-rate-limiting / ai-prompt-guard / ai-rag） | ★★（AI 插件较新） |
| 团队可二次开发 | 需要 Go / Wasm | 需要 Lua | **Java，你们最强** |
| 部署速度 | ★★★★★（`curl install.sh \| bash` 一键 + 控制台） | ★★★★（Helm/Docker） | ★★★（依赖 Admin + 注册中心） |
| 国内生态 | 阿里云，商业化支持 | 国内案例最多 | 国内 Java 微服务圈 |
| Token 配额 / 限流 | 原生插件（Redis 存储 + 控制台配置 + 观测面板） | 原生插件 | 需自研 |

**我的建议（给你团队的具体路径）**：

- **起步用 Higress AI 网关**：一周内就能有"多模型 + Token 配额 + 用量面板"，满足 M3 的上线需求，团队不必先啃 Lua 或 Go。
- **同时用 Apache ShenYu 做业务侧南北向入口**（如果你们已有 Java 微服务体系），因为它是 Java，团队能改、能加自定义鉴权与业务插件。
- **两者不要叠三层**：要么 ShenYu(入口) → Higress(AI)，要么 APISIX/Higress 同时承担入口与 AI，**绝不要 APISIX + Higress + ShenYu 三个一起上**。
- **New-API 只用做内部工具**（多模型对比测试、临时渠道管理），**不作为对外计费权威源**——AGPL + 附加条款 + 与自研会员体系形成两套用户两套账。
- **LiteLLM 只用做开发期统一 SDK / 评测**，团队 Python 弱，不进生产关键路径。

### 3.3 "平台采购 + BYOK" 双模式怎么落

| 模式 | 平台侧 | 网关侧 | 计费侧 |
|---|---|---|---|
| 平台采购 | 平台持有供应商 Key，进渠道池 | 用虚拟 Key 发给用户，走平台渠道 + 负载均衡 | 按 Token 计量 → 扣点数/额度 |
| BYOK | **信封加密**存储用户 Key（KMS 主密钥 + 数据密钥），只在内存解密 | 按 user 维度选用户私有上游凭证 | 平台不收模型费，但仍**计量**（用于限流、防滥用、成本画像） |

关键点：
- BYOK 的 Key 必须**不可逆加密 + 不可回显**，日志与链路追踪都要脱敏；
- BYOK 用户要签免责（上游封号/欠费/条款风险自担）；
- **计费系统必须能区分这两种模式的用量**，否则对账一定乱。

## 4. 其余各层选型

### 4.1 计费账本：自研 append-only ledger（Postgres），OpenMeter 备选

**不推荐 Lago 做核心账本**：AGPL-3.0 + Ruby + 支付渠道只有 Stripe/Adyen/GoCardless（**没有微信/支付宝**），国内落地要绕过它的收款编排，性价比低。

**推荐自研最小双录账本**（这块代码量不大，但必须一开始就写对）：

```
wallet            -- 余额快照（由流水派生，不可手工改）
ledger_entry      -- append-only 流水：user_id, biz_type, amount, ref_id, idempotency_key(UNIQUE), created_at
usage_event       -- Token 用量事件（按月分区）：request_id, user_id, skin_id, provider, model, input_tokens, output_tokens, cache_tokens, unit_price, cost
reconcile_job     -- 与供应商账单按日核对
```

铁律：
1. **余额只能由流水派生**，禁止 `UPDATE balance = balance - x` 这类就地改；
2. 所有扣费必须带 **idempotency_key 唯一索引**；
3. 先**冻结/预授权**再结算，防止欠费跑单；
4. 若引入创作者分账，再加 `settlement` / `payout` 两张表，同样 append-only。

**什么时候引入 OpenMeter（Apache-2.0）**：当计费维度膨胀到「多指标 × 阶梯 × 承诺量 × 多币种」时，用 OpenMeter 承接"计量"层，你的账本只管"钱"。M1–M3 阶段自研足够。

### 4.2 商城内核：不上重型电商，自研 headless

Medusa（MIT）/ Vendure（MIT）/ Saleor（BSD-3）都是为**实物 SKU + 库存 + 物流 + 多供应商**设计的。你们的商品是**零库存数字资产**，交付动作 = "写一条 entitlement 记录"。

引入它们的代价：多一套商品/购物车/结算概念 + 一套平行用户表，还要和文档里的「会员编码 + 抖音ID + 解锁」体系做双向同步 → **复杂度大于收益**。

**推荐自研**：`product` / `skin` / `skin_version` / `order` / `payment` / `entitlement` / `unlock_record`。

只有当你们确定要做「开放创作者上传 + 复杂营销（优惠券/拼团/订阅计划/分账）」时，再评估 **Vendure**（TS，插件化最好，团队 TS 若能引入）。

### 4.3 后端主干：Spring Boot 3 + Java 21，模块化单体起步

团队 Java 最强，就不要在主干上分散精力：

| 关注点 | 选型 | 备注 |
|---|---|---|
| 框架 | Spring Boot 3.x（Java 21） | 模块化单体，按 `member / unlock / catalog / order / ledger / skin / admin` 分包 |
| ORM | MyBatis-Plus（国内团队主流）或 JPA | 复杂统计用 MyBatis 更顺 |
| 数据库版本化 | **Flyway** | 强制所有 schema 变更走迁移脚本 |
| 认证 | **Sa-Token**（国内 Java 生态、中文文档、轻） | Keycloak 对本场景过重 |
| 分布式锁 / 限流 | **Redisson** | 解锁幂等、额度扣减用得上 |
| 模型调用适配 | **Spring AI** 或 **LangChain4j** | Java 侧统一协议、Tool Calling、BYOK 适配 |
| 后台管理 | **Ant Design Pro**（若 React）或 **vue-vben-admin**（若 Vue） | **不要自己写运营后台的 CRUD**，文档里 4 个后台页面直接套模板 |

**不建议**用 NestJS / Node 做主干：团队栈不匹配，且解锁与计费的事务一致性在 Java 侧更稳。

### 4.4 前端：Next.js 或 Nuxt，二选一取决于现有前端能力

| 场景 | 推荐 | 理由 |
|---|---|---|
| 团队有 React 经验 | **Next.js（App Router）+ TypeScript + Tailwind + shadcn/ui** | 生态最大，皮肤预览器与商城都需要 SSR/SEO |
| 团队无 React 经验（只有 Vue/jQuery） | **Nuxt 3 + Vue 3 + Tailwind + Element Plus** | 国内中文资料多、上手最快，别再让团队为框架分心 |

**对话 UI 组件层**：参考 **assistant-ui（MIT）** 的消息流/流式/工具调用渲染抽象，以及 **Vercel AI SDK** 的流式协议设计；但**产品骨架必须自研 Skin Renderer**——因为你的核心资产是"皮肤体系"，套用别人的默认 UI 等于放弃护城河。

### 4.5 文游叙事引擎：自研状态机，ink/Yarn 只作 DSL 灵感

- **ink（MIT）**：纯分支叙事的优秀 DSL，但没有 LLM 介入点；
- **Yarn Spinner（MIT）**：对话树优秀，同样面向"预先写好的内容"；
- AI 文游 = **LLM 生成 + 状态机约束 + 存档回档 + 变量系统**。建议在 Java 侧自研轻量状态机，把 ink / Yarn 的语法当设计参考，不要直接引依赖（会带来跨语言/跨运行时负担）。

### 4.6 基础设施

| 层 | 选型 | 备注 |
|---|---|---|
| 对象存储 | **阿里云 OSS / 腾讯云 COS** | 自建请规避 MinIO（AGPL 社区版商用有争议）；自建备选 Garage / RustFS / Ceph |
| CDN | 云厂商 CDN + **签名 URL 防盗链** | 皮肤包按 `/{skinId}/{version}/` 不可变路径发布 |
| 主库 | PostgreSQL 16 | 授权、订单、账本 |
| 缓存 | Redis 7 | 限流、锁、会话、配额 |
| 分析库 | **ClickHouse** | Token 用量、网关日志、成本画像（Higress/APISIX 均可直出） |
| 搜索 | Meilisearch / Typesense | 皮肤搜索，Postgres 全文起步也行 |
| 部署 | 早期 **Docker Compose + Dokploy/Coolify** → 中期 **K3s** → 阿里云 ACK / 腾讯 TKE | 不要一上来就 K8s |
| 可观测 | OpenTelemetry + Prometheus + Grafana + Loki/Tempo + Sentry | 大盘必须含"每用户成本/毛利" |
| 内容安全 | **阿里云内容安全 / 腾讯天御** | 国内合规场景不建议自建审核模型 |
| 支付 | **微信支付 V3 + 支付宝**，自研订单/回调/对账 | 不用第三方聚合支付当核心账本 |

## 5. 国内合规：这是工期关键路径，不是上线后补的

因为你们选了"国内为主 + 面向公众提供生成式 AI 服务"，以下事项会直接决定能不能上线：

1. **ICP 备案**（网站本身）；若涉及经营性收费 → ICP 许可证 / EDI；
2. **生成式 AI 服务备案 / 算法备案**：向公众提供生成式 AI 服务需按《生成式人工智能服务管理暂行办法》完成备案；上游模型若已备案（DeepSeek / 通义 / 豆包），你作为应用层通常需完成算法备案/登记；
3. **AI 生成内容标识**：《人工智能生成合成内容标识办法》要求显式 + 隐式标识 → 文游输出必须带标识；
4. **实名制 + 日志留存**（不少于 6 个月）+ 投诉举报入口 + 未成年人保护；
5. **上游模型 ToS**：转卖 API 额度可能违反供应商条款 → 必须签商务合作/授权，或自建/私有化模型。这一条是"平台统一采购"模式的**法务前置条件**，不是技术问题。

**排期建议**：把 1–3 项的申报工作放在 M1 就启动，与开发并行；否则 M3 做完也上不了线。

## 6. 最终推荐组合（按里程碑）

### M1 — 会员与解锁（约 2–3 周，先不碰大模型）
- 后端：Spring Boot 3 + Java 21 + MyBatis-Plus + Flyway + PostgreSQL + Redis + Sa-Token
- 前端：Next.js 或 Nuxt（商城 + 登录 + 产品选择）
- 后台：Ant Design Pro / vue-vben-admin（套模板）
