# 叩君芯会员产品网站 · 第 3 轮架构讨论
## 读完《分手结局修改器 v2》与《小手机》之后：架构重估与新增选型

> 新增输入条件：
> 1. 文游 = 《分手结局修改器》《小手机》这类"AI 驱动的手机模拟叙事游戏"
> 2. **所有内容由平台自营，用户只能使用，不能上传** → 无 UGC 创作者生态
> 3. 网站要提供**游戏框架 + 后台服务**
> 4. 要**分段式披露**，防止前端 UI 设计泄露
> 5. 一部分 AI 响应设计（如人设生成）**整合到后端**
> 6. 后台管理员提供**上传接口 + 规范文档**，按规范打包素材与前端后上架
>
> 本文档基于对两个项目的实际代码阅读（非推测）。许可证标注为「已核实」的通过 GitHub License API 实测；新增候选标注「待核实」。

## 0. 我实际读到了什么（这是本轮所有建议的依据）

### 0.1 《分手结局修改器 v2》现状

| 事实 | 位置 | 影响 |
|---|---|---|
| 纯静态站，部署在 Cloudflare Pages | `_headers` / `_redirects` | **国内访问不稳，与"国内为主"直接矛盾** |
| **System Prompt 全文在前端**，包含 `c.truth`（隐藏真相）、人物档案（外显/内在/成因/说话方式）、"痛感标准"、伏笔设计规则 | `js/system-prompt.js` (7.6KB) | **核心创作方法论完全暴露**，F12 就能抄走 |
| 全部剧情数据在前端 | `js/data/asphyxia.js` (33KB) + `phone-life.js` (33KB) + `couples.js` | 剧透 + 可整体扒站 |
| PACK/STATE 协议解析、校验、应用全在前端 | `js/protocol.js` (578 行) | `validateEditPack` 在前端可绕过；改逻辑必须重发前端 |
| 用户自填 API Key，前端直连 `api.deepseek.com` | `js/api.js` | 无法做平台计费；Key 存本地 |
| 游戏状态存 localStorage | `STORAGE_KEY = 'breakup_editor_v4pm'` | **与需求文档"多设备同步"要求直接冲突**；存档可改；换设备丢档 |
| UI 逻辑 109KB 单文件 | `js/ui.js` | 不可分段加载，首屏压力大 |

**但同时要肯定**：这个项目的协议设计（消息级重演边界 `computeReplayBoundary`、PACK 的 KEEP/REPLACE 语义、`buildReplayPackFromOriginal` 作为不依赖 AI 的硬兜底）**质量相当高**，这是可以沉淀成平台资产的。

### 0.2 《小手机》现状

| 事实 | 位置 | 影响 |
|---|---|---|
| 单文件 HTML 287KB，PRD 明确"交付物为单一 html 文件" | `小手机01.html` | 无法分段披露、无法按需加载 |
| 人设 prompt 明文存 localStorage | `char.prompt` | 用户人设可被导出/共享 |
| AI 指令靠正则解析 `[REDPACKET:金额:祝福语]`、`[ORDER_FOOD:...]`、`[MOVE:行:列]` | 内联在 HTML | 模型一变格式就崩；无 schema 校验 |
| 状态存 localStorage `mengnv_phone_v2`，超 4MB 预警 | 内联 | 存档上限低、不可迁移 |
| 用户自填 Key + 自定义模型 ID | `STATE.apiKey` | 面向用户的门槛：PRD 写"用户能注册 DeepSeek 获取 API 密钥" |

### 0.3 关键发现：《小手机》的问题单，根因全是架构

`主界面等问题(1).docx` 里记录的真实缺陷，逐条看根因：

| 产品问题 | 真实根因 |
|---|---|
| "上下文衔接有问题，不记得前面聊过的内容" | 上下文组装在前端，没有服务端摘要压缩 |
| "语音消息重复回复一样的内容，跟上下文割裂" | 从前端已有回复里抽一条口语化文案，没有服务端二次生成 |
| "点外卖/购物/发红包触发条件太死板人机" | 触发判定是前端关键词匹配，不是服务端多轮意图判定 |
| "相册图片图文不一致，太出戏" | 用 `picsum.photos` 随机图，没有语义绑定 |
| "朋友圈没按时间排序 / 看不到角色新发朋友圈 / 评论时机不对" | 缺服务端调度器，无法做**延迟触发** |
| "聊天后不自动记备忘录" | 缺服务端事件钩子 |
| "返回机制迷幻，要回退很多次" | 前端导航栈实现问题（这个确实是前端问题） |

**结论：产品的迭代瓶颈已经出现了，而瓶颈不在 UI，在于"AI 编排 + 状态"被放在浏览器里。** 这直接支撑你要的"AI 响应设计整合到后端"。

## 1. 核心结论：把"游戏"重构成三层

```
① 平台运行时 Platform Runtime   ← 平台拥有，永不下发给游戏包
   手机外壳 / 锁屏 / 桌面 / 导航栈 / 状态栏
   通用 App 容器：聊天 · 朋友圈 · 相册 · 备忘录 · 钱包 · 音乐 · 小游戏
   皮肤渲染器（读 Skin Spec / Layout Spec）
   沙箱宿主（Form B 接入的游戏跑在这里）

② 游戏内容包 Content Pack        ← 管理员上传，进对象存储 + CDN
   manifest + 主题 tokens + 布局描述 + 素材 + 剧情数据

③ 服务端大脑 Server Brain        ← 平台后端，游戏包看不到
   AI 编排 / prompt 版本库 / 结构化输出校验 / 会话状态 / 内容按节点下发 / 计量计费
```

**一句话**：让「具体游戏」变成数据，「游戏引擎」变成一号产品。

## 2. 关于「分段式披露」：先纠正认知，再给可落地方案

### 2.1 必须承认的上限

**只要浏览器要渲染，代码和样式就必然在客户端。绝对防拷贝不存在。** 混淆、加密 loader 都只是把成本从"5 分钟"提高到"几天"，不能阻止有决心的人。

《小手机》是单文件 HTML —— 扒站成本约等于"另存为"。这是现状。

### 2.2 真正有效的三件事（按 ROI 排序）

| 优先级 | 手段 | 为什么有效 |
|---|---|---|
| **P0** | **Prompt / 人设 / 叙事规则 100% 服务端化** | 前端再也拿不到 `truth`、痛感标准、伏笔设计。这**不是"提高扒站成本"，而是"根本拿不到"** —— 因为客户端只收到流式文本结果。这是收益最大的一条 |
| **P0** | **内容按节点/进度服务端下发** | 服务端只返回"玩家已到达的节点"。未到达的内容**根本不下发**。这才是真正意义上的"分段"，同时解决剧透 |
| **P1** | **UI 结构声明化：平台渲染器 + 游戏包只交数据** | 到这一步，"前端设计泄露"这个问题基本被消解 —— 因为游戏包里**没有前端设计**，只有 token / 布局描述 / 素材 |

### 2.3 分级手段清单

| 级 | 手段 | 效果 | 成本 |
|---|---|---|---|
| L0 | 构建压缩 + 混淆 + 不上 sourcemap + 禁目录索引 | 低 | 极低 |
| L1 | 路由/场景级 code splitting，素材按需加载 | 低 | 低 |
| L2 | 素材短时效**签名 URL** + 用户**隐形水印**（泄露可追溯） | 中 | 低 |
| **L3** | **UI 布局用 JSON 描述、由平台渲染器渲染** | **高（性价比拐点）** | 中 |
| L4 | 关键样式/字体子集服务端动态下发 | 中 | 中 |
| L5 | 远程渲染串流（neko / Selkies，WebRTC 推视频流） | 理论最高 | **极高** |

**L5 我明确不建议**：文字对话类游戏用视频串流，延迟、带宽、并发成本全部爆炸，用户体验还变差。这是"用大炮打蚊子"。

**我的结论：做到 L3 就够了。** 到 L3，游戏包里只有数据与素材，没有可独立还原的 UI 设计。

## 3. 两种游戏接入形态（这是给管理员规范的核心分野）

### Form A：平台托管（**推荐**，新游戏走这条）

游戏方只交：**素材 + 主题 tokens + 布局描述（JSON）+ 剧情内容 + 服务端 AI 配置**，**不交前端代码**。

- 平台渲染器负责渲染，用的是平台的通用手机外壳与 App 容器
- 防泄露最好（L3），审核最快（schema 校验可机审）
- **管理员不需要会写前端** —— 这对运营效率是决定性的
- 适合：《小手机》这种"标准手机模拟器 + 换人设换剧情"的游戏

### Form B：沙箱自渲染（兼容现有游戏，过渡用）

游戏方交：**构建好的前端 dist + manifest**，跑在**独立域名 iframe** 里。

- 必须先做 P0 两件事（prompt 服务端化 + 内容服务端化），否则沙箱只是把 HTML 挪个位置
- 强制通过平台 SDK 调 AI，禁止直连模型
- 适合：《分手结局修改器》这种有大量定制 UI 与协议逻辑的游戏

### 两种形态的共同铁律

1. **AI 调用必须走平台 SDK**，不可自行直连任何模型（这是计费、计量、内容安全、成本归因的底线）
2. **禁止外链**任何第三方 CDN/接口
3. **不得读取宿主 DOM / Cookie / localStorage**（Form B）
4. **存档写入必须经服务端**（防改档、支持多设备同步）

## 4. 服务端 AI 中台：从两个项目抽象出的 7 项通用能力

这就是"一部分 AI 响应设计整合到后端"的具体清单：

| # | 能力 | 现状位置 | 服务端化后 |
|---|---|---|---|
| 1 | **prompt 模板与版本** | `system-prompt.js` 拼字符串 | 服务端模板库 + 语义化版本 + 灰度 + 变量注入（人设/真相/指标） |
| 2 | **人设生成** | 小手机前端 `genStepPrompt` | `POST /ai/persona:generate` → 返回结构化人设 JSON，落库 |
| 3 | **结构化输出** | `«L:...»` 标签 / `[REDPACKET:...]` 正则 | **JSON Schema 强约束**（模型侧 structured output / tool calling）+ 服务端校验 + 失败重试 |
| 4 | **叙事重演与状态机** | `protocol.js` 578 行 | 服务端：解析 → 校验边界 → 应用 → 落库 → 返回结构化 delta |
| 5 | **会话状态与记忆** | localStorage | 服务端权威存储 + 摘要压缩 + **多设备同步** |
| 6 | **事件触发**（红包/外卖/礼物/评论） | 前端关键词判断 | 服务端「回合结束意图判定」+ 可配置触发规则 + 冷却时间 |
| 7 | **延迟任务** | 无 | 服务端调度队列（"不同角色在不同时间评论朋友圈"必需） |

### 一个强烈建议：把自制文本标签协议换成 JSON Schema 强约束

现状 `protocol.js` 用正则 `«([A-Z]+)(?::([^»]*))?»` 解析，模型多一个空格、换个全角符号就崩；`validateEditPack` 只能**事后丢弃**（`packInvalid: '推演结果不完整，未写入改写'`）—— 这是**把模型的不稳定转嫁给用户**。

改成 JSON Schema 后：模型侧约束格式 → 服务端校验 → 不合法就自动重试 → 用户几乎感知不到失败。同时 `[REDPACKET:...]` / `[MOVE:行:列]` 这类**应该改成 Tool Calling**（模型调用 `send_redpacket(amount, message)` 工具），比正则健壮一个数量级。

## 5. 新增开源选型

### 5.1 服务端 AI 编排（Java 侧，团队最强）

| 项目 | 语言 | 许可证 | 用途 |
|---|---|---|---|
| **Spring AI** | Java | Apache-2.0（待核实） | Spring 原生集成、结构化输出、ChatMemory、Tool Calling、多模型抽象 |
| **LangChain4j** | Java | Apache-2.0（待核实） | 同上，生态更偏中文社区，AI Service 抽象好 |
| **Langfuse** | TS/Python | 核心 MIT + `ee/` 另有许可（**待核实**） | **prompt 版本管理 + trace + 成本归因 + 评测**，可自托管 |

**为什么特别推荐 Langfuse**：它同时覆盖你三个诉求 —— prompt 版本化、每次调用的成本归因、调用链审计。而且它是"旁路"的（你的服务端调它 API 上报），不侵入主干，可以很晚才决定要不要上。

> 注意：Spring AI / LangChain4j 二选一即可，**不要都用**。团队 Java 强 + 已用 Spring Boot → 选 **Spring AI**。

### 5.2 声明式 UI 渲染（Form A 的核心）

| 项目 | 许可证 | 评价 |
|---|---|---|
| **amis**（百度） | Apache-2.0（待核实） | JSON 配置驱动 UI，"服务端下发配置、前端渲染"模型天然契合分段披露 |
| **Alibaba LowCode Engine** | MIT（待核实） | 低代码引擎，适合做**可视化搭建后台**，偏重 |
| **Formily**（阿里） | MIT（待核实） | 表单/布局 schema |

**但我的建议是：自研轻量 DSL，不直接套 amis。**
理由：手机模拟器的界面（桌面/微信/朋友圈/相册）是**高度定制的固定布局**，通用低代码引擎的表达力和体积都不划算。你们已有的 `«PACK»` 协议其实就是个好 DSL 雏形，把它结构化 + 用 **JSON Schema** 做校验校验就够了。amis / LowCode Engine 的价值在于**给运营做可视化搭建**，那是 M4 再考虑的事。

补充：动效走 **Lottie（MIT，待核实）/ Rive** 这类 JSON 描述，既小又难以直接还原为设计稿。

### 5.3 沙箱（Form B）

| 方案 | 评价 |
|---|---|
| ❌ qiankun / Wujie / micro-app | **不要用**。微前端解决的是"多子应用共享主应用状态"，而你要的是"隔离"，方向相反 |
| ✅ **独立域名 iframe + `sandbox` + CSP + postMessage** | 正确方案。自己写个薄 SDK 约 300~500 行 |
| 可参考 **Penpal** | MIT（待核实），成熟的 postMessage RPC 库 |

关键：游戏包域名必须是**独立子域**（如 `game-xxx.koujunxin.com`），才能阻断对主站 Cookie / localStorage 的访问。同域 iframe 隔离是假的。

### 5.4 存档与内容分段（服务端权威状态）

| 方案 | 许可证 | 评价 |
|---|---|---|
| **自研：Postgres JSONB + Redis** | — | **推荐**。文字游戏的"存档"= 一张 `game_save` 表 + JSONB 快照 + 版本号。完全够用 |
| **Nakama**（Heroic Labs） | Apache-2.0（待核实） | 开源游戏后端（账号/存档/排行榜/匹配/Lua 运行时）。能力强，但会与你自己的会员体系形成**两套账号** |
| **Colyseus** | MIT（待核实） | 实时多人游戏服务器。**文字游戏不需要** |

**结论：文字叙事游戏不上游戏服务器框架。** 自研 JSONB 存档 + 延迟队列足够；只有将来做实时多人对局才考虑 Colyseus。

### 5.5 延迟任务 / 事件调度（朋友圈"不同时间评论"必需）

| 方案 | 许可证 | 评价 |
|---|---|---|
| **Redis ZSET 延迟队列** | — | **起步首选**，自研 < 200 行，够用 |
| **Temporal** | MIT（待核实） | 工作流持久化执行，Java SDK 一流。业务复杂到"多步延迟 + 补偿 + 重试"时上 |
| **XXL-JOB** | 注意许可证（待核实） | Java 生态定时任务，偏"定时调度"不偏"延迟事件" |

**建议：M1–M3 用 Redis ZSET；出现"跨天延迟 + 多步补偿"需求时上 Temporal。**

### 5.6 素材保护与前端加固

| 手段 | 工具 | 许可证 |
|---|---|---|
| JS 混淆 | **javascript-obfuscator** | BSD-2-Clause（待核实） |
| 关键算法 WASM 化 | Emscripten / AssemblyScript | MIT / Apache-2.0 |
| 隐形水印 | blind-watermark 类库 | 待核实 |
| 素材签名 URL | 云 OSS + CDN 签名（自建） | — |
| 图片 EXIF 剥离 / SVG 脚本检测 | 服务端上传校验时做 | — |

### 5.7 AI 网关与计量（沿用第 2 轮结论，但增加归因维度）

- 网关：**Higress AI 网关**（Apache-2.0 ✅ 已核实）
- 计量账本：**自研 Java append-only ledger**（第 2 轮结论）
- **新增归因维度**：`game_id` + `session_id` + `turn_id` —— 必须能回答"哪个游戏最烧钱""哪一局最贵"

## 6. 管理员上传接口与规范（你要的规范文档骨架）

### 6.1 游戏包目录结构

```
game-package/
├── manifest.json              # 必填
├── theme/
│   ├── tokens.json            # 设计 token（颜色/字号/间距/圆角/动效）
│   └── layout.json            # Form A：布局描述
├── assets/
│   ├── images/  audio/  fonts/
│   └── assets.manifest.json   # 哈希 / 尺寸 / 体积
├── content/                   # Form A：剧情内容
│   ├── nodes.json             # 节点、消息、碎片、指标
│   └── characters.json
├── dist/                      # Form B：构建产物
├── server/                    # ⚠️ 上传后进服务端库，不进 CDN
│   ├── prompts/               # prompt 模板 + 变量声明
│   ├── protocol.schema.json   # 结构化输出 JSON Schema
│   └── triggers.json          # 事件触发规则 + 冷却
└── checksums.json
```

`manifest.json` 必填字段建议：

```json
{
  "id": "breakup-editor",
  "name": "分手结局修改器",
  "version": "2.1.0",
  "form": "A" | "B",
  "runtimeCompat": ">=1.4.0 <2.0.0",
  "entry": "dist/index.html",
  "contentVersion": "2026.09.1",
  "permissions": ["ai.complete", "state.save", "asset.signed"],
  "budget": { "tokensPerSession": 200000, "modelTier": "standard" },
  "audit": { "copyright": "自研", "contentRating": "16+" }
}
```

### 6.2 上传接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/admin/games` | 创建游戏 |
| POST | `/admin/games/{id}/versions` | 创建草稿版本 |
| POST | `/admin/games/{id}/versions/{v}/package` | 上传 zip（multipart） |
| POST | `/admin/games/{id}/versions/{v}/validate` | 干跑校验，返回报告 |
| POST | `/admin/games/{id}/versions/{v}/publish` | 发布（支持灰度比例） |
| POST | `/admin/games/{id}/versions/{v}/rollback` | 回滚 |
| GET | `/admin/games/{id}/versions/{v}/report` | 校验报告 |

服务端上传时必须做：
1. 解包 → manifest schema 校验
2. 体积 / 尺寸 / 数量上限校验
3. **素材安全扫描**：SVG 内嵌脚本检测、图片 EXIF 剥离、禁止外链 URL
4. **禁止 `server/` 目录出现在 CDN 产物中**（这一条是防泄露的命门）
5. 生成 `checksums.json`，写入对象存储
6. 校验 `runtimeCompat` 与当前宿主版本

### 6.3 规范文档必须包含

1. 目录结构与 manifest 字段说明（含版本兼容策略）
2. **内容数据 Schema**（节点 / 消息 / 碎片 / 指标 / 结局）
3. **服务端 AI 配置 Schema**（prompt 变量、结构化输出 schema、触发规则）
4. 素材规范（格式、尺寸、体积上限、命名、版权证明）
5. 平台 SDK API（Form B：`ai.complete` / `state.save` / `assets.sign` / `events.emit`）
6. 安全红线（不得直连模型、不得外链、不得读宿主 DOM）
7. 上架检查清单
8. 版本兼容与迁移策略（宿主升级后旧游戏包怎么办）

### 6.4 一个关键设计：**内容与代码分离**

剧情内容**不要打进游戏包**，放**服务端内容库**（独立的 `contentVersion`）。

收益：改一句台词不用重发前端；内容可按节点分段下发（真正防剧透）；内容可灰度、A/B、单独审核。

## 9. 我最想说的一个战略判断

从这两个项目看，你们真正的资产**不是某一款游戏**，而是两样东西：

1. **叙事 prompt 方法论** —— 《分手结局修改器》里那套"痛感标准 / 口是心非 / 伏笔呼应 / 留白 / 隐藏真相"，写得相当有水准，是可以复用的创作引擎；
2. **"手机模拟器"交互范式** —— 微信 / 朋友圈 / 备忘录 / 相册 / 钱包 / 音乐 / 小游戏 的多 App 联动。

**这两样东西一旦服务端化 + 模板化，你就能用同一套引擎快速产出新游戏 —— 这才是平台的价值。**

反过来，如果继续"每款游戏一个独立 HTML"，你永远在做项目，不是做平台；而且每一款都要从零重写 AI 编排、会话、触发、存档、计费 —— 第 0.3 节那串问题单会在每一款新游戏上重演一遍。

**所以：把「游戏引擎」当一号产品，「具体游戏」当内容。**
