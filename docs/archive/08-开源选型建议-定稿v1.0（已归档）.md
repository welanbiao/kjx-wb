# 叩君芯会员产品平台 · 开源选型建议
## Open Source Technology Selection v1.0

> **选型原则（按你的要求）**
> 1. **尽量不重复造轮子** —— 能用成熟开源的，不自研
> 2. **运维简单** —— 优先"少组件、单进程、无额外中间件"，宁选功能够用的轻量方案，不选功能过剩的重型方案
> 3. 团队 Java 最强，TS 前端可引入，Python 略会
> 4. 国内落地为主，合规优先
>
> **判定维度**：功能匹配度 ｜ 语言与团队栈 ｜ 许可证 ｜ **运维成本** ｜ 社区活跃度 ｜ 国内可用性
>
> **许可证标记**：✅ 宽松（MIT/Apache/BSD，闭源商用无义务） ｜ ⚠️ 有义务（AGPL/GPL/FSL，需评估） ｜ 🔍 待核实
>
> **配套文档**：`04-完整功能规格说明书.md`、`05-功能清单与层级结构.md`、`06-日志与数据留存设计.md`

## 1. 后端主干框架

| 项目 | 语言 | 许可证 | 优点 | 缺点 |
|---|---|---|---|---|
| **Spring Boot 3** | Java | ✅ Apache-2.0 | 生态最全、招人最容易、国内资料最多、与下文所有 Java 库天然兼容 | 启动慢、内存占用大（容器化后无感） |
| Solon | Java | ✅ Apache-2.0 | 启动快（~100ms）、内存小、国产、API 简洁 | 生态小，第三方集成要自己写 |
| Quarkus | Java | ✅ Apache-2.0 | 原生编译、启动快、云原生 | 国内资料少、编译期增强踩坑多 |
| Vert.x | Java | ✅ Apache-2.0 | 高并发、异步 | 编程模型陡峭，团队要重新学 |

**✅ 推荐：Spring Boot 3 + Java 21**

理由：
1. 团队 Java 最强，Spring Boot 是**最不需要学习成本**的选择
2. 本方案里所有 Java 库（Sa-Token / MyBatis-Plus / Redisson / LiteFlow / SMS4J / IJPay / Spring AI / X-File-Storage）**都是 Spring Boot 优先适配**的
3. 启动慢在内网容器化部署下不是问题，且**单体能起就好**——本平台不需要微服务
4. 招人成本：Spring 简历池比 Solon/Quarkus 大一个数量级

**架构建议**：**模块化单体**（按 `account` / `member` / `work` / `tool` / `ai` / `billing` / `log` 分包），**不要微服务**。理由：运维简单是你的原则，微服务会引入注册中心、配置中心、链路追踪、分布式事务四个新问题。

## 2. 认证与权限（RBAC）

| 项目 | 许可证 | 优点 | 缺点 |
|---|---|---|---|
| **Sa-Token** | ✅ Apache-2.0 🔍 | 极轻（一个 jar）、中文文档、30 分钟接入、支持多端登录/踢人/二级认证 | 只管认证授权，不管用户表 |
| Spring Security | ✅ Apache-2.0 | 官方、功能最全、企业标配 | 配置繁琐，学习曲线陡；简单场景杀鸡用牛刀 |
| Keycloak | ✅ Apache-2.0 🔍 | 完整 IdP：SSO/OIDC/SAML/用户联邦/管理台 | 重（Java + Quarkus + 独立库），**运维成本高** |
| Zitadel | ✅ Apache-2.0 🔍 | 现代化、多租户友好、Go 写的很轻 | 国内资料少 |

**✅ 推荐：Sa-Token**

理由：
1. **运维简单**：它只是一个 jar，不是独立服务。Keycloak 要多维护一个 Quarkus 应用 + 数据库，违背你的原则
2. 本平台的账号体系是**自建的**（手机号/邮箱注册），不需要 SSO 联邦能力，Keycloak 的功能 90% 用不上
3. 需求里的"多设备登录 / 踢人 / 会话管理"Sa-Token 原生支持
4. 后台 RBAC 权限点可复用 RuoYi-Vue-Pro 自带的（见 §19）

**注意**：Sa-Token 要配合**服务端会话 + Redis**（不要用 JWT 纯无状态），因为需求里要"设备列表 / 强制下线"。

## 3. 短信 / 邮件 / 站内信

| 项目 | 许可证 | 优点 | 缺点 |
|---|---|---|---|
| **SMS4J** | ✅ Apache-2.0 ✅已核实 | dromara 出品；**一套 API 支持 10+ 厂商**（阿里/腾讯/华为/云片/容联/助通…）；换厂商零改代码；Spring Boot Starter | 只做短信 |
| 各云厂商 SDK 直连 | 商业 | 官方支持 | **厂商绑定**，换厂商要改业务代码 |
| 自研适配层 | — | 完全可控 | 重复造轮子 |
| 阿里云短信 + 腾讯云短信双接 | 商业 | 有冗余 | 两套 API 两套错误码 |

**✅ 推荐：SMS4J**

理由：
1. **正面命中"不重复造轮子"**：短信适配层是典型的重复劳动，SMS4J 已经做好了
2. **正面命中"运维简单"**：纯 jar，无新组件
3. 未来换厂商或加备用通道，只改配置

**邮件**：`spring-boot-starter-mail`（Spring 官方，✅ Apache-2.0）—— 无需第三方。

**站内信**：**自研**（一张 `notification` 表 + Redis 未读计数）。理由：站内信逻辑与本平台权益/绑定强耦合，开源方案（如各类"消息中心"）反而要适配。

## 4. 数据访问与 Schema 迁移

| 项目 | 许可证 | 优点 | 缺点 |
|---|---|---|---|
| **MyBatis-Plus** | ✅ Apache-2.0 | 国内绝对主流、CRUD 零 SQL、分页/逻辑删除/多租户开箱、资料最多 | 复杂 SQL 仍需手写 XML |
| MyBatis-Flex | ✅ Apache-2.0 🔍 | 更轻更快、API 更现代 | 生态与资料少于 MP |
| Spring Data JPA | ✅ Apache-2.0 | 标准、对象化、跨库 | 复杂查询与性能调优坑多，国内团队不熟 |
| jOOQ | ⚠️ 分版本（OSS 版 Apache-2.0 / 商业版） | 类型安全 SQL | 需要商业授权才能用于闭源商业数据库 |

| 迁移工具 | 许可证 | 优点 | 缺点 |
|---|---|---|---|
| **Flyway** | ✅ Apache-2.0 | 简单直接（SQL 脚本）、Spring Boot 原生集成 | 不支持回滚（社区版） |
| Liquibase | ✅ Apache-2.0 | 支持回滚、多格式（XML/YAML/SQL） | 概念多，配置重 |

**✅ 推荐：MyBatis-Plus + Flyway**

理由：MyBatis-Plus 是**国内 Java 团队默认选项**，团队不需要学习成本；Flyway 简单到只需要 `V1__init.sql`、`V2__add_xxx.sql` 这样的文件名，符合"运维简单"。

## 5. 缓存、分布式锁、限流、延迟队列

| 项目 | 许可证 | 优点 | 缺点 |
|---|---|---|---|
| **Redis + Redisson** | ✅ Apache-2.0 | **一个依赖解决 4 件事**：分布式锁、限流器、延迟队列、布隆过滤器；API 高级易用 | Redisson 偏重（但对单体无感） |
| Valkey + Redisson | ✅ BSD-3 | Valkey 是 Redis 的 BSD 分支，**许可更干净** | 生态刚起步 |
| Redis + Lettuce + 自研锁 | ✅ | 轻 | **重复造轮子**，锁写错会出生产事故 |
| Sentinel | ✅ Apache-2.0 | 流量控制/熔断/系统保护强 | 偏"服务治理"，单体项目过重 |

**✅ 推荐：Redis 7 + Redisson**

理由（这条**直接命中"不重复造轮子 + 运维简单"**）：

| 需求 | Redisson 已提供 |
|---|---|
| 解锁/绑定幂等锁 | `RLock` |
| 绑定失败限次、AI 调用限流 | `RRateLimiter` |
| **延迟任务（朋友圈延迟评论、埋雷爆发）** | **`RDelayedQueue`** ← 省掉一整套 MQ/调度系统 |
| 防缓存穿透 | `RBloomFilter` |
| 会话存储 | `RMapCache` |

> **额外收益**：因为 Redisson 已覆盖延迟队列，**M5 的"延迟任务"不需要引入任何新组件**。

**许可提醒**：Redis 7.4+ 改为 RSALv2/SSPL（源码可得但不可商用为托管服务）。**本平台是自用，不受影响**；若在意，可换 **Valkey**（BSD-3，协议完全兼容）。

## 6. AI 网关

| 项目 | 语言 | 许可证 | 优点 | 缺点 |
|---|---|---|---|---|
| **Higress AI 网关** | Go/Envoy | ✅ Apache-2.0 ✅已核实 | 一键 Docker 部署；控制台可视化配消费者/Token 配额/限流；**自带 AI 监控面板**；内置 DeepSeek/通义/豆包/Azure/OpenAI | 二次开发需 Go/Wasm |
| Apache APISIX | Lua/OpenResty | ✅ Apache-2.0 ✅已核实 | 插件生态最广（ai-proxy-multi / ai-rate-limiting / ai-prompt-guard / ai-rag / ai-cache） | 二次开发需 Lua |
| New-API | Go | ⚠️ **AGPL-3.0 + Section 7** ✅已核实 | 开箱即用的额度/计费/多渠道/后台 | **AGPL 义务**：改版必须开源，且须保留其署名与界面链接；与自研会员体系形成两套账号两套账；README 自述"公开转卖需先完成备案授权" |
| LiteLLM | Python | ✅ MIT（`enterprise/` 除外）✅已核实 | 100+ 供应商适配、虚拟 Key、预算、成本追踪 | Python 不进团队主栈；高并发代理非其强项 |
| Bifrost / Envoy AI Gateway / Portkey | Go/TS | 🔍 待核实 | 新一代 AI 网关 | 生态与国内落地案例少 |

**✅ 推荐：Higress AI 网关**

理由：
1. **运维简单**：`curl install.sh | bash` 一条命令起，带控制台。APISIX 需要 Helm/YAML 调优，New-API 要额外维护用户体系
2. **开箱即得**：Token 配额、限流、多模型路由、监控面板全部可视化配置，**M3 一周内能上线**
3. **许可证干净**：Apache-2.0，可自由二次开发与闭源分发
4. 国内生态：阿里云支持，中文文档完善

**为什么不选 New-API**：它的核心卖点是"渠道分发 + 额度计费 + 后台"，这些**你都要自研**（因为要跟会员/绑定/作品权益打通）。用它等于维护两套用户体系和两套账，且背上 AGPL 义务。

**演进路线**：Higress（M3 起步）→ 若需深度定制业务网关，再加 **Apache ShenYu**（Java，团队可改）承担南北向入口。

## 7. AI 编排 SDK

| 项目 | 许可证 | 优点 | 缺点 |
|---|---|---|---|
| **Spring AI** | ✅ Apache-2.0 🔍 | Spring 原生、结构化输出（`BeanOutputConverter`）、ChatMemory、Tool Calling、多模型抽象、Advisor 机制 | 相对新，部分能力仍在追赶 |
| LangChain4j | ✅ Apache-2.0 🔍 | AI Service 抽象优雅、中文社区活跃、工具调用完善 | 概念比 Spring AI 多 |
| Semantic Kernel (Java) | ✅ MIT 🔍 | 微软背书、规划器能力强 | Java 版成熟度低于 .NET/Python |
| 纯 HTTP 手写 | — | 无依赖 | **重复造轮子**，结构化输出/重试/工具调用都要自己写 |

#### 7.1 澄清一个常见误解：Spring AI 不能替代 Spring Boot

> 有同事建议"直接用 Spring AI 代替 Spring Boot"——**这个说法不成立**。二者是**底座与插件**的关系，不是二选一。

```
你的应用
├── Spring Boot 3.x                ← 底座：内嵌容器、自动配置、事务、配置、Actuator
│   ├── starter-web                ← HTTP 接口（登录/绑定/解锁/订单）
│   ├── starter-validation         ← 参数校验
│   ├── Sa-Token / Spring Security ← 认证授权
│   ├── MyBatis-Plus + Flyway      ← ORM 与 schema 迁移
│   ├── Redisson                   ← 锁 / 限流 / 延迟队列
│   ├── SMS4J / IJPay / X-File-Storage
│   └── Spring AI                  ← ★ 只是这一层里的一块
│       ├── ChatClient / ChatModel    ← 模型调用抽象
│       ├── Tool Calling              ← 工具调用
│       ├── ChatMemory                ← 会话记忆
│       ├── Structured Output         ← 结构化输出
│       └── VectorStore / Advisors    ← 向量检索与拦截
└── 前端
```

**Spring AI 是 Spring Boot 应用里的一个依赖（一组 starter），不是独立框架。**
它**不提供** Web 层、安全认证、数据访问、事务管理 —— 因此**无法只用它写登录注册**。

本平台约 **80% 的代码**（注册登录、绑定验证、会员额度、解锁、订单支付、作品上架、后台管理、日志）**与 Spring AI 无关**。

**同事的说法可能是想表达这两件事之一（那都是对的）：**
1. "AI 部分不用再选 LangChain4j 或自己写 HTTP 客户端，Spring AI 一个就够" → ✅ 正确，本方案正是如此
2. "从 Spring AI 的示例工程起步搭项目" → ✅ 可以，但那本质上仍是个 Spring Boot 工程

#### 7.2 版本兼容矩阵（重要）

| 组合 | 说明 | 建议 |
|---|---|---|
| **Spring Boot 3.x + Spring AI 1.x** | 生态成熟，**所有国产库均已适配** | ✅ **本项目采用** |
| Spring Boot 4.x + Spring AI 2.0 | Spring AI 2.0 已 GA，对应 Boot 4 线 | ⚠️ 暂不采用 |

**为什么不用 Spring AI 2.0**：本技术栈含大量国产库（RuoYi-Vue-Pro、Sa-Token、MyBatis-Plus、IJPay、SMS4J、X-File-Storage），它们的 Spring Boot 4 适配通常**滞后半年到一年**。
**为了 Spring AI 2.0 的新特性把整个生态拖进 Boot 4，风险远大于收益。** 等 M4/M5 生态跟上后再评估升级。

**依赖清单示例**（Spring AI 只是其中一行）：

```
spring-boot-starter-parent
  ├── spring-boot-starter-web
  ├── spring-boot-starter-validation
  ├── mybatis-plus-boot-starter
  ├── sa-token-spring-boot3-starter
  ├── redisson-spring-boot-starter
  ├── flyway-core
  ├── smsj-spring-boot-starter
  ├── ijpay-*
  ├── x-file-storage-spring-boot-starter
  └── spring-ai-starter-model-openai     ← 与其他 starter 平级
```
**✅ 推荐：Spring AI**

理由：
1. 团队用 Spring Boot，Spring AI 是**零心智负担**的延伸
2. 本平台三个硬需求它都覆盖：
   - **结构化输出**（对应规格 §8.4 的 JSON Schema 强约束）
   - **ChatMemory**（对应 §8.5 会话与记忆）
   - **Tool Calling**（对应 §8.8 提示词 × Tool 联动）
3. **不要 Spring AI 和 LangChain4j 同时用**，二选一即可

## 8. Prompt 管理与 LLM 可观测

| 项目 | 许可证 | 优点 | 缺点 |
|---|---|---|---|
| **Langfuse** | ⚠️ 核心 MIT + `ee/` 另有许可 🔍 | prompt 版本管理 + trace + **成本归因** + 评测集 + 数据集；可自托管；**旁路上报，不侵入主干** | 有企业版功能需付费 |
| Helicone | ✅ Apache-2.0 🔍 | 轻量代理式、成本分析直观 | 自托管版功能少于云版 |
| Phoenix (Arize) | ⚠️ 需核实（ELv2 风险） | 评测与可视化强 | 许可需仔细看 |
| OpenLLMetry | ✅ Apache-2.0 🔍 | 纯 OTel 埋点，接入现有观测栈 | 只有 trace，没有 prompt 管理 |

**✅ 推荐：Langfuse（可选，M5 再上）**

理由：
1. **一次覆盖三个诉求**：prompt 版本化（规格 §8.2）、每次调用成本归因（§8.6）、调用链审计
2. **旁路集成**：你的服务端调它的 API 上报即可，**不改变主链路**，随时可摘
3. 可以很晚才决定上不上——**先自研 prompt 表 + ClickHouse 记录 `AI_CALL`，等评测需求上来再引**

**注意**：核心是 MIT，但 `ee/` 目录另有许可（与 LiteLLM 同模式），自托管用核心功能没问题。

## 9. 声明式工具组合引擎 ★（本方案最关键的一条）

> 这是规格 §8.9.2 里"作品自定义工具 = 声明式组合"的落地引擎。需求是：**用平台原子能力拼装出工具，支持顺序/分支/循环/子调用/事务/重试/超时，管理员不写代码。**

| 项目 | 许可证 | 优点 | 缺点 |
|---|---|---|---|
| **LiteFlow** | ✅ Apache-2.0 🔍 | **国产规则/流程编排引擎**；组件化编排；EL 表达式写流程；支持 `THEN/WHEN/IF/SWITCH/FOR/WHILE`；Spring Boot 集成好；中文文档 | 偏"业务规则编排"，需要做一层 DSL 到 EL 的转换 |
| 自研步骤机 | — | 完全贴合需求 | **重复造轮子**（分支/循环/事务/重试都要自己实现并写测试） |
| Warm-Flow | ✅ 开源（dromara）🔍 | 国产轻量工作流，可 jar 引入设计器，解决 Flowable/Activiti 复杂的问题 | 面向**审批流**（人工节点），与本需求不完全对口 |
| Flowable / Camunda | ✅ Apache-2.0 | 功能最强、BPMN 标准 | **重**（独立引擎 + 表结构 + 设计器），运维成本高 |
| Temporal | ✅ MIT 🔍 | 持久化工作流、补偿、重试一流 | 要额外部署 Server；本需求用不上其全部能力 |

**✅ 推荐：LiteFlow**

理由（**这是本建议书里性价比最高的一条**）：

规格 §8.9.2 要求的 12 项表达能力，LiteFlow 的 EL 几乎一一对应：

| 规格要求 | LiteFlow 对应 |
|---|---|
| 顺序执行 | `THEN(a, b, c)` |
| 条件分支 | `IF(x, a, b)` |
| 多路分支 | `SWITCH(x).to(a, b, c)` |
| 循环 | `FOR(n).DO(a)` / `WHILE(x).DO(a)` |
| 并行 | `WHEN(a, b, c)` |
| 子流程/子工具调用 | `THEN(a, SUB("chainId"))` |
| 超时/重试 | 组件级配置 |
| 事务 | Spring `@Transactional` 标注在组件上 |
| 变量传递 | `ContextBean` |

**落地方式**：管理员在后台用**可视化步骤编辑器**产出 JSON → 平台把它编译成 LiteFlow 的 EL 链 → LiteFlow 负责执行。**你只需要写"原子能力组件"（约 12 组，对应规格 §8.9.1），编排交给 LiteFlow。**

> 这一条把"自研工作流引擎"的工作量从"2 个月"压到"2 周"。

| Formily | ✅ MIT 🔍 | 表单/布局 Schema | 面向表单，不适合手机界面 |
| Mitosis | ✅ MIT 🔍 | 一次编写编译到多框架 | 解决的是另一个问题 |

**✅ 推荐：自研轻量 DSL（渲染器）+ JSON Schema（校验）**

理由：
1. **目标场景是固定布局**（手机外壳/微信/朋友圈/相册/备忘录/钱包），不是"任意中后台页面"。amis 的组件库表达力过剩、体积过大

3. 校验层用 **networknt/json-schema-validator**（✅ Apache-2.0，Java 最主流 JSON Schema 实现）——**这一块不要自研**
4. 后台的"可视化布局编辑器"（拖拽产出 `layout.json`）可以后期再做，M5 先手写 JSON + Schema 校验

**若后期需要可视化搭建** → 评估 **amis** 的编辑器部分或 **LowCode Engine**。

## 30. MySQL 适配说明（若主库选 MySQL 8.0）

### 30.1 结论：可以，而且对你们可能更优

| 维度 | 判断 |
|---|---|
| 功能匹配 | ✅ 完全够用。本平台没有 PG 专属的复杂查询场景 |

### 30.2 六处必须改的设计

#### 🔴 1. 分区表唯一键限制（会导致建表直接失败）

MySQL 规定：**Every unique key on the table must use every column in the table's partitioning expression**（含主键）。
来源：[MySQL 8.0 Reference Manual 26.6.1](https://docs.oracle.com/cd/E17952%5F01/mysql-8.0-en/partitioning-limitations-partitioning-keys-unique-keys.html)

所以下面这条在 MySQL 里**根本建不出来**（ERROR 1503）：

```sql
-- ❌ MySQL 建不出来：唯一键 idempotency_key 没包含分区列 created_at
CREATE TABLE ledger_entry (
  id BIGINT PRIMARY KEY,
  idempotency_key VARCHAR(64) UNIQUE,
  amount DECIMAL(18,6),
  created_at DATETIME
) PARTITION BY RANGE (TO_DAYS(created_at)) (...);
```

**受影响表**：`ledger_entry`、`log_biz`、`log_audit`、`log_sec`、`usage_event`（原设计都按时间月分区）

**三种解法**：

| 方案 | 做法 | 适用 |
|---|---|---|
| **A. 幂等键独立成表**（推荐） | 新建 `idempotency_guard(idempotency_key PK, scene, ref_id, created_at)`，**不分区**。流程：先插 guard → 冲突即返回原结果 → 再插业务表 | 账本、解锁、支付回调 |
| **B. 复合主键** | 主键改 `(id, created_at)`，取消全局唯一键，幂等交给 guard 表或 Redis `SETNX` | 日志表 |
| **C. 不分区 + 归档表** | 热表 + `_archive` 表定时迁移。分区的目的本就是"快速删旧数据"，归档同样能达到 | 日志表 |

**推荐组合**：
- **账本/解锁/支付类** → 方案 A（额外一张小表，换来干净的幂等语义）
- **日志类** → 方案 C（日志不是必须分区；归档 + 定期 `DELETE ... LIMIT` 也能活）
- **ClickHouse 的几张表不受影响**（`log_access` / `log_ai_call` / `log_tool_call` 用 ClickHouse 自己的分区语法）

> 方案 A 的额外好处：**统一了全平台的幂等处理**。解锁、绑定、支付回调、AI 扣费都能复用同一张 guard 表，不用各写一套。

#### 2. 无 `RETURNING`

| PG | MySQL |
|---|---|
| `INSERT ... RETURNING id` | `SELECT LAST_INSERT_ID()` |

MyBatis-Plus 的 `useGeneratedKeys="true"` + `keyProperty` 会**自动处理，业务代码无感**。
唯一要注意：批量插入时 `LAST_INSERT_ID()` 语义与 PG 的 `RETURNING` 不同。

#### 3. 无 pgvector → 语义缓存改 Redis Stack

| 原设计 | MySQL 下改为 |
|---|---|
| pgvector（复用 PG） | **Redis Stack**（RediSearch + 向量检索，复用已有 Redis） |

注意：MySQL 9.0 才有原生 `VECTOR` 类型，且仅 HeatWave（Oracle 云），**云上 RDS MySQL 不可用**。

#### 4. DDL 非事务性

| PG | MySQL |
|---|---|
| 支持事务性 DDL，迁移失败可整体回滚 | **每条 DDL 隐式提交**，中途失败留下半完成状态 |

**对策**：
1. **一个迁移文件只做一件事**（一条 `ALTER` 或一张表）
2. 迁移前**自动备份**（Flyway 前置钩子 + RDS 快照）
3. **禁止**在同一迁移里混 DDL + 大表 DML
4. Flyway 配置 `cleanDisabled=true`（防止误执行 `clean` 清库）
5. 大表 `ALTER`（如加索引）走 `pt-online-schema-change` 或 `gh-ost`，避免锁表

#### 5. JSON 检索能力弱

| PG | MySQL |
|---|---|
| `JSONB` + GIN 索引 + `@>` 包含查询，检索强 | `JSON` 类型，检索需**生成列 + B 树索引** |

**对策：需要按条件查的字段，一律抽成独立列，不要塞在 JSON 里。**

| 场景 | 是否受影响 |
|---|---|
| `game_save.state_json` | ✅ 无影响（整存整取，从不按 JSON 内的值查询） |
| 作品 manifest | ✅ 无影响（`type`/`status`/`version` 本来就是列） |
| 工具定义 | ⚠️ 需把 `tool_name` 从 JSON 抽成列（要按名字查） |
| 结构化输出校验 | ✅ 无影响（在应用层校验，不进库） |

#### 6. 数组类型

| PG | MySQL |
|---|---|
| `TEXT[]`、`INT[]` 原生数组 | 用 `JSON` 数组或关联表 |

**受影响**：`log_audit.roles TEXT[]` → 改 `JSON`（审计日志的 roles 只读不查，JSON 足够）。

### 30.3 MySQL 反而更好的地方：中文全文检索 ✅

| 维度 | MySQL 8.0 | PostgreSQL |
|---|---|---|
| 中文分词 | **内置 ngram 分词器**（5.7+），开箱即用 | 需装 `pg_jieba` / `zhparser` 扩展 |
| 云 RDS 可用性 | ✅ 直接可用 | ⚠️ **很多云 RDS 不让装扩展或需提工单** |
| 分词精度 | 🔶 二元分词，不支持自定义词典/停用词/同义词 | ✅ 精准分词，支持词典 |

**结论**：对"作品名 + 简介"这种简单搜索场景，**MySQL 的 ngram 够用且更省事**（少一个扩展依赖，符合"运维简单"）。

```sql
ALTER TABLE work
  ADD FULLTEXT INDEX ft_work (name, summary) WITH PARSER ngram;

SELECT id, name FROM work
WHERE MATCH(name, summary) AGAINST ('都市 悬疑' IN BOOLEAN MODE);
```

### 30.4 字符集与排序规则（MySQL 必看）

| 项 | 必须 |
|---|---|
| 字符集 | **`utf8mb4`** —— 绝不能用 `utf8mb3`/`utf8`（存不了 emoji，而文游里 emoji 是刚需） |
| 排序规则 | MySQL 8.0 默认 `utf8mb4_0900_ai_ci`；中文可评估 `utf8mb4_zh_0900_as_cs` |
| 连接串 | 显式 `characterEncoding=utf8mb4` |
| 表/列级 | 建表时统一指定，不要依赖库默认 |

**这一条如果配错，上线后改起来极痛苦**（要重建全库）。

### 30.5 其他 MySQL 注意点

| 项 | 说明 |
|---|---|
| 存储引擎 | **必须 InnoDB**（事务 + 行锁）；禁用 MyISAM |
| **隔离级别** | MySQL 默认 **REPEATABLE READ**（PG 是 READ COMMITTED）。<br>**解锁/绑定的 CAS 更新**（`UPDATE ... WHERE unlocked_count < available_count`）在该级别下**依然安全**（`UPDATE` 是当前读，会加行锁）——但要注意"快照读"与"当前读"的区别，`SELECT` 后判断再 `UPDATE` 的写法不安全，**必须用单条 CAS 语句** |
| 自增主键 | `BIGINT AUTO_INCREMENT`；MySQL 8.0 已持久化自增值，重启不回退 |
| 大字段 | `TEXT`/`BLOB` 放独立扩展表，避免主表行溢出影响查询 |
| 时区 | 统一 `Asia/Shanghai`，连接串显式 `serverTimezone=Asia/Shanghai` |
| 慢查询 | 开 `slow_query_log` + `long_query_time=1`，用 `pt-query-digest` 分析 |
| 连接池 | HikariCP（Spring Boot 默认）；`maximumPoolSize` 建议 `CPU核数×2 + 磁盘数` |
| 分区替代 | 日志类用**归档表 + 定时清理**替代分区（见 30.2 方案 C） |

### 30.6 一句话总结

**用 MySQL 8.0。** 要做的改动只有 6 处，而且**都不难**：
- 幂等键抽成独立的 `idempotency_guard` 表（反而让全平台幂等统一了）
- 日志表不分区，改归档
- 语义缓存从 pgvector 换成 Redis Stack（本来就在架构里）
- 迁移文件拆细 + 前置备份
- 需要查的 JSON 字段抽成列
- `TEXT[]` 改 JSON

**唯一真正放弃的是 pgvector**，而它本来就是 M6 的可选项。
